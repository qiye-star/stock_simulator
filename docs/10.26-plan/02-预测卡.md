## 0. 摘要

- 开启事件模式的存档里，**重大事件的第一条快讯发布时**，B 挂在 A 的发布钩子上生成一张预测卡，钩子返回 True，A 把存档暂停并停止本批推进（含补推、跳过）。卡上 1–3 道题：方向+幅度 5 档（RPS）、产业链冲击排序前 3（NDCG@3）、传闻真假（2 档 RPS），全部由 `GameEvent` + 存档 seed 确定性生成。
- 作答截止 = **触发后行情再出现一个交易 tick 之前**（市场暂停时没有时间压力，恢复行情且未答即作废）。提交时默认自动继续行情。
- 出卡频率随存档时钟版本：v1 约每 8–12 分钟一张；v2 每交易日（normal 档约 20.5 分钟）1–2 张。
- 结算：方向/排序题在窗口（触发日起 3 个交易日；v1 约 3 分钟、v2 normal 档约 1 小时现实时间）收盘后，传闻题在揭晓 tick 后。每题 0–100 分，**积分 = 分数**（保持评分规则的严格适当性），每张卡一次入账。另算“基线分”（相对瞎猜）、校准表、同伴分（给 C）。
- **积分账本按用户记账**：`point_accounts`（余额，乐观锁，CHECK ≥0）+ `point_ledger`（流水，`UNIQUE(user_id, idempotency_key)`）。`services/points.py` 的 `credit/debit` 不提交事务，C/D/E 统一通过它记账。
- 计分纯函数放 `domain/scoring.py`（RPS、NDCG、桶、基线分、同伴分、校准表），题目生成与称号放 `domain/predictions/`。
- 积分用途：情报卡（揭示边强度档/延迟、传闻真假提示，调 A 的 `reveal_edge` / `rumor_hint`）、用户级称号、C 的排行。
- 新增 8 张表、6 个错误码、11 个 REST 接口、2 种 WS 消息；网页新增 `features/predictions/`，手机端新增预测卡组件与 2 个页面。

### 1.1 积分账本 `backend/src/stocksim/services/points.py`

**归属**：积分属于**用户**，不属于存档。删存档不影响余额与流水（流水的 `save_id` 置 NULL）。删用户级联删除。

**表**（完整列见 §9）：
- `point_accounts`：PK `user_id`；`balance`、`lifetime_earned`、`lifetime_spent`、`entry_seq`、`equipped_title`、`version`（乐观锁）。`CHECK balance >= 0`。
- `point_ledger`：每次变动一行；`delta`（带符号）、`balance_after`、`reason`、`ref`、`idempotency_key`、`save_id?`、`meta?`。`UNIQUE(user_id, idempotency_key)`，`UNIQUE(user_id, seq)`，`CHECK balance_after >= 0`。

**函数**（全部 keyword-only；**都不 commit**，由调用方在自己的事务里提交）：
```python

**不提供系统账户、不提供 `lock_account`**（一致性核对 2026-10-26 定稿，04 已按此改写）：
- 账本只记**用户**积分的变动，余额恒 ≥ 0。D 的做市补贴不是任何用户的余额变动，**不进本账本**：资金池与补贴发行量记在 D 自己的表（`prediction_markets.pool_points / subsidy_points / subsidy_returned_points`，04 §5.6 给出含发行量的守恒式）。
- 不加悲观锁：`credit/debit` 每次都改 `point_accounts` 行并带 `version` 乐观锁，同一用户的并发事务（含 D 跨市场下单）在 flush/提交时冲突，调用方整体重试即可。D 的“额度检查在扣款之后才可信”由此保证：额度查询与扣款在同一事务，冲突重试时会重读额度。
- 锁顺序约定：调用方若先锁了自己的行（如 D 的市场行 `FOR UPDATE`），再调 `credit/debit`；同一事务里给多个用户记账时按 `user_id` 升序调用，避免 PostgreSQL/MySQL 上互等。

**语义**：
1. **幂等**：先按 `(user_id, idempotency_key)` 查；命中且 `(reason, delta, save_id)` 相同 → 原样返回已有流水，不改余额；不同 → 抛 `LedgerConflict`。同一事务里重复调用也命中（autoflush 可见）。
2. **账户自动开户**：`credit`/`debit` 内部先 `open_account`。
3. **并发**：改 `point_accounts` 时依赖 `version` 乐观锁（与 `saves.version` 同一套，sqlite/postgres/mysql 通用，不用 `SELECT … FOR UPDATE`）。`credit/debit` 在写完流水后立即 `db.flush()`，冲突会就地抛 `StaleDataError`（版本冲突）或 `IntegrityError`（幂等键/seq/开户主键冲突），**原样上抛**。调用方必须回滚整个事务并重做（重做时幂等键会命中已提交的流水）。
4. **余额不得为负**：服务层在 `debit` 里检查；DB 的两条 CHECK 是兜底。`credit` 不接受负数；需要扣减一律走 `debit`。`admin_adjust` 也分别用 credit/debit。
5. **seq**：`entry_seq += 1` 后写入流水的 `seq`，用于游标分页（`[seq]` base64url，降序）。
6. **幂等键约定**（≤96 字符，`^[a-z_]+:\S+$`——冒号前是小写来源前缀，之后不含空白；`edge_id` 含中文行业名与 `>`，所以不限制字符集；ref ≤64 字符）：

| 来源 | reason | 幂等键 | ref |
| --- | --- | --- | --- |
| B 开户 | `welcome` | `welcome:{user_id}` | `user:{user_id}` |
| B 预测卡 | `prediction` | `prediction:{card_id}` | `card:{card_id}` |
| B 情报卡·边 | `intel_card` | `intel_edge:{user_id}:{edge_id}:L{level}` | `edge:{edge_id}` |
| B 情报卡·传闻 | `intel_card` | `intel_hint:{save_id}:{event_id}` | `event:{event_id}` |
| C 挑战奖励（03 §7.6） | `challenge` | `challenge:{challenge_id}:{user_id}` | `challenge:{challenge_date}` |
| D 买入 / 卖出（04 §1.1） | `market_buy` / `market_sell` | `market_buy:{trade_id.hex}` / `market_sell:{trade_id.hex}` | `market:{market_id.hex}` |
| D 兑付 / 作废退款 | `market_payout` / `market_refund` | `market_payout:{market_id.hex}:{user_id.hex}` / `market_refund:{market_id.hex}:{user_id.hex}` | `market:{market_id.hex}` |
| E 复盘预测（05 §5.6） | `replay_prediction` | `replay:{user_id.hex}:{level_id.hex}:{qid}`（用 32 位 hex，qid ≤16 时最长 89） | `replay:{save_id.hex}:{qid}` |

**事务辅助**（新文件 `backend/src/stocksim/services/tx.py`，B 引入，C/D/E 可复用）：

def run_in_transaction[T](db: Session, fn: Callable[[], T], *, refresh: Sequence[object] = (),
                          attempts: int = 3) -> T:
    """执行 fn() 后 db.commit()；遇 StaleDataError / IntegrityError 回滚、refresh 给定对象后重试。
    AppError 直接回滚并上抛。最后一次仍冲突则上抛。"""
```

## 2. 现状要点（实施前已核对代码）

- `services/market.py::_run_ticks(db, save, n)` 是唯一推进点，当前返回 None；A 改为返回实际推进数，并在每个有快讯的交易 tick 后调 `run_publish_hooks`，返回 True 时 `save.paused=True` 并跳出循环（01 §6.4）。payload 只在批末写回，所以**钩子运行时 `market_states.payload` 还是批前的值**——B 的钩子不读价格。
- `_advance_to_now_once`：`save.paused` 时直接返回 0；被钩子截停时 A 把 `last_tick_at` 置为 now，丢弃剩余墙钟时间。`skip_clock` → `advance_ticks` → `_run_ticks`，同样会被截停，`skipped_ticks` 为实际推进数。

## 3. 玩法与流程

### 3.1 触发
`predictions.on_publish(db, ctx) -> bool`（在 `main.create_app` 注册；A 在推进事务内调用，**不得 commit**）：
```
if not ctx.save.events_enabled: return False
policy = card_policy(db, save); mode = policy.force_mode or _settings_mode(db, save)   # 无设置行 → "pause"
if not policy.enabled or mode == "off": return False
triggers = [e for e in ctx.events
            if e.major and min(n.trading_tick for n in e.news) == ctx.trading_tick]   # 事件的第一条快讯
created = False
for ev in sorted(triggers, key=lambda e: e.event_id):
    if db.scalar(select(PredictionCard.id).where(save_id==, event_id==ev.event_id)): continue
    tb = timebase(save.clock_rules)
    specs = build_questions(ev, QuestionContext(seed=save.market_seed, trigger_trading_tick=ctx.trading_tick, structure=structure_for(save.events_ruleset), clock_rules=save.clock_rules))
    db.add(PredictionCard(status="open", opened_trading_tick=ctx.trading_tick, opened_tick=ctx.tick,
                          opened_trading_day=tb.day_of(ctx.trading_tick), deadline_trading_tick=ctx.trading_tick,
                          window_days=DIRECTION_WINDOW_DAYS, paused_by_card=True, questions=[q.to_public() for q in specs], …))
    created = True
return created          # True → A 暂停存档并截停本批
```
- **priced_in 事件**在铺垫快讯（precursor）时触发，标题是“市场预期…”，玩家要判断“买预期、卖事实”。
- **传闻**在首发（publish）时触发；证实/辟谣快讯不再出卡。
- 同一 tick 两条重大事件（极少见）→ 两张卡同时 open。
- 卡片只在钩子里创建，切到 `pause` 模式**不补发**过去的事件。

### 3.2 卡片状态机
```
            作答(截止前)                 全部题结算
  open ───────────────▶ answered ─────────────────▶ settled   （入账）
   │                       ▲│ 截止前可重复提交覆盖
   │ 截止(行情又推进了一个交易 tick) / 主动“不答”
   ▼
 expired ── 全部题结算后 settled_at 有值（只展示结果，不发积分）
 任意未结算状态 ── debug reset-market ──▶ void
```
- `deadline_trading_tick = opened_trading_tick`（常量 `ANSWER_GRACE_TRADING_TICKS = 0`）：只要当前 `trading_tick ≤ deadline` 就能提交/覆盖。午休、收盘后不产生交易 tick，所以“恢复行情后在午休里作答”仍然有效，不泄露任何新价格。
- **v2 补充**：语义不变，仍按交易 tick 计（v2 一个 tick = 1 游戏分钟，normal 档 5 秒）。截止前的午休/收盘停留（11:30、15:00 停留期间 tick 不变）与随后的自动快进（跳到 12:59 / 次日 9:29）都不产生交易 tick，不会让卡作废；之后的 13:00 / 9:30 才是下一个交易 tick。注意 11:30 与 15:00 本身是交易 tick（只出价不接单），卡在 11:29 触发后恢复行情，到 11:30 即作废。
- 过期是**惰性**的：`settle_due`、作答接口、列表接口发现 `status=open && 当前 trading_tick > deadline` 时改为 `expired`。

### 3.3 与时钟、补推、多标签页的交互
| 情形 | 行为 |
| --- | --- |
| WS 推送循环补推 / `open_save` 补推 | `_run_ticks` 在触发 tick 截停并暂停，剩余墙钟时间丢弃（A）。玩家离开很久回来，也会停在第一张卡上，不会错过 |
| `clock/skip` | 同样在触发 tick 截停；`ClockOut.paused=true`，`skipped_ticks`=实际推进数。前端据此拉取 open 卡并弹出 |
| 玩家提交，`resume=true`（默认） | 同一事务内：若 `save.paused` 且该存档**没有其它 open 卡** → `save.paused=False`、`last_tick_at=now`（与 `resume_clock` 等价） |
| 玩家提交，`resume=false` | 只存答案，保持暂停（“提交并留在暂停中看盘/下单”） |
| 玩家未答就点继续或跳过 | 后端不拦截（`clock/*` 不改）。前端在调用前检查本地 open 卡并弹确认“继续将放弃本张预测卡”。下一个交易 tick 后该卡过期 |
| 卡片打开时手动“暂停” | 已经是暂停态，`pause_clock` 幂等无变化 |
| 暂停中手动下单 | 允许（现状如此）。触发 tick 时首 tick 冲击已计入价格（01 §5.4 knot `(0, I)`），暂停不额外放大信息优势 |
| 多标签页 | 每个 WS 连接都会推 `prediction` 消息（§10.3）。A 标签提交 → B 标签收到 `op=answered` 关弹层；A 标签恢复行情 → B 标签收到 `op=expired`。两个标签同时提交 → 卡片 `version` 乐观锁，后者重试后覆盖（截止前以最后一次为准） |
| `prediction_mode=off` | 钩子返回 False，不出卡、不暂停 |
| 存档没开事件模式 | A 不调钩子；B 的存档级接口 409 `EVENTS_DISABLED` |
| `debug/time` 改分钟 | v1 只影响展示用的 `clock_minute`；截止和结算都按交易 tick，不受影响。v2 的 `debug/time` 只向前推进（07 §6.6），等同跳过，可能被钩子截停 |
| v2 自动快进（07 §5.2） | 有 open 卡时存档已暂停，暂停期间不快进，**不需要“有 open 卡就阻止快进”的额外规则**；玩家不答直接 resume 后快进照常，卡在下一个交易 tick 过期 |
| v2 离线补推 | 补推上限按交易 tick 计（300 个，约 1.2 个交易日，07 §5.3），仍在第一张卡的触发 tick 截停 |

### 3.4 结算时点
| 题 | 可结算条件（`cur_tt` = 当前 `_meta.trading_tick`） | 真值 |
| --- | --- | --- |
| `dir` 方向+幅度 | `cur_tt ≥ tb.first_tt(d0 + W)`（v1 即 `20·(d0+W)`，v2 即 `242·(d0+W)`，都是次日开盘的换日 tick），即窗口最后一日 `d0+W−1` 已收盘、candles 已落库 | 窗口涨跌幅 bp（§4.1） |
| `rank` 排序 | 同上 | 窗口末 tick 的理论冲击排名（§4.2） |
| `rumor` 真假 | `cur_tt ≥ ev.rumor.resolve_trading_tick` | `ev.rumor.truth` |

`settle_due(db, save) -> SettleReport`（**自己 commit**，经 `tx.run_in_transaction`，幂等）：
1. 取该存档 `status ∈ {open, answered, expired}` 且 `settled_at IS NULL` 的卡（`IX(save_id, status)`）。
2. open 且 `cur_tt > deadline` → `expired`。
3. 对每道可结算且未结算的题：算真值写入 `card.outcomes[qid]`；如果有答案，算 `score / uniform_score / baseline / p_outcome_pct / hit` 写入 `prediction_answers`。
4. 卡上所有题都已结算 → `settled_at=now`；`answered` → `settled`，`points = Σ 各题分数`；按 `card_policy` 决定是否入账：`points.credit(user_id, delta=实际发放, reason=policy.points_reason, ref=f"card:{id}", idempotency_key=f"prediction:{id}", save_id, meta={"event_id","scores"})`。日上限：`sum_since(reasons=["prediction"], since=UTC 当日 0 点)`，超出部分不发，`points_capped=true`。
5. 结算后跑称号判定（§8），新解锁写 `user_titles`。

调用点：`api/ws.py::tick_once`（`advance_to_now` 与自动交易之后，存档开启事件时）、`GET /saves/{id}/predictions*` 与 `GET /points/stats`（读之前）。

### 3.5 reset 与删档
- `on_reset(db, save)`（A 在 `debug.reset_market` 换 seed 前调用，不 commit）：该存档 `settled_at IS NULL` 的卡 → `status=void, settled_at=now`，不发积分；删除该存档的 `intel_rumor_hints`（事件内容随 seed 改变；不退款）。已结算的卡与流水保留。边揭示是用户级、与 seed 无关，保留。
- 删存档：卡、答案、传闻提示级联删除；流水保留（`save_id` 置 NULL）；已解锁称号保留。统计与校准只按现存卡计算，删档后会变少（已知、可接受）。

### 4.1 方向+幅度题 `dir`（kind=`bucket`，5 档，RPS）
- **目标**：scope=industry → 源行业（`target_kind="industry"`，n=`stock_count`）；scope=stock → 源股票（`"stock"`，n=1）；scope=market → 全市场（`"market"`，n=385，`target=null`）。
- **窗口**：`d0 = tb.day_of(trigger_trading_tick)`（v1 即 `// 20`，v2 即 `// 242`），`from_day = d0`，`to_day = d0 + W − 1`（W=3，两版相同；v2 下约 1 小时现实时间，是否缩短见 Q5）。口径：**`d0−1` 日收盘 → `to_day` 收盘**。触发前当日已走出的部分玩家看得到，属于公开信息。
- **真值** `change_bp`：统一经 `change_bp_for(db, save, target_kind=…, target=…, from_day, to_day)`（§1.3）。其中 industry 调 `events.industry_change_bp(db, save, industry, from_day, to_day)`；stock/market 由 B 自算，口径与 A 相同：逐股 `round_half_up_div((close_to − close_from_prev)·10000, close_from_prev)`，再对 n 只 `round_half_up_div(Σ, n)`。返回 None（理论上不会）→ 该题作废，不计分。
- **档位边界**（只依赖公开的 n、W、目标类型，**不依赖 M**，不泄密；公开函数 `bucket_edges_bp(target_kind, n, W)`，D 的分档合约直接调用它，保证同一事件的预测卡、挑战题与市场档位一致）：
  ```

  sigma = isqrt(W · (I²·10⁴ + n·K²·10⁴) // n) // 100           # ≈ √W·√(I²/n + K²)；v1（K=0）与原式 isqrt(516²·W·10⁴//n)//100 逐位相同
  e1 = max(round_half_up_div(sigma, 20)·10,   FLOOR[kind][0])          # ≈ σ/2，取整到 10bp
  e2 = max(round_half_up_div(3·sigma, 20)·10, FLOOR[kind][1], e1+20)   # ≈ 1.5σ
  edges_bp = (−e2, −e1, e1, e2)；outcome = bucket_of(change_bp, edges_bp)
  ```

### 4.2 产业链冲击排序题 `rank`（NDCG@3）
- **只对 scope ∈ {industry, stock} 出题**（market 事件不走传导图）。题面：“到 D{to_day} 收盘，**除源行业外**，哪 3 个板块受这条消息的冲击最大（不论涨跌）？按从大到小排”。
- **真值用理论冲击，不用实际涨跌**：`impact_at(ev, v, tt_end) = |scale_ppm_v · S(tt_end − publish_tt − delay_v)| / 1e6`，`tt_end = tb.first_tt(to_day+1) − 1`（to_day 的最后一个交易 tick：v1 为 `20·(to_day+1) − 1`，v2 为 `242·(to_day+1) − 1`，即 15:00）；`S` 是 A §5.4 的形状曲线（`_shape_at` 适配 A 的 `eval_path`）。理由：35 个行业只有 1–2 只股票，实际涨跌的噪声会让诱饵随机“上榜”，题目变成抽奖；理论冲击只取决于产业链结构、强度、延迟，正是情报卡揭示的东西。结算页同时展示每个候选的实际涨跌供参考。
- **候选**（8 个，确定性）：
  1. `T` = `ev.impacts` 中行业 ≠ 源行业、`impact_at ≥ RANK_MIN_IMPACT_PPM` 的节点，按 (`impact_at` 降序, 行业下标升序) 排；`len(T) < 3` → **不出排序题**。
  2. `include = T[:RANK_TRUE_MAX]`（3–5 个）。
  3. 诱饵池 = 全部行业 − 源行业 − include；结构邻居（源行业 2 跳内的 `neighbors`）权重 3，其它权重 1；用 §4.4 的 RNG 做不放回加权抽样，`j = 0..` 依次抽 `RANK_CANDIDATES − len(include)` 个。
  4. 候选按**行业下标**排序后输出（显示顺序与冲击无关）。
- **相关度**（结算时 `resolve_rank`）：候选按 (`impact_at` 降序, 下标升序) 排，前 3 个且 `impact_at > 0` 的依次 3/2/1，其余 0。因为 T 至少 3 个且都在候选里，前三一定来自 include。

## 5. 计分（`domain/scoring.py`）

### 5.1 RPS（方向题、传闻题）
- 定义：`RPS = 1/(K−1) · Σ_{j=0}^{K−2} (F_j − O_j)²`，F/O 为预测/结果的累积分布；得分 `round(100·(1−RPS))`。
- 整数实现（概率为百分比）：`S = Σ_{j<K−1} (cumP_j − cumO_j)²`（cumO_j ∈ {0,100}），`score = round_half_up_div((K−1)·10⁶ − 100·S, (K−1)·10⁴)`。
- 均匀分布精确值：`T = Σ_{j<K−1} ((j+1)·100 − cumO_j·K)²`，`uniform = round_half_up_div((K−1)·10⁶·K² − 100·T, (K−1)·10⁴·K²)`。K=5：结果在 0/1/2/3/4 档时分别为 70/85/90/85/70；K=2：75。
- 示例（K=5，`probs_from_pick(3, 70, 5) = [7,7,8,70,8]`，cumP = 7,14,22,92）：

| 实际档 | S | 得分 | 均匀分 | 基线分 |
| --- | --- | --- | --- | --- |
| 3（猜中） | 49+196+484+64=793 | 98 | 85 | +87 |
| 4（偏一档） | 49+196+484+8464=9193 | 77 | 70 | +23 |
| 0（反向） | 8649+7396+6084+64=22193 | 45 | 70 | −36 |
- 传闻题：`[20,80]`，证实 → 96、辟谣 → 36；均匀 75。

### 5.2 `probs_from_pick(pick, conf_pct, k)`
`conf_pct ∈ [ceil(100/k), 100]`；其余 `100−conf` 平分给另外 k−1 档，余数按“离 pick 近优先、同距下标小优先”逐个 +1。`(3,70,5) → [7,7,8,70,8]`；`(1,80,2) → [20,80]`；`(2,20,5) → [20,20,20,20,20]`。前端（网页 `model.js`、手机 `prediction-card.js`）实现同一算法，并用同一组用例测试。

### 5.3 NDCG@3（排序题）
- `gain(rel) = 2^rel − 1`（3→7，2→3，1→1）；折扣 `DISCOUNT_PPM[i] = round(10⁶·ln2/ln(i+1))`，i=1..10，模块加载时用 Decimal 算好：`(1_000_000, 630_930, 500_000, 430_677, 386_853, …)`。
- `DCG = Σ_{i≤k} gain(rel(order_i))·DISCOUNT_PPM[i]`；`IDCG` 用 relevance 降序；`score = round_half_up_div(100·DCG, IDCG)`；IDCG=0 抛 `ValueError`。`order` 中不在 relevance 的项 rel=0；重复项抛 `DomainError(VALIDATION_ERROR)`。
- 随机期望（候选位置边际均匀）：`E[DCG] = (Σ_c gain_c / n)·Σ_{i≤k} DISCOUNT_PPM[i]`，`uniform = round_half_up_div(100·Σgain·Σdisc, n·IDCG)`。
- 示例：真前三 A(3) B(2) C(1)，`IDCG = 7·10⁶ + 3·630 930 + 1·500 000 = 9 392 790`：
  - `[A,C,B]`：7 000 000 + 630 930 + 1 500 000 = 9 130 930 → **97**
  - `[B,A,X]`：3 000 000 + 4 416 510 + 0 = 7 416 510 → **79**
  - 8 个候选随机：`100·11·2 130 930 / (8·9 392 790)` → **31**；`[B,A,X]` 基线分 = `round(100·(79−31)/69)` = **70**

### 5.4 基线分（单人反馈，不影响积分）
`baseline_score(S, U)`：`S ≥ U` 时 `round_half_up_div(100·(S−U), 100−U)`（U=100 时为 0）；否则 `round_half_up_div(100·(S−U), U)`。把 `[0, U, 100]` 线性映射到 `[−100, 0, 100]`，含义是“比瞎猜强多少”。另提供 Metaculus 口径 `log_baseline_score(p, k) = round(100·(ln p% − ln(1/k))/ln k)`（p 夹到 [1,100]），供 C 选用。

### 5.5 同伴分（给 C）
- 分数差版本：`peer_i = S_i − mean_{j≠i} S_j = round_half_up_div(n·S_i − ΣS, n−1)`；n=1 返回 `[0]`。例：`[80,60,40] → [30,0,−30]`。适用 RPS/NDCG/任何 0–100 分。
- 对数版本（Metaculus）：`L_p = round(10⁶·ln(p/100))`（p 夹到 [1,100]，模块加载时建 101 项表），`peer_i = round_half_up_div(100·(n·L_i − ΣL), (n−1)·10⁶)`。例：`p=[70,40,10]` → `[125, 41, −167]`。理论合计为 0，舍入后误差 ≤ n。
- C 用哪种由 C 定；有序 5 档题建议用分数差版本（对数版本不区分“差一档”和“差四档”）。

### 5.6 校准
- 样本：每道已结算、已作答的概率题（dir、rumor），`claimed = max(probs)`，`hit = (outcome == argmax_pick)`；并列最大（`argmax_pick` 为 None）的不计入。
- `calibration_bins`：10 档 `[0,10) … [80,90) [90,100]`，档号 `min(claimed // 10, 9)`。
- `calibration_error_bp`（期望校准误差，bp）= `round_half_up_div(100·Σ_b |100·hits_b − claimed_sum_b|, N)`；N=0 返回 None。
- 例：`(70,✓)(70,✗)(75,✓)(90,✓)` → 第 7 档 n=3 hits=2 claimed_sum=215，第 9 档 n=1 hits=1 claimed_sum=90；`|200−215| + |100−90| = 25` → `2500/4` = **625 bp**。

### 5.7 积分发放规则（`services/predictions.py`）
- **每题积分 = 该题得分（0–100）**；卡片积分 = 各题之和（2 题最多 200，3 题最多 300）；过期/作废 0。
- 为什么不用“基线分”发积分：积分对得分是仿射变换才保持严格适当（如实报概率期望最高）；`max(0, 基线分)` 这类截断会诱导极端置信（例：真实信念 70% 证实，报 100% 的期望积分 17.5 > 如实报的 11.2），校准曲线就没有意义了。代价是瞎猜也能拿 ~75/题，用日上限控制刷分（见开放问题 Q1）。
- `PREDICTION_DAILY_POINTS_CAP = 2000`（每用户每 UTC 自然日，`reason="prediction"` 的入账合计）。v1 连续跳过可以约每 2 次跳过出一张卡；v2 跳过按关键时点走（8 次一日），约每 5–6 次出一张卡，正常游玩约 4 张/小时（约 600 积分/小时）。上限防的是“多存档 + 狂点跳过 + 乱答”；数值是否下调见 06 §4.3（建议 1000）与 Q1。
- 卡片结果里给出 `score / uniform_score / baseline / points / capped`，前端两种分都显示。

## 6. 积分账本实现要点（契约见 §1.1）

- 模型 `models/points.py`：`PointAccount`（`__mapper_args__ = {"version_id_col": version}`，必须是 Column 对象）、`LedgerEntry`、`UserTitle`。

- 索引：`IX(user_id, created_at)`（日上限、日情报数）、`IX(save_id)`。
- `ledger_page` 游标：base64url(JSON `[seq]`)，降序；非法 → 422 `VALIDATION_ERROR {field:"cursor"}`。

## 15. 风险

1. **刷分**：积分 = 原始分，瞎猜约 75/题；多存档并行 + 连点跳过可提高出卡速度。缓解：每日 2000 上限、称号与 C 排行都看基线分/同伴分而不是积分。若仍不够，可加“同一用户每真实小时最多 N 张计分卡”（Q1）。
2. **理论真值与实际涨跌不一致**：排序题按理论冲击判分，结算页会出现“排名第 1 的板块实际只涨 0.3%”。缓解：结算页文案写明“按事件冲击排序（剔除随机波动）”，并并列展示实际涨跌（Q6）。
3. **A 的数据或常量改动**：首版发布后 A 升规则集版本时，老卡结算仍用存档的 `events_ruleset` 重建事件（A 按版本分派），B 的题目 JSON 在出卡时已固化，`rules_version` 预留按版本分派。
4. **钩子在推进事务内**：钩子只做少量查询 + `db.add`，不读行情、不 commit；`structure_for` 按规则集版本缓存，避免每次读文件。
5. **settle_due 频率**：每个 WS 连接每轮一次（v1 默认每 3 秒；v2 每个游戏分钟醒一次，normal 档 5 秒，07 §5.5），查询走 `IX(save_id, status)`；大量历史卡不影响（只查未结算的）。
6. **公开数据**：边强度写在仓库 JSON 里，情报卡是“玩法上的隐藏”（01 风险 7 同）。
7. **多标签确认框只在前端**：第三方客户端直接调 `/clock/resume` 会让卡作废，这是预期行为。

## 16. 开放问题（需用户拍板）

- **Q1 积分口径**：本计划“每题积分 = 得分（0–100）+ 每日上限 2000”，保持适当性、易理解，代价是瞎猜也有 ~75/题。备选“积分 = max(0, 基线分)”更防刷但会诱导极端置信、校准曲线失真。选哪个？上限多少？
- **Q2 开户赠送**：新用户送 200 积分，便于先体验情报卡。是否需要？
- **Q3 情报卡价格与归属**：边 L1 100 / L2 200（补差 100）/ 传闻提示 80；每日 8 次。边揭示按**用户**永久生效（档位是静态数据），传闻提示按存档。是否同意？C 的挑战存档是否禁用情报卡（由 C 通过 `CardPolicy.intel_allowed` 决定）？
- **Q4 截止规则**：“行情再走一个交易 tick 就作废”，即未答就点继续 = 放弃。是否要改成“继续后仍有 N 个交易 tick 宽限”（会泄露部分走势，需要打折）？
- **Q5 窗口长度**：方向/排序题固定 3 个交易日（v1 约 3 分钟、v2 normal 档约 1 小时真实时间）。是否要按事件类型变化（如传闻用到揭晓为止）？v2 是否缩短为 2 日（约 40 分钟，07 的建议）？本计划保留 3 日：C 的回合题与 D 的分档合约共用这个窗口（03 的 `MAX_BURST_TT = 3N` 按它定），v2 的形状与传导延迟按交易日等比放大，3 日窗口下排序题的出题率与 v1 相同；缩到 2 日会让滞后 2 日的传导节点来不及到达，排序题变少。
