# 07 · 时钟规则 v2：时钟一天 = K 线一天

> 前提：[00-背景与决策.md](00-背景与决策.md) 决策 10（时钟节奏）、决策 12（手机端交易状态栏）。与 [01-事件行情.md](01-事件行情.md) 的 A2 步骤（第 5–9 步）有合入顺序约束，见 §10.2。
> 本文的 API、列名、常量在**实施时**才写入 `docs/CONTRACT.md` 与 `backend/src/stocksim/models/CLAUDE.md`；本目录不是契约来源。
> §1「对外契约」是 08（手机端）与 01–05 唯一应引用的部分；其余小节是实现细节，可以在不破坏 §1 的前提下调整。

## 0. 摘要

- **规则按存档分版本**：`saves.clock_rules`（int，1 或 2）。迁移把现有存档设为 1，新建存档为 2。v1 的行情、节奏、跳过、成就窗口与现在逐位一致，由现有金值测试 `test_market_engine_golden.py` 守护，该测试一字不改。
- **不与 `events_ruleset` 合并**：两者是正交的两个维度。事件算法从 `clock_rules` 派生出时间基 `TimeBase`，再按 `(clock_rules, events_ruleset)` 唯一确定（§3.2）。
- **v2 引擎**：每个交易日固定 242 个交易 tick（9:30–11:30、13:00–15:00 的 242 个分钟），沿用 v1 的“换日 tick”结构，只把 20 换成 242。新存档固定从 9:30 开局，因此**换日恰好发生在次日 9:30**，15:00 收盘后行情仍显示当日涨跌。单 tick 波动重新标定：个股特质噪声 + 全市场共同因子 + 按“股票×交易日”抽取的波动档位与少量趋势日。预估日收益标准差约 2.3%，触及涨跌停约占 0.8% 的“股票·交易日”，熔断不触发（§4.3）。
- **节奏**：交易时段每个游戏分钟对应 `ms_per_minute` 毫秒，三档 2500 / 5000 / 7500，一个交易日分别约 10 / 20 / 30 分钟，默认 5000。为此新增用户设置 `users.clock_speed`，**不复用** `refresh_rate_ms`（§5.1）。
- **自动快进放在服务端** `advance_to_now`，由纯函数 `clock.plan_catchup_v2` 按“锚点 + 停留时长”计算：11:30 停 5 秒后跳到 12:59；15:00 停 15 秒（收盘小结）后跳到次日 9:29。跳转复用现有 `_run_ticks`，和“跳过”走同一条路径，结果确定。多标签页、离线补推、暂停、预测卡截停的行为都有定义（§5）。
- **撮合时间窗**：v2 只在 `[9:30, 11:30)` 和 `[13:00, 15:00)` 接单。11:30 与 15:00 这两个 tick 只产生收盘价，停留期间下单返回 `MARKET_CLOSED`（§4.2）。
- **对外**：`ClockOut` 与 WS `tick.clock` 增加 `clock_rules / phase / trading / next_event / ms_per_minute / next_tick_at / fast_forward_at / server_time`；WS 新增 `{"t":"phase"}` 消息；新增 `GET /api/v1/saves/{id}/day-summary` 作为收盘小结的数据源；`/me` 增加 `clock_speed`；`SaveOut` 增加 `clock_rules`。**不新增错误码**。

| 字段 | 类型 | 新增？ | 说明 |

### 1.3 `phase` 与 `next_event` 定义
| phase | v1 分钟区间 | v2 分钟区间 | next_event.kind / minute |
| --- | --- | --- | --- |
| `pre_open` | `[0, 570)` | `[0, 570)` | `open` / 570 |
| `morning` | `[570, 690]` | `[570, 690)` | `lunch` / 690 |
| `lunch` | `(690, 780)` | `[690, 780)` | `reopen` / 780 |
| `afternoon` | `[780, 900]` | `[780, 900)` | `close` / 900 |
| `closed` | `(900, 1440)` | `[900, 1440)` | `open` / 570（次日） |

v1 的端点归属沿用 `is_trading_time` 的闭区间（v1 在 11:30、15:00 仍可下单）；v2 改成半开区间（§4.2）。
`next_event.at` 的计算：
- v1：`last_tick_at + Δ分钟 × refresh_rate_ms`，Δ 按跨日取模（v1 的非交易分钟也按刷新间隔走，例如 15:00→9:30 是 1110 分钟 × 3 s ≈ 55.5 分钟）。
- v2：交易时段内为 `last_tick_at + Δ分钟 × ms_per_minute`；停在 11:30 / 15:00 时为 `fast_forward_at + ms_per_minute`，即跳到 12:59 / 9:29 后再走 1 分钟；停在 9:29 / 12:59 时为 `last_tick_at + ms_per_minute`。

状态栏的时段进度可以由前端从 `clock_minute` 计算，不需要额外字段：`elapsed = 0（m<570）| m−570（570≤m≤690）| 120（午休）| 120+(m−780)（780≤m≤900）| 240（m>900）`，`progress = elapsed / 240`。

### 1.4 收盘小结数据：`GET /api/v1/saves/{id}/day-summary`
- 参数：`trading_day: int?`，默认当前交易日；允许范围 `[max(0, 当前日 − 30), 当前日]`，超出返回 422 `VALIDATION_ERROR {"field":"trading_day"}`。他人存档返回 404 `SAVE_NOT_FOUND`。入口照常调用 `open_save`。
- 时机：WS 收到 `{"t":"phase","to":"closed"}`，或 REST 看到 `phase=="closed"` 时调用一次，在 `fast_forward_at` 之前展示。离线错过收盘的玩家回来后，如果发现 `trading_day` 比上次看到的大，前端可以用 `trading_day=上次的日` 补看“昨日小结”。
- 响应 `DaySummaryOut`：
```
{ trading_day: int, date: str, clock_rules: "v1"|"v2",
  status: "trading"|"closed",                  // 当前日且尚未收盘 = trading；当前日已收盘或任何过去的日 = closed
  equity_cents: int, prev_equity_cents: int|null, day_pnl_cents: int|null, day_pnl_bp: int|null,
  cash_cents: int|null, market_value_cents: int|null,   // 过去的日取自 equity_snapshots；缺快照时为 null
  trades: { count, buy_count, sell_count, buy_amount_cents, sell_amount_cents, fee_cents, realized_pnl_cents },
  market: { total, up, down, flat, limit_up, limit_down, avg_change_bp },   // 全市场等权；limit_* 按收盘价是否等于涨跌停价
  top_gainers: SummaryQuoteOut[≤5], top_losers: SummaryQuoteOut[≤5],
  holdings: [{code, name, quantity, close_cents, change_bp, market_value_cents}] | null,  // 只有当前日才有，过去的日为 null
  next_open_at: str|null }                     // 当前日、v2、未暂停时 = next_event.at（kind=open），否则 null
SummaryQuoteOut = { code, name, close_cents, change_bp, limit: "up"|"down"|null }
```
- 数据口径：当前日由 `load_market` 状态（`price/prev_close`）与 `portfolio_view` 的当日盈亏计算；过去的日用 `candles`（第 d 日与第 d−1 日的收盘价）、`equity_snapshots`（第 d 日与第 d−1 日；d=0 时“前一日”取初始资金）、`trades.trading_day == d`。v1 存档同样可用（一日 = 20 tick）。

### 1.5 WS 变化
- `tick` 帧的 `clock` 增加 §1.2 的新增字段，计算函数与 REST 共用（`services/market.py::clock_fields`）。
- 新增服务端消息 `{"t":"phase","from":"afternoon","to":"closed","trading_day":12,"clock_minute":900}`：`StreamState` 记住上一帧的 phase，变化时在 tick 帧**之后**发送一次。首帧不发。一次补推跨过多个时段时，只报告“上一帧 → 当前”。

### 1.6 `TimeBase`（01–04 的领域代码用它代替硬编码的 20）
`domain/clock.py`：
```python
@dataclass(frozen=True)
class TimeBase:
    ticks_per_day: int                                   # v1 = 20，v2 = 242
    def day_of(self, trading_tick: int) -> int           # tt // N
    def first_tt(self, day: int) -> int                  # N * day（第 0 日的 offset 0 不会被推进到，与 v1 相同）
    def offset_of(self, trading_tick: int) -> int        # tt % N
    def rolls_at(self, trading_tick: int) -> bool        # tt > 0 and tt % N == 0（这个 tick 先换日再走价）
def timebase(clock_rules: int) -> TimeBase
V2_TRADING_TICKS_PER_DAY = 242
def v2_minute_of_offset(offset: int) -> int              # 0..120 → 570+o；121..241 → 780+(o−121)
def v2_tick_of(day: int, offset: int) -> int             # 全局 tick 的闭式：1440·day + (v2_minute_of_offset(o) − 570)
```

## 2. 现状要点（实施前已核对）

- `domain/clock.py`：交易分钟是 `is_trading_time`，即 `[570,690] ∪ [780,900]`，共 242 分钟，含端点。`TICKS_PER_TRADING_DAY = 20`。`random_start_minute(seed)` 用 `rand_below(seed, -2, 0, 0, 121)`，在 9:30–11:30 中均匀取开局分钟。`skip_target_minutes` 照搬 legacy：交易中跳到 11:29 / 11:39 / 14:59；非交易时段跳到 9:29 / 11:34 / 12:59。夜猫窗口 11:35–11:40 落在午休里。
- `domain/market_engine.py::advance(state, seed, tick, minute, *, drift=None)`（工作区已加 drift）：非交易分钟返回副本；交易分钟时 `trading_tick += 1`，`trading_tick % 20 == 0` 时先 `_rollover` 再走价。第 0 日只有 19 个 tick（tt 1..19），之后每日 20 个。普通股每 tick `rand_below(k=0, 40000) − 20000` ppm；bull_bias 用 k=0、k=1；成交量 `_candle_volume(prev_daily_volume, 当日涨跌, k=2 扰动)` **每 tick 重算**而不是累加，所以 `daily_volume` 是快照，不单调。
- 金值测试 `tests/unit/domain/test_market_engine_golden.py` 已存在，覆盖 seed {1, 2024, 2^62+7}、从 600 分钟起推进 200 个全局 tick。
- `services/market.py`：`_run_ticks` 每分钟调用一次 `advance`（包括非交易分钟）；`decode_state` 中 `day = tt // 20`；`_batch_rolls` 预判本批是否换日，决定是否读取前 4 日 K 线；`_advance_to_now_once` 按 `users.refresh_rate_ms` 计算 `n = elapsed // rate`，超过 `TICK_CATCHUP_MAX`（300）时丢弃多余时间；`advance_ticks` 不看暂停，并把 `last_tick_at` 置为 now；`intraday` 用 `processed = tt − 20·day + (1 if day≥1)` 和单股 sim 重放；`clock_view` 输出 6 个字段。
- `api/ws.py`：每 `refresh_rate_ms` 一轮 `tick_once`：`advance_to_now` → `run_auto_trade` → 做差。`clock` 为 `{minute, trading_day, paused, trading = is_trading_time}`。
- 撮合 `domain/matching.py:108` 与自动交易（`domain/auto_trade/executor.py:98`、`services/auto_trade.py:393`）都用 `is_trading_time` 判断能否下单。`TradeSettings` 只在 `services/trading.py:188` 一处构造。
- 成就：`early_bird`（570–575）、`night_owl`（695–700，在午休里，下单必然 `MARKET_CLOSED`，**现有规则下不可达**），由 `domain/achievements/stats.py` 按成交的 `minute_of_day` 统计。`afternoon_open` 只是 `session` 文案，没有对应成就。
- `core/config.py` 有 `TICKS_PER_TRADING_DAY = 20` 设置，但没有任何代码读取它。
- 测试：`test_clock.py`（v1 跳过表、时段）、`test_market.py::test_day_rollover_appends_closed_candle`（25 tick 换日）、`test_saves.py::test_clock_pause_resume_and_skip`（`skipped_ticks == 119`）、`test_saves.py:42`（开局在 570–690）、`test_market_list_intraday.py`、`test_equity.py`、`test_concurrent_rollover.py`（每日 20 tick）都依赖 v1 节奏。
- 前端：网页版 `features/settings/prefs.js` 的刷新选项是 1000/3000/5000；手机端 `me.js` 同样是 1s/3s/5s，`store.real.js` 用 `clock.trading` 与本地 `sessionLabel` 推导状态。

## 3. 规则版本

### 3.1 字段与迁移
- `models/save.py`：`clock_rules: Mapped[int] = mapped_column(Integer, default=CLOCK_RULES_V2, server_default="1")`，`__table_args__` 加 `CheckConstraint("clock_rules IN (1, 2)", name="clock_rules_valid")`。ORM 默认值设为 2，这样新代码忘记传值时得到新规则；server_default 设为 1，这样迁移时已有的行全部是 v1。
- `models/account.py`（users）：`clock_speed: Mapped[str] = mapped_column(String(8), default="normal", server_default="normal")`，加 `CheckConstraint("clock_speed IN ('fast','normal','slow')", name="clock_speed_valid")`。
- 迁移：`cd backend && uv run alembic revision --autogenerate -m "clock rules v2"`，检查生成的 batch 模式与 server_default；`down_revision` 接在当时的 head 后面（现在是 `f1c260b097ed`，与 A5 的先后见 §10.2）。
- 同步 `models/CLAUDE.md` 的 saves、users 两行。

### 3.2 与 01 的 `events_ruleset` 是否合并 —— 结论：不合并
1. **正交**：事件可以开也可以关，时钟可以是 v1 也可以是 v2。合并成一个版本号就得编码成组合值，而 `events_ruleset = 0` 已经被 01 用来表示“关闭”。
2. **依赖方向是单向的**：时钟规则决定时间基（N = 20 或 242），事件算法从时间基派生以 tick 计的常量；反过来，事件对引擎没有影响（`drift=None` 时逐位一致）。
3. **规则集身份**：一个存档的未来走势由 `(market_seed, clock_rules, events_ruleset)` 唯一确定。01 §6.6 的“发布后改动必须升版本”同样适用于这个二元组：发布后改 v2 的波动常量，就要新增 `clock_rules = 3`，不能改 2。01 的缓存键要带上 `clock_rules`（§8 第 01 条）。
4. 生产环境里能出现的组合：(v1, 事件关)——老存档；(v2, 事件开/关)——新存档。(v1, 事件开) 只会出现在测试里（API 不能建 v1 存档），允许存在，但不作为发布支持的组合。

### 3.4 v1 零改动的保证
- **domain**：`advance(..., rules: int = CLOCK_RULES_V1)`。v1 分支就是现在的函数体原样（可以抽成 `_advance_v1`，但不改任何语句）；v2 分支是新函数 `_advance_v2`。`test_market_engine_golden.py` 一字不改，另加一条断言：显式传 `rules=1` 的结果也等于金值。
- **其它 domain 函数**用默认参数保持原行为：`is_order_time(m, rules=1) == is_trading_time(m)`；`session_label` 不变（v2 用新函数 `session_label_v2`）；`compute_stats(..., clock_rules=1)`；`TradeSettings.clock_rules = 1`。
- **services**：v1 存档的 `_advance_to_now_once` 保留现有分支原样；`_run_ticks` / `decode_state` / `intraday` 把 20 换成 `timebase(save.clock_rules).ticks_per_day`。唯一的结构改动是“非交易分钟不调用 `advance`”（§5.2，03 也提出了同样的改动）；`advance` 在非交易分钟只返回副本，所以结果相同，并用集成测试守护：v1 存档推进 3000 tick 的 payload 与逐分钟调用 `advance` 的纯 domain 重放相同。
- **API**：只加字段，不改已有字段的语义（WS `trading` 对 v1 仍是 `is_trading_time`）。
- **测试**：现有集成测试模块一律加 `pytestmark = pytest.mark.usefixtures("clock_v1")`，原断言不动，证明 v1 行为未变；v2 另写新测试（§9）。

## 4. v2 引擎

### 4.1 交易分钟、交易日边界与对齐不变量
- 价格 tick 仍是 `is_trading_time` 的 242 个分钟（含 11:30 与 15:00 两个收盘 tick）。v2 的时间基是 `TimeBase(242)`，引擎结构与 v1 相同：`rolls = tt % 242 == 0`，`trading_day = tt // 242`。
- **开局固定在 570（9:30）、tt = 0**，这时开盘价等于昨收。第 0 日的 tick 是 571..690（120 个）加 780..900（121 个），共 241 个，tt 1..241，正好对应 v1 第 0 日只有 19 个 tick 的情况。次日 9:30 那一分钟 tt = 242，先换日再走价。之后每日 9:30..15:00 共 242 个 tick，tt 从 242d 到 242d+241。
- **一天一根日 K**：换日发生在**次日 9:30**，而不是 15:00。所以 15:00 收盘后到次日开盘前，状态里还是当日的开高低收和昨收，行情列表显示的是当日涨跌，收盘小结可以直接读状态。已收盘的日 K 和权益快照在换日 tick 写入 `candles` / `equity_snapshots`，逻辑与 v1 相同。
- **对齐不变量**：对 v2 存档始终有 `tt % 242 == f(clock_minute)`，其中 `f(m) = m−570（570≤m≤690）| 120（690<m<780）| m−659（780≤m≤900）| 241（其它）`，实现为 `clock.v2_expected_offset(m)`。会改变分钟又不推进 tick 的操作只有 `debug/time`、`debug/reset-market` 和直接写库（03 的镜像同步写的是 master 自洽的值）。v2 把前两者改成“只能向前推进 / 重置到 570”（§6.6），所以不变量只可能被手工改库破坏。`market._run_ticks` 在 v2 存档上检查它，不成立时记 warning（不抛错）；`intraday` 照旧做终点校验，校验失败就退化为 `exact=false`。

### 4.2 撮合时间窗
- `domain/clock.py::is_order_time(minute, rules=1)`：v1 等同 `is_trading_time`；v2 为 `570 ≤ m < 690 or 780 ≤ m < 900`（240 个可下单分钟）。
- 理由：v2 会在 11:30 与 15:00 停留几秒到十几秒展示午休/收盘小结。如果停留期间还能成交，“已收盘却能下单”会让人困惑，状态栏也说不清。11:30 与 15:00 两个 tick 照常走价，产生半日和全日的收盘价，但不接单（真实市场 15:00 后同样不接受连续竞价单）。
- 落点：`TradeSettings` 新增 `clock_rules: int = 1`（`domain/types.py`），`matching.execute_order` 第 108 行改为 `is_order_time(minute_of_day, settings.clock_rules)`；`auto_trade/executor.py:98` 同理；`services/trading.py:188` 构造时传 `clock_rules=save.clock_rules`；`services/auto_trade.py:393` 改为 `is_order_time(save.clock_minute, save.clock_rules)`。错误码仍是 `MARKET_CLOSED {minute_of_day}`。

### 4.3 波动标定

**目标与依据**（A 股主板个股的常见量级；没有事件的 v2 存档要“平静但不死”）：

| 指标 | 目标区间 | 依据 |
| --- | --- | --- |
| 个股日收益标准差（全部“股票·交易日”） | 1.9%–2.7% | A 股个股日波动常见 2%–3%；v1 实际约 5.2%，过大 |
| 非趋势日标准差 | 1.4%–2.1% | 平常日子应该平静，异动来自少数股票 |
| 等权指数日收益标准差 | 0.5%–1.1% | 沪深 300 约 1%；没有共同因子时只有 0.12%，大盘是一条直线 |
| 日内振幅 (high−low)/昨收 中位数 | 1.8%–3.5% | 分时图要有起伏 |
| 触及涨跌停（high ≥ 涨停价或 low ≤ 跌停价）占比 | 0.4%–1.3% | 385 只每天约 2–5 只。常态市场里约 1%–2% 的个股涨停；这里不想完全没有，否则 `fomo`/`panic` 成就几乎不可达 |
| 收盘封板占比 | 0.15%–0.7% | 约为触板的一半 |
| 单 tick 最大 \|move\| | < 1% | 远低于熔断阈值 5%，没有事件时熔断永不触发（与现状相同） |
| 平均日收益 | ±0.05% 以内；触涨停/触跌停次数比在 0.7–1.4 | 无系统性趋势 |
| bull_bias（影视飓风）收涨日占比 | ≥ 80% | 彩蛋保留“偏多头”，但不再天天涨停（v1 每 tick 期望 +0.85%，每天都封涨停） |

**模型**（全部整数 ppm；股票 i、全局 tick t、交易日 d）：
```
vol_i,d   = 波动档位（每个“股票×交易日”抽一次）: 35% 750_000 | 45% 1_000_000 | 15% 1_500_000 | 5% 2_500_000
trend_i,d = 4% 的概率为 ±U[200, 450] ppm/tick（趋势日，整日约 ±4.8%–10.9%），否则为 0
idio      = rand_below(seed, t, i, 0, 3_200) − 1_600                 # 特质噪声，σ ≈ 924 ppm
mkt_t     = rand_below(seed, t, 400, 0, 1_680) − 840                 # 全市场共同因子，σ ≈ 485 ppm，所有股票共用
move      = round_half_up_div(idio × vol_i,d, 1e6) + mkt_t + trend_i,d + (bull ? V2_BULL_DRIFT_PPM : 0) + drift(事件)
attempted = max(1, scale_ppm(pre, 1e6 + move))；熔断判断与涨跌停钳制同 v1
```
- 方差拆分：普通档特质噪声的日 σ ≈ 924×√242 ≈ 1.44%，共同因子的日 σ ≈ 0.75%。档位混合（E[vol²] ≈ 1.30）让日收益呈尖峰厚尾；趋势日贡献大部分涨跌停。
- 不用“纯 iid 均匀噪声”的原因：日 σ 为 2% 的高斯游走触及 ±10% 的概率约为 6e-7，没有事件的存档将永远看不到涨跌停。
- 不复制 v1 的单 tick ±2%：242 个 tick 下日 σ 会达到 18%，几乎天天触板。
- **价格离散化**：5 元股票的 1 分 = 2000 ppm，大于单 tick 噪声的半宽，四舍五入后很多 tick 是 0，少数是 ±1 分。这样会抬高低价股的方差，但不引入偏差（`round_half_up_div` 只在恰好 .5 时偏上，ppm 粒度下概率可忽略）。仿真脚本按价位分桶报告，要求低价股 σ / 整体 σ ≤ 1.3。
- **bull_bias**：v2 不再使用 k=1 的 70/30 分支，改为在普通噪声上加 `V2_BULL_DRIFT_PPM = 120`（日均约 +2.9%，收涨日约 95%）。k=1 保留，不使用。

**常量**（`domain/market_engine.py`，前缀 `V2_`）：`V2_IDIO_SPAN_PPM=3_200`、`V2_IDIO_OFFSET_PPM=1_600`、`V2_MKT_SPAN_PPM=1_680`、`V2_MKT_OFFSET_PPM=840`、`V2_VOL_TABLE=((35,750_000),(45,1_000_000),(15,1_500_000),(5,2_500_000))`、`V2_TREND_PCT=4`、`V2_TREND_PPM=(200,450)`、`V2_BULL_DRIFT_PPM=120`、`V2_MARKET_FACTOR_IDX=400`、`V2_REGIME_TICK_BASE=-(1<<33)`、成交量相关常量见 §4.5。

**预估**（本计划撰写时用 Python `random` 代替 splitmix 做的粗仿真，200 只 × 100 个交易日，含 5–100 元的整数分价格离散化）：日 σ 2.30%；非趋势日 σ 1.78%；等权指数 σ 0.64%；振幅中位数 2.39%；触板 0.77%；封板 0.38%；单 tick 最大 0.51%；峰度 7.7。去掉趋势日后触板只有 0.08%，这就是保留趋势日的原因。**正式数值以 C4 的仿真脚本（真实 RNG + 全量股票池）为准**，不达标时只改上面这些 `V2_*` 常量。

**仿真验证脚本** `scripts/clock_v2_sim_report.py`（纯标准库，`sys.path` 指向 `backend/src`，只 import `stocksim.domain`，自己读 `data/*.json`）：
- 用法：`python3 scripts/clock_v2_sim_report.py --seeds 3 --days 60 [--check]`。全量 385 只，从 570 开局按分钟逐 tick 调用 `advance(..., rules=2)`，跳过非交易分钟时用跳转。
- 输出：上表全部指标，外加低价股（<10 元）σ 比、每日成交量漂移（第 60 日 / 首日的中位数，要求在 0.5–2）、`daily_volume` 日内单调比例（要求 100%）、熔断触发次数（要求 0）、单 tick `advance` 的 p95 耗时（385 只，要求 < 8 ms）。
- `--check`：任一指标越界就以非零码退出。CI 跑 `--seeds 2 --days 40`。

### 4.4 RNG 布局（v2 新增；写进 `domain/rng.py` 文档字符串与 `domain/CLAUDE.md`）
| 命名空间 | tick 参数 | stock_idx | k | 用途 |
| --- | --- | --- | --- | --- |
| v1/v2 交易 tick（不变） | 全局 tick ≥ 1 | 0..384 | v1：0 涨跌、1 彩蛋幅度、2 成交量、100–119 五档；v2：0 特质噪声、1 **保留不用**、2 成交量扰动、100–119 五档 | |
| **v2 共同因子** | 全局 tick ≥ 1 | **400** | 0 | 每个交易 tick 一个，所有股票共用 |
| **v2 日档位** | `V2_REGIME_TICK_BASE − d`，即 `−2^33 − d` | 0..384 | 0 波动档位，1 是否趋势日，2 趋势幅度，3 趋势方向 | 每个“股票×交易日”抽一次 |
| init / 开局分钟（不变） | −1 / −2 | | | v2 不再使用 −2（开局固定） |
| 01 事件（不变） | `−2^32 − d`、`−2^32 + 4096` | | | 与 v2 日档位相距 2^32 个 tick |

**不换 tick 编号的结论**：v2 继续用“全局 tick = 游戏分钟计数（含非交易分钟）”作为 RNG 的 tick 维度。理由：
1. 跳过 / 快进与逐分钟推进逐位等价，依赖的就是每分钟 tick 加 1；
2. 01–04 都用 trading_tick 定位，全局 tick 只用于展示和五档；
3. 两个存档几乎不可能共用 seed，即使共用，也是两局互不相干的游戏。

“版本混淆”靠 `saves.clock_rules` 列和 v2 payload 的 `_meta.rules = 2` 自描述来避免，不靠换编号。

无碰撞论证（写成测试 `test_clock_v2_rng_layout.py`，暴力枚举）：同一个 tick 内，idx 400 与 0..384 的 Δidx ≥ 16，`|Δidx·7919| ≥ 126 704`，远大于 k 的跨度（≤ 119）。跨 tick 时，|Δidx| ≤ 400 下最接近 `Δtick·1 000 003` 的是 Δtick=3、Δidx=−379，差 1292，仍大于 119。日档位命名空间与交易/init/事件的 tick 差 ≥ 2^32，线性索引 L 的差约 4e15，远小于 2^64，不会回绕相等。测试枚举的范围：交易 tick [−2, 5000] × idx {0..384, 400} × k {0,1,2,100..119}、日档位 d ∈ [0, 400] × idx [0,384] × k [0,3]、init、事件两段（复用 01 的枚举器）。

档位抽取是 `(seed, d, idx)` 的纯函数。为了避免每 tick 多做 4×385 次 RNG，`_advance_v2` 在状态里缓存当日档位：`state["regime"] = {"day": d, "vol": {idx: ppm}, "trend": {idx: ppm}}`，day 变化时重算。这个键**不写入 payload**，`decode_state` 后为空，首个 tick 时重建。缓存只对 state 中出现的 idx 计算，所以单股分时 sim 只算 1 只。

### 4.5 成交量（v2 改成当日累计）
- v2 每个交易 tick：`inc = max(1, prev_daily_volume × (1e6 + 3/2·clamp(daily_change, ±20%)) × r // (1e12 × 242))`，其中 `r = 700_000 + rand_below(seed, t, i, 2, 600_000)`；然后 `daily_volume += inc`，`volume = daily_volume`，当日 K 的 `volume = daily_volume`。
- 结果：`daily_volume` 在日内单调递增，收盘时就是全日成交量；日 K 的成交量与 v1 同一量级（期望约等于前一日）。换日沿用 `_rollover`（`prev_daily_volume ← daily_volume`，`daily_volume ← 0`，均量取近 5 根 K）。
- 对外：v2 的 `IntradayPointOut.volume` 单调不减，相邻点之差就是分钟成交量；`QuoteOut.volume` 是当日累计。在 CONTRACT 写明两版口径的区别。

### 4.6 涨跌停与熔断
- 涨跌停 ±10%（相对昨收）不变；“昨收”在 v2 是真实的上一个交易日收盘价，语义终于和 A 股一致。
- 熔断规则不变（单 tick ≥5% 触发，冷却 3 tick）。v2 噪声的单 tick 最大约 0.5%，01 的事件漂移另有单 tick 上限（见 §8 第 01 条），因此不会触发熔断，与现状一致。不引入“日内累计熔断”。

### 4.7 状态、payload 与 candles
- state 结构同 v1（`trading_tick, trading_day, breaker, stocks`），另有不持久化的 `regime`。
- `market_states.payload`：股票部分仍是 9 项数组。`_meta` 在 v2 为 `{"trading_tick", "as_of", "rules": 2}`；v1 保持 `{trading_tick, as_of}`，不新增键。`decode_state(payload, prior, rules)` 校验 `_meta.get("rules", 1) == save.clock_rules`，不一致抛 `RuntimeError`（数据损坏）。WS / 快照遍历本来就跳过非 list 值，不受影响。
- `candles`：每个交易日一行，`trading_day` 是 v2 日序号，`date = as_of + trading_day`（现有 `_day_iso`）。开局写入的 59 根历史 K 与 v1 完全相同（`init_market` 不分版本），所以在 tick 0 把 `clock_rules` 从 2 改成 1 等价于新建 v1 存档，测试可以借此建 v1 存档。

### 4.8 分时重放（intraday）仍为 exact
- `services/market.py::intraday`：`N = timebase(save.clock_rules).ticks_per_day`；`processed = tt − N·day + (1 if day≥1)`；`sim.trading_tick = N·day − (1 if day≥1)`；`advance(sim, seed, tick, minute, drift=…, rules=save.clock_rules)`。v2 的共同因子和日档位都是 `(seed, t | d, idx)` 的纯函数，与其它股票无关，所以单股重放与全市场推进逐 tick 一致。
- `_day_ticks` 仍按 `is_trading_time`（价格 tick）倒推。v2 在盘后或盘前最多倒推约 1440 个分钟，开销可以忽略。
- 终点校验不变；v2 多比较一项：sim 的累计 `daily_volume` 等于 payload 的 `daily`。

## 5. 节奏与自动快进

### 5.1 每分钟时长与三档；是否复用 `refresh_rate_ms`
| 档 | `ms_per_minute` | 交易时段 242 分钟 | 加两段停留（5 s + 15 s） |
| --- | --- | --- | --- |
| fast | 2500 | 10 分 5 秒 | ≈ 10.4 分钟 / 交易日 |
| **normal（默认）** | 5000 | 20 分 10 秒 | ≈ 20.5 分钟 / 交易日 |
| slow | 7500 | 30 分 15 秒 | ≈ 30.6 分钟 / 交易日 |

**结论：新增 `users.clock_speed`，不复用 `refresh_rate_ms`。** 理由：
1. 复用会同时改变 v1 存档的节奏。v1 每 `refresh_rate_ms` 推进 1 分钟（含非交易分钟），老存档应保持原样；
2. 现有取值不合适：默认 3000 在 v2 只有 12 分钟一天，达不到 20 分钟的目标；两端前端提供的 1 s 档在 v2 只有 4 分钟一天；
3. `refresh_rate_ms` 还决定 WS 的推送间隔，在 v2 里这两件事要解耦（§5.5）。

v2 存档完全忽略 `refresh_rate_ms`（WS 断线后的轮询间隔仍由前端自行决定）。只做三档枚举，不提供连续值，便于前端做分段控件，也便于 03/04 推导时长。

### 5.2 墙钟到游戏分钟的调度（纯函数）
`domain/clock.py`（全部以整数毫秒表示时间，不读系统时钟）：
```python
V2_LUNCH_DWELL_MS = 5_000      # 默认值；服务层从 Settings.CLOCK_LUNCH_DWELL_MS 读取后传入
V2_CLOSE_DWELL_MS = 15_000     # 默认值；Settings.CLOCK_CLOSE_DWELL_MS
@dataclass(frozen=True)
class Step: kind: Literal["tick", "jump"]; due_ms: int; minutes: int
def next_step_v2(minute, anchor_ms, *, ms_per_minute, lunch_dwell_ms, close_dwell_ms) -> Step
@dataclass(frozen=True)
class CatchupPlan: minutes: int; trading_ticks: int; anchor_ms: int; truncated: bool
def plan_catchup_v2(minute, anchor_ms, now_ms, *, ms_per_minute, lunch_dwell_ms,
                    close_dwell_ms, max_trading_ticks) -> CatchupPlan
```
`next_step_v2` 的状态表（`anchor` = 时钟到达当前分钟的墙钟时刻，持久化为 `saves.last_tick_at`）：

| 当前分钟 m | 动作 | 到期时间 | 推进分钟数 |
| --- | --- | --- | --- |
| 569..689、779..899（下一分钟是交易分钟） | tick | anchor + ms_per_minute | 1 |
| 690（11:30，上午收盘） | jump → 779（12:59） | anchor + lunch_dwell | 89 |
| 900（15:00，收盘） | jump → 次日 569（9:29） | anchor + close_dwell | 1109 |
| 其它非交易分钟（只可能来自 debug/time 推到盘后，或手工改库） | jump → 下一个 569 或 779 | anchor（立即） | 按 `skip_target_v2` |

`plan_catchup_v2` 从 (m, anchor) 出发反复取 `next_step_v2`，直到 `due_ms > now_ms`。每执行一步，`anchor = due_ms`。tick 步计入 `trading_ticks`，达到 `max_trading_ticks` 时 `truncated=True`、`anchor_ms = now_ms`（丢弃剩余墙钟时间，与 v1 超过上限时的处理相同）。jump 步不计入上限。一个交易日只有 2 次 jump，上限 300 时循环不超过约 306 次。

### 5.3 实现位置：服务端 `advance_to_now`（不让前端调 skip）
| 方案 | 多标签页 | 离线回来 | 暂停 | 确定性 |
| --- | --- | --- | --- | --- |
| 前端到点调 `/clock/skip` | 每个标签都会调；靠“skip 在非交易时段幂等”勉强成立，但如果某标签的时钟偏快，会提前跳 | 没有客户端在线就永远停在 15:00 | 前端要自己判断 | 依赖客户端时钟 |
| **服务端在 `advance_to_now` 中按锚点计算（采用）** | 所有请求得到同一个计划，靠乐观锁去重 | 补推时自然经过停留与跳转 | `paused` 直接返回 0 | 只依赖服务端时间与存档字段 |

`services/market.py::_advance_to_now_once` 改为：
```
now = utcnow()
if save.paused: return 0
if save.last_tick_at is None: save.last_tick_at = now; commit; return 0
if save.clock_rules == 1: <现有 v1 代码原样>
ctx = clock_ctx(db, save)               # ms_per_minute（users.clock_speed）+ 两个停留时长（Settings）
plan = plan_catchup_v2(save.clock_minute, ms(save.last_tick_at), ms(now), ...,
                       max_trading_ticks=Settings.TICK_CATCHUP_MAX)
if plan.minutes == 0: return 0
done = _run_ticks(db, save, plan.minutes)   # 返回实际推进数（与 01 §6.4 一致）
save.last_tick_at = dt(plan.anchor_ms) if done == plan.minutes else now   # 被预测卡钩子截停时丢弃剩余时间
commit; return done
```
- **跳转复用“跳过”路径**：jump 就是 `_run_ticks(n)`，与 `advance_ticks` / `skip_clock` 同一条代码。每分钟 tick 加 1，非交易分钟不走价，所以“自动快进”“手动跳过”“逐分钟推进”三者的 payload 逐位相同（写测试）。
- **非交易分钟不调 `advance`**：`_run_ticks` 循环里 `if not is_trading_time(minute): continue`（只加 tick 和分钟）。否则一次隔夜跳转要做 1109 次 385 只股票的整状态复制。v1 结果不变（§3.4）。03 §2 也提出了同样的改动，谁先合入谁做，另一方删掉自己的那一条。
- **多标签页 / 多实例**：两个请求同时补推时，后提交者 `StaleDataError`（若跨换日还会撞 candles 唯一约束而 `IntegrityError`），由 `_retrying` 回滚、刷新存档后重算，那时锚点已推进，结果是 n=0。与现状相同。
- **离线补推**：上限 `TICK_CATCHUP_MAX`（默认 300）在 v2 里**按交易 tick 计**，约 1.24 个交易日；超出后丢弃剩余墙钟时间并把锚点置为 now。如果截断时恰好停在 15:00，收盘小结会重新给满 15 秒。是否改成“离线不推进”见 Q6。
- **暂停**：暂停时不推进、不跳转。停在 15:00 时按暂停就能一直看收盘小结；`resume_clock` 把锚点置为 now，停留窗口重新计时。
- **预测卡（02）截停**：钩子只在交易 tick 上触发。`done < plan.minutes` 时锚点置为 now，已经暂停，与 01 §6.4 的处理相同。
- **模式分发顺序**：`_advance_to_now_once` 开头先做 03（挑战）、05（复盘）的 `save.mode` 分发，再按 `clock_rules` 分支。挑战与复盘都不走 v2 调度器。

### 5.4 收盘小结的展示窗口
- 15:00 那个 tick 一到，`phase` 变为 `closed`，`fast_forward_at = 到达 15:00 的时刻 + 15 s`。前端收到 WS `phase` 消息后调用 `/day-summary` 展示小结。到 `fast_forward_at` 后服务端跳到 9:29，再过 `ms_per_minute` 到 9:30 换日开盘。
- 11:30 停留 5 秒，只用于显示“午间休市”，不调用小结接口。
- 停留时长是 `Settings.CLOCK_LUNCH_DWELL_MS` / `CLOCK_CLOSE_DWELL_MS`（`ge=0, le=600_000`），e2e 可以设为 0 加快测试。它们只影响节奏，不影响行情。

### 5.5 WS 推送节奏（v2）
- 每轮 `tick_once` 结束后计算 `due = min(next_tick_at, fast_forward_at)`（都为 null 时视为暂停）。下一轮延迟 `delay = clamp(due − now + 50 ms, MIN_REFRESH_MS, ms_per_minute)`；暂停时取 `V2_WS_PAUSED_POLL_MS = 2000`。这样每个游戏分钟只醒一次，并且在快进时刻准点醒来。
- 其它标签页的跳过、暂停最多延迟一个 `ms_per_minute` 才反映到本连接；本标签的 REST 操作返回 `ClockOut`，前端直接应用即可。
- `tick_once` 改为返回 `(messages, next_delay_ms)`；`stream_save` 用它代替固定的 `interval`。v1 连接仍固定为 `refresh_ms`。

### 5.6 一个交易日的时间线（normal）
| 墙钟 | 游戏时钟 | phase | 事件 |
| --- | --- | --- | --- |
| 0:00 | 9:30 | morning | 换日 tick（第 1 日起），开盘 |
| 9:55 | 11:29 | morning | 上午最后一个可下单分钟 |
| 10:00 | 11:30 | lunch | 上午收盘 tick；`fast_forward_at` = 10:05 |
| 10:05 | 12:59 | lunch | 快进 89 分钟（无行情变化） |
| 10:10 | 13:00 | afternoon | 下午开盘 |
| 20:05 | 14:59 | afternoon | 最后一个可下单分钟 |
| 20:10 | 15:00 | closed | 收盘 tick；WS 推 `phase`；收盘小结；`fast_forward_at` = 20:25 |
| 20:25 | 次日 9:29 | pre_open | 快进 1109 分钟 |

## 6. 受影响功能逐项处理

### 6.1 自动交易
- 接单判断改用 `is_order_time(m, rules)`（§4.2），停留窗口与盘后不触发。
- 冷却以 tick 计（默认 2，time 类 10）。v2 中 1 tick = 1 游戏分钟，所以 time 条件的语义变成“每 10 个游戏分钟”，normal 档约 50 秒（legacy 是 30 秒）。常量不改，只更新 `domain/auto_trade/CLAUDE.md` 的单位说明。
- 跳转一次加 89 或 1109 个 tick，跳转后冷却自然已过，不需要特殊处理。自动交易仍是每个 WS 轮次在 `advance_to_now` 之后运行一次（不是逐 tick），v2 每轮最多推进 1 个交易 tick，评估粒度反而比 v1 更细。

### 6.2 时段成就与 `session` 文案
| 项 | v1（不变） | v2 |
| --- | --- | --- |
| `early_bird` 窗口 | 570–575 | 570–575（可下单） |
| `night_owl` 窗口 | 695–700（午休，不可达） | **895–899**，即收盘前 5 分钟，与 legacy 文案“在收盘前5分钟完成交易”一致 |
| `session` 取值 | `session_label` 原样 | `session_label_v2`：570–575 `early_bird`，780–785 `afternoon_open`，895–899 `night_owl`，其余可下单分钟 `trading`，其它 `closed` |

落点：`clock.is_night_owl_window(m, rules=1)`、`is_early_bird_window(m, rules=1)`；`compute_stats(..., clock_rules=1)` 透传；`services/achievements.py::record_unlocks` 传 `save.clock_rules`。一个存档内所有成交的规则相同，统计口径一致。v1 夜猫不可达这个 legacy 缺陷是否顺手修复，见 Q4（修复不影响行情）。

### 6.3 T+1
代码不变，仍按 `trading_day` 判断。v2 的语义变成真实的“次日 9:30 后可卖”，normal 档下约 20 分钟后。前端提示文案要同步（§7.3）。

### 6.4 权益快照与资产曲线
代码不变。v2 每个交易日（≈20 分钟）写一行，`7d/30d` 区间就是真实的 7/30 个交易日。`equity_snapshots.tick` 记的是换日 tick（次日 9:30 的全局 tick）。

### 6.5 跳过按钮（`POST /api/v1/saves/{id}/clock/skip`）
v2 用 `clock.skip_target_v2(m)`，每次至少推进 1 分钟，“跳到下一个关键时点”：

| 当前 m | 目标 | 说明 |
| --- | --- | --- |
| 570..688 | 689（11:29） | 与 legacy 相同：留最后 1 分钟可下单 |
| 689 | 690（11:30） | 上午收盘，进入午休停留 |
| 690..778 | 779（12:59） | 跳过午休停留 |
| 779 | 780 | 开盘 |
| 780..898 | 899（14:59） | |
| 899 | 900（15:00） | 收盘，进入小结停留 |
| ≥ 900 或 < 569 | 569（下一个 9:29） | 跳过收盘停留 |
| 569 | 570 | 开盘（第 1 日起为换日 tick） |

v2 删除夜猫停顿点（11:34 / 11:39）。跳过仍不看暂停（现状），推进后锚点置为 now。从开盘起连按 8 次正好走完一个交易日（570→689→690→779→780→899→900→569→570），e2e 用这个序列。预测卡截停照常（`skipped_ticks` 为实际推进数）。是否另加 `{"to":"next_open"}` 之类的参数见 Q11。

### 6.6 调试 API（仅 `ENABLE_DEBUG_API=true`）
- `POST /saves/{id}/debug/time {minute_of_day}`：v1 仍直接改分钟。v2 改为**只向前推进**：`n = (target − cur) mod 1440`，`n > 0` 时调用 `market.advance_ticks(db, save, n)`，`changed = n`（可能被钩子截停）。这样对齐不变量保持成立，分时仍然 exact。如果目标落在非交易、非停留分钟，下一次 `advance_to_now` 会立即跳到下一个 9:29 / 12:59，见 §5.2 表最后一行。
- `POST /saves/{id}/debug/reset-market`：v2 额外设置 `clock_minute = 570`、`last_tick_at = now`。01 的 reset 钩子照常运行。
- 其余调试接口不变。

### 6.7 导出与旧版导入
- `saves.export_save` 的 save 节新增 `"clock_rules": "v1"|"v2"`。这是新增字段，不单独升 `EXPORT_FORMAT_VERSION`；如果 A2 已经升到 2，就和它一起写进 v2 格式说明。
- 旧版导入：见 §3.3，新存档为 v2，开局 570。旧成交仍是 `trading_day = −1`、`tick = 0`，不受影响。

### 6.8 开局时间
v2 固定 570，不调用 `random_start_minute`（该函数和 rng 的 tick=−2 保留给 v1）。`test_saves.py:42` 的“开局在 570–690”对 v2 改为 `== 570`。

### 6.9 其它
- 当日盈亏（`portfolio`）的口径不变，v2 的“当日”是真实的一天。
- 五档 `order_book(price, seed, save.tick, idx)` 不变。停留期间 `tick` 不变，五档也不变。
- 03 / 05 的守卫（`CHALLENGE_UNSUPPORTED`、`REPLAY_UNSUPPORTED`）位于 v2 调度之前，不受影响。
- 预测卡（02）与自动快进：卡片只会在交易 tick 上弹出，弹出时存档被置为暂停，暂停期间不会快进，所以**不需要额外的“有 open 卡就阻止快进”规则**（回答 06 §5 关于 02 的第 4 条）。玩家不答题直接 resume 后，快进照常进行。

## 11. 风险

1. **两套规则并存**：引擎、调度、撮合窗、成就、测试都要按版本分支，测试矩阵翻倍。缓解：分支点集中在 `clock.py` 的少数函数和 `TradeSettings.clock_rules`；v1 分支逐字保留，由金值测试与 `clock_v1` 回归守护。
2. **低价股离散化**：5 元股的单 tick 噪声小于 1 分，价格会“粘住”，方差偏大约 5%–30%（按价位不同）。仿真脚本按价位分桶把关；如果体感不好，可以在 v3 引入亚分精度的隐藏价格（payload 格式要变，代价大，首版不做）。
3. **事件分册需要重新调参**：v2 噪声是 v1 的约 0.45 倍，01 的信噪比表、情报卡价值梯度、02/04 的分档都要在 v2 下重跑仿真。01 若在 v2 前定稿，会返工。
4. **性能**：01 的日计划长度 ×12；分时重放最长 242 tick；隔夜跳转 1109 个分钟（跳过非交易分钟后只是整数自增）。最坏的请求是补推 300 个交易 tick（与 v1 相同）加上冷缓存的 1–2 个日计划。
5. **离线体验**：v2 离线补推最多约 1.2 天，然后丢弃剩余时间，玩家可能困惑“为什么只过了一天”。见 Q6。
6. **网页版不改界面**：网页版新建的存档也是 v2，但看不到收盘小结，刷新档位不起作用，跳过语义变了。可以接受，在网页版改版前用文案提示（需要改网页版 i18n，超出“暂不改”的范围），见 Q8。
7. **对齐不变量依赖“无人手改分钟”**：今后任何直接写 `clock_minute` 的代码（03 的镜像除外）都会破坏它。缓解：`_run_ticks` 检查并告警；分时自动退化为 `exact=false`；在 `services/CLAUDE.md` 写明禁止直接写分钟。
8. **成交量语义变化**：v2 的 `volume` 是当日累计，v1 是快照，前端图表若按 v1 理解会画错。在 CONTRACT 写明，并在手机端同步。
9. **v2 金值的冻结时点**：发布前可以继续调 `V2_*`，发布后只能新增 `clock_rules = 3`。要在发布检查单里写明。
10. **停留窗口内的时钟偏差**：多实例部署时，各实例的 `now` 不同会让快进时刻相差几百毫秒。由于以锚点计算且有乐观锁，结果仍然确定，只是早晚略有差异。

## 12. 开放问题

- **Q1 三档速度**：2500 / 5000 / 7500 ms（约 10 / 20 / 30 分钟一天），默认 5000，可以吗？slow 是否要更慢（10000，约 40 分钟）？
- **Q2 停留时长**：午休 5 s、收盘小结 15 s。午休是否干脆不停？收盘小结是否需要“我看完了再跳”的显式按钮（可以复用 skip）？
- **Q3 撮合窗**：v2 在 11:30 和 15:00 不接单（半开区间），接受吗？
- **Q4 夜猫成就**：v2 把窗口改为 14:55–14:59。v1 的窗口在午休里、永远不可达，要不要顺手把 v1 也改成 14:55–15:00？这会改变 v1 的成就行为，但不影响行情逐位一致。
- **Q5 波动模型**：接受“档位 + 4% 趋势日 + 共同因子”的厚尾模型和 §4.3 的目标吗？如果只要纯 iid 噪声（实现更简单），没有事件的存档几乎看不到涨跌停，`fomo`/`panic` 成就基本不可达。另外，开启事件的存档是否关闭趋势日（避免与事件的“异动”混淆）？本计划建议保留，作为“无消息异动”的噪声。
- **Q6 离线补推**：v2 沿用“上限 300 个交易 tick（≈1.2 天）后丢弃”，还是改成“没有客户端连接就不推进”（类似暂停，更接近单机游戏）？
- **Q7 是否允许玩家新建 v1 存档**（作为“经典快节奏”选项）？本计划不开放，只在测试中可用。
- **Q8 网页版新建的存档**是否也用 v2？本计划为是（服务端无法区分客户端）。
- **Q9 bull_bias 彩蛋**：v2 每日约 +2.9%，收涨约 95%，很少涨停。是否要保留 v1 那种“天天封板”的夸张效果（例如把漂移调到约 +400 ppm）？
- **Q10 前端 typedef**：根 `CLAUDE.md` 要求改 API 时同步 `frontend/src/api`，本计划只同步 JSDoc 与一个新导出函数。如果“暂不改前端”指一行都不改，C10 的这部分推迟到网页版改版。
- **Q11 跳过的粒度**：是否要给 `/clock/skip` 加可选参数 `{"to":"next_stop"|"close"|"next_open"}`，提供“一键到收盘 / 到明天”？本计划不加。
- **Q12 `/day-summary` 的历史范围**：30 个交易日够吗？是否需要“周小结”？
- **Q13 清理配置**：删除没有被读取的 `Settings.TICKS_PER_TRADING_DAY`（如果有部署的 `.env` 设置了它，`extra="ignore"` 会静默忽略），可以吗？
