## 0. 摘要

- **时间模型：回合制全服时间线**（§3）。每天一个挑战，全服共用一个 master 行情（同 seed、同时钟，时钟规则 v2）。剧本按 4 个**回合事件**（从重大事件中按规则挑出，§4.2）切成 4 个回合：每回合先按固定节奏“快放”行情（0.75 s/交易 tick，一个交易日约 3 分钟，单段 ≤ 3 个交易日、≤ 9.1 分钟），停在回合事件首条快讯处，**全服一起停住**几个小时供作答和交易，到下一个时段再继续。v2 每个交易日都有 1–2 条重大事件，回合以外的重大事件只作为快讯出现（不出题、不开市、不停顿）。任何人任何时候进来看到的都是同一个“现在”：没人能先探路看到未来，D 也有了共同价格（即 04 Q1 说的“直播”形态）。
- **不给每人一份行情**：master 是无主存档（`saves.mode='challenge_market'`，`user_id=NULL`），持有 `market_states` 与 `candles`；玩家挑战存档（`mode='challenge'`）只持有资金、持仓、成交，行情经新列 `saves.market_source_id` 读 master。1000 人参加也只有一份 K 线。
- **题目复用 B**：每个回合 = B 的一张预测卡（同一事件的 dir/rank/rumor 题，`build_questions` 生成，所有人逐字节相同），但卡和答案存在 C 自己的表里（B 的卡绑定单存档暂停，不适合全服时间线）。计分用 B 的 `rps_score/ndcg_at_k_score/peer_scores/baseline_score`；参与 < 5 人退化为基线分。交易收益按同伴差值折算、封顶后计入综合分。
- **seed**：`HMAC-SHA256(挑战密钥, 日期|尝试序号)` 派生并按剧本质量筛选；开局前公布 `sha256(承诺原文)`，结算后公布 seed 与盐，前端本地校验。泄露面逐项封堵（§5）。
- **触发**：懒触发（挑战相关请求）+ 推荐开启的 compose `challenge-runner` 循环；多实例幂等靠唯一约束、乐观锁、条件更新，不引入应用内调度器。奖励一次性经 B 账本 `points.credit(reason="challenge")` 发放。

## 1. 对外契约（B/D 引用这里）

### 1.1 挑战实体与生命周期
- 主键 `challenges.id`（uuid）；人类可读唯一键 `challenge_date`（UTC+8 日历日 `YYYY-MM-DD`），一天至多一个挑战。
- 持久化 `status`：

| status | 进入条件 | 含义 |
| --- | --- | --- |
| `scheduled` | 生成完成 | 承诺已公布；不能报名，行情未开始 |
| `running` | `now ≥ starts_at`（条件更新，懒迁移） | 时间线推进中；`now < entry_closes_at` 时可报名 |
| `settled` | master 到达 `end_tt`、全部题目已判定、`now ≥ ends_at` 后结算事务提交 | 成绩、排名、奖励已写；**seed 公开** |
| `void` | 生成失败或 CLI 作废 | 不计分不发奖；已有承诺的照样公开 seed |

- 派生 `phase`（时间线纯函数按 `now` 算，不落库）：`before` → `burst`（第 k 回合快放）→ `hold`（停在第 k 个事件，作答窗口）→ … → `final`（最后一段快放，跑到最后一题判定点）→ `ended`。
- 回合 `round.state`：`pending`（未到）→ `burst` → `open`（停顿中、可作答）→ `closed`（已过截止）→ `resolved`（本回合全部题已判定）。

### 1.2 公共时间线（真实时间 ↔ 交易 tick）
记 N=`CHALLENGE_ROUNDS`=4；第 k 回合停顿 tick 为 `hold_k`（`hold_0=0`）；`end_tt` 为最后一题判定 tick；每交易 tick 真实时长 `tick_ms`；恢复时刻 `resume_1..resume_{N+1}`（`resume_1 = starts_at`）。

| 真实时间区间 | 公共交易 tick `tt(now)` |
| --- | --- |
| `now < resume_1` | 0 |
| 第 k 回合快放 `[resume_k, hold_at_k)`，`hold_at_k = resume_k + (hold_k − hold_{k−1})·tick_ms` | `hold_{k−1} + ⌊(now − resume_k)/tick_ms⌋` |
| 第 k 回合停顿 `[hold_at_k, resume_{k+1})` | `hold_k` |
| 最终段 `[resume_{N+1}, ends_at)`，`ends_at = resume_{N+1} + (end_tt − hold_N)·tick_ms` | `hold_N + ⌊(now − resume_{N+1})/tick_ms⌋` |
| `now ≥ ends_at` | `end_tt` |

- 单调不减；交易 tick 0 以外的每个值恰好对应一个真实时刻区间。
- **作答窗口**：第 k 回合 `[hold_at_k, closes_at_k)`，`closes_at_k = resume_{k+1} − CHALLENGE_CLOSE_LEAD_MS`（5 s，抵消多实例时钟偏差）。D 的合约按自己的 tick 规则开收（04 §3.3），只需用本节映射。
- 交易 tick → 全局 tick/游戏分钟：master 是 v2 存档（`clock_rules=2`），开局 `clock_minute=570`（9:30）、`tick=0`、`trading_tick=0`，满足 07 §4.1 的对齐不变量（tt = 0 时必须在 9:30）；第 0 日 241 个交易 tick，之后每日 242 个（下文记每日 tick 数为 `N_TPD`，以免与回合数 N 混淆），换日在次日 9:30。推进按纯函数 `minutes_to_tt` 逐分钟走，午休与隔夜**瞬间跨过**（不经过 07 的停留与自动快进）。由于对齐不变量，`tt` 与全局 tick、分钟一一对应（07 §1.6 的 `v2_tick_of`、`v2_minute_of_offset`）。同一 `tt` 对所有人是同一全局 tick，A 的 RNG 与漂移逐位一致。
- 默认 `tick_ms = CHALLENGE_TICK_MS = 750`：一个交易日 242 tick 约 3 分钟。快放段 11:30 与 15:00 这两个 tick 照常出价但不接单（07 §4.2），快放中在这两个分钟下单得到 `MARKET_CLOSED`。
- **玩家存档永远不会领先公共时间线**：玩家没有自己的时钟，只镜像 master（§7.3）。

### 1.3 回合事件的枚举与钩子
- 只有**回合事件**可被出题、被 D 开市、让时间线停顿。v2 每个交易日都有 1–2 条重大事件，`[1, end_tt]` 内必然有回合以外的重大事件（一场约 7 个交易日，约 10 条重大事件，只有 4 条是回合事件）：它们照常发布快讯、照常影响行情，但**不出题、不开市、不停顿**，B 的钩子在挑战存档上本来就不出卡（§1.6 的 `CardPolicy`）。所以 D 必须**只对回合事件开市**，用 §1.7 的 `round_event_ids` 判断，不能再用“全部 `major`”（原 v1 设计里的“恰好 N 条”保证已取消）。
- 键 `(challenge_id, event_id)` 唯一；`event_id` 即 A §1.2 的 ID。完整 `GameEvent` 只在服务端经 `challenge_events(...)`（§1.7）取得。
- 可见性：`event_id/hold_tt/hold_at/resolve_tt`、题目在 `now < hold_at` 前保密；`resume_at`、`closes_at` 公开。
- 钩子 `services/challenges/hooks.py`（在 `main.create_app` 注册；与 A §1.5 同规则：运行在调用方事务内、**不得 commit**、必须幂等）：

### 1.4 seed 派生、承诺与公开（D 复用）
- 派生（纯函数 `domain/challenge/commit.py`）：`derive_seed(key: bytes, date_iso: str, attempt: int) -> int = int.from_bytes(HMAC_SHA256(key, f"stocksim-challenge-seed|v1|{date_iso}|{attempt}")[:8], "big") >> 1`，取值 `[0, 2^63)`。`key` = 配置 `CHALLENGE_SEED_KEY`（UTF-8）；未配置时 `HMAC_SHA256(SECRET_KEY, "stocksim/challenge-seed-key/v1")`。HMAC 单向：公开一天的 seed 不泄露密钥与其它天。
- 承诺：`commitment_input = f"stocksim-challenge|v1|{date_iso}|ruleset={events_ruleset}|clock={clock_rules}|seed={seed}|salt={salt_hex}"`（`clock` 是时钟 v2 增补的字段；格式尚未发布，所以不升 `v1` 前缀），`seed_commitment = sha256(commitment_input)` 的小写 hex；`salt_hex = secrets.token_hex(16)`（服务层生成后传入纯函数）。函数：`commitment_input(...) -> str`、`make_commitment(...) -> str`、`verify_commitment(input, digest) -> bool`。
- 公开时机：`seed_commitment` 自 `scheduled` 起公开；`market_seed`、`seed_salt`、`commitment_input` 只在 `status ∈ {settled, void}` 时由 `GET /challenges/{id}/reveal` 输出。**JSON 里 seed 一律十进制字符串**（> 2^53，JS 数字会丢精度）。
- D 不读 seed（04 §1.2 第 2 条）；D 若要承诺自己的量，复用 `make_commitment` 的格式，前缀换成 `stocksim-<模块>`。

## 2. 现状要点（实施前已核对代码）

- `domain/market_engine.py::advance(state, seed, tick, minute)`：RNG 维度是**全局 tick**；非交易分钟直接返回副本。`clock.random_start_minute(seed)` 用 seed 决定开局分钟（泄露约 7 bit），挑战不用它。时钟 v2（07）合入后 `advance` 多一个 `rules` 参数，v2 新存档一律从 570 开局，这个泄露面对 v2 已不存在；挑战固定 570。
- 07 的 v2 调度（`plan_catchup_v2`、停留、自动快进）只用于普通存档；`_advance_to_now_once` 开头先按 `save.mode` 分发（挑战、复盘），再按 `clock_rules` 分支（07 §5.3），所以挑战存档不经过 07 的调度器。
- `services/market.py`：`_market_row` 按 `save.id` 取 `MarketState`；`stock_market` 按 `Candle.save_id == save.id` 取 K 线；`_run_ticks` 每个 tick 都调 `advance`（含非交易分钟），跨日时写 candles 与 `record_close_snapshot`；`_advance_to_now_once` 按 `users.refresh_rate_ms` 补推、上限 `TICK_CATCHUP_MAX=300`；`advance_ticks` 无视暂停。`intraday` 用 `save.tick/clock_minute/market_seed` 重放。`order_book(price, seed, save.tick, idx)` 只用当前 tick。

## 3. 时间模型（核心难点）

### 3.1 方案比较
| 维度 | ① 各人独立时钟（同 seed，可暂停/跳过） | ② 固定窗口统一实时推进（不可停） | **③ 回合制全服时间线（采用）** |
| --- | --- | --- | --- |
| 异步参加 | 好 | 差：错过就错过 | 好：每个停顿窗口数小时 |
| 同一剧本 | 是 | 是 | 是 |
| 多账号探路 | **防不住**：小号先跳过看结果，大号再答（04 风险 1） | 不可能 | 不可能：没人比全服更早看到未来 |
| D 共同价格 | 不成立，需“超前锁定”且挡不住小号 | 成立 | 成立 |
| 决策 6（预测时暂停） | 每人暂停 | 违背 | 全服在重大事件处停顿，语义一致 |
| 存储 | 每人一份 K 线（2.3 万+行/人/天） | 一份 | 一份 |
| 临场感 | 强 | 强 | 快放段可围观，停顿段静止 |

**结论：③。** ①的探路无法靠规则堵住（Pastcasting 接受了这一点，但它没有排行奖励和预测市场），D 又需要同一时间线；②对异步不友好。③的代价是停顿段行情静止——这正是决策 6 的“预测时暂停”，只是全服一起暂停。

### 3.2 规则
- 示意（默认时段，北京时间）：
```
07:00 快放(0→h1) ┤停顿① 作答R1 … 11:59:55截止 │12:00 快放(h1→h2) ┤停顿② … │17:00 快放 ┤停顿③ … │20:30 快放 ┤停顿④ … │23:00 最终段(h4→end_tt) ┤结算
```
- 默认 `CHALLENGE_SLOTS="07:00,12:00,17:00,20:30,23:00"`（N+1 个）。每段快放 ≤ `CHALLENGE_MAX_BURST_TT = 3·N_TPD = 726` 交易 tick × `CHALLENGE_TICK_MS = 750` ≈ 9.1 分钟，每个作答窗口 ≥ 2 小时 20 分；最终段同样 ≤ 726 tick（方向/排序题在触发后第 3 个交易日收盘判定、传闻揭晓 ≤ 726 tick，§4.2），约 23:10 前可结算。一场挑战的 `end_tt` 中位数约 1700 tick（约 7 个交易日），上限 `8·N_TPD = 1936`。
- **时间预算的推导**（v2，每日 tick 数 `N_TPD = 242`）：方向题窗口 3 个交易日（02 §4.1，两版相同），所以最终段 = `242·(d0+3) − hold_N ≤ 726`，单段快放上限必须 ≥ `3·N_TPD`；再要求单段 ≤ 10 分钟，得 `tick_ms ≤ 600_000 / 726 ≈ 826`，取 750（一个交易日约 3 分钟，比普通存档 normal 档快约 6.7 倍）。
- **玩家时钟**：玩家存档没有自己的时钟。每次 `open_save`/WS 轮询先把 master 推到 `tt(now)`，再把 master 的 `tick/clock_minute/trading_day` 镜像到玩家存档（有变化才写），`paused = phase ∉ {burst, final}`。
- **ClockOut（07 §1.2）对挑战存档**：在 `sync_entry_save` 镜像之后由 07 的 `clock_fields` 统一按存档字段计算：`clock_rules = "v2"`；`phase / trading` 按 v2 定义由 `clock_minute` 推出；`ms_per_minute` 在快放段（burst/final）为 `tick_ms`、停顿段与赛前赛后为 null；`next_tick_at` 在快放段为 `real_time_of(tt+1)`，其余为 null；`fast_forward_at` 恒为 null；`next_event.at` 用本分册时间线（`real_time_of` 映射到下一个时段变化的 tt，停顿段为 null）。实现方式：本分册在 07 的 `clock_ctx` 里为 `mode ∈ CHALLENGE_MODES` 注册覆盖函数。`/day-summary`（07 §1.4）对挑战存档可用，读 `candles` / `market_states` 一律经 `market_key(save)`。
- **暂停/继续/跳过/调试时间**：409 `CHALLENGE_UNSUPPORTED {feature:"clock"|"debug"}`。
- **补推**：master 不受 `TICK_CATCHUP_MAX` 限制，一次推到 `tt(now)`（目标由时间唯一确定，丢 tick 会让实例间不一致）。
- **检查点**：推进时在每个 `hold_k` 与每个题目的 `resolve_tt` 处**精确停下**（同一事务），依次处理回合打开、题目判定，再推到目标。懒推进一次跨多个检查点，与实时推进结果相同。
- **与 B 的暂停兼容**：C 注册的 `CardPolicy(enabled=False)` 让 B 的 publish 钩子在 master 上不出卡、不截停；挑战的“暂停”由时间线承担。小快讯不停顿。
- **迟到者**：`entry_closes_at = closes_at_N` 前任何时候可报名，初始资金相同，从当时行情开始；已截止回合计 0 分（不扣分）。错过的快放用分时、K 线、快讯列表回看。
- **作答修改**：窗口内可改，最多 `CHALLENGE_MAX_REVISIONS=20` 次，以最后一次为准。
- **交易**：快放与停顿都可下单。停顿点必是 v2 的可下单分钟（§4.2 规则 1 排除了 11:30、15:00 这两个只出价不接单的 tick），所以整个作答窗口都能交易；快放段经过 11:30 / 15:00 时那一个 tick 不接单。`phase=ended` 或已结算 → `CHALLENGE_ENDED`；自动交易禁用。

### 4.2 纯函数
```python
@dataclass(frozen=True)
class MajorRef:          # 由 A 的 GameEvent + B 的题目派生
    event_id: str; kind: str; trigger_tt: int; resolve_tt: int   # resolve_tt = 该事件全部题目判定 tick 的最大值
@dataclass(frozen=True)
class RoundPlan:
    event_ids: tuple[str, ...]; hold_tts: tuple[int, ...]; resolve_tts: tuple[int, ...]; end_tt: int
def plan_rounds(majors: Sequence[MajorRef], *, rounds, warmup, min_gap, max_burst, max_tt,
                holdable: Callable[[int], bool]) -> RoundPlan | None
def holdable_v2(tt: int) -> bool     # is_order_time(v2_minute_of_offset(timebase(2).offset_of(tt)), 2)：偏移不是 120（11:30）或 241（15:00）
```
v1 设计（“取前 N 个重大事件、`[1, end_tt]` 内不许有别的重大事件”）在 v2 下不可行：v2 每个交易日都有 1–2 条重大事件，回合间隔又要 ≥ 半天，中间必然夹着别的重大事件，64 次筛选几乎全部失败。v2 改为**从重大事件里贪心挑回合**，其余重大事件保留为普通快讯：

1. **候选**：按 `(trigger_tt, event_id)` 升序的重大事件中，满足 `holdable(trigger_tt)`、`trigger_tt ≥ warmup`、且该 tick 上没有**另一条**重大事件的首条快讯（避免停顿时两条“重大”并列、玩家分不清哪条是回合）。precursor 可能落在 11:30/15:00，这类事件不当回合（01 §4.2 只约束正式发布偏移）。
2. **贪心**：第一个候选为回合 1；之后依次取第一个满足 `trigger_tt − hold_{k−1} ≥ min_gap` 的候选，直到凑满 `rounds` 个；凑不满则失败。
3. 每段快放 `hold_k − hold_{k−1} ≤ max_burst`（`hold_0 = 0`）；
4. `resolve_tt_k > hold_k`；`end_tt = max(resolve_tts)`，`end_tt − hold_N ≤ max_burst`，`end_tt ≤ max_tt`；
5. 每个回合事件 B 至少出 1 题（`build_questions` 非空，dir 题总会出）。
6. 非回合重大事件**允许**存在，不出题、不开市、不停顿（§1.3）；D 只对回合事件开市（04 §3.1）。

可行性（本计划撰写时的蒙特卡洛，按 01 §4.2/§4.3 的 v2 分布：每日 1 条 60% / 2 条 40%，偏移在合法集均匀，传闻 15%、揭晓 [242,726]，priced_in 约 10%、提前 [242,484]；20 000 次）：单次尝试接受率约 98%（`max_tt = 8·N_TPD`；不限 `max_tt` 时 99.8%），`end_tt` 中位数约 1694、p95 约 1936。64 次尝试全部失败的概率可以忽略。若 `max_burst` 取 `2·N_TPD`（07 的初始建议），最终段放不下 3 日窗口，接受率为 0，所以取 `3·N_TPD`。正式结论以 C1 的 `test_challenge_screening.py`（真实 A、B 代码）为准。

`domain/challenge/timeline.py`：`build_timeline(*, hold_tts, end_tt, resume_ms, tick_ms, close_lead_ms, min_window_ms) -> Timeline`（校验时段递增、快放结束早于截止且窗口 ≥ `min_window_ms`）；`target_tt(tl, now_ms)`；`reached_ms(tl, tt)`；`phase_at(tl, now_ms) -> PhaseInfo(phase, round_index, next_change_ms)`；`minutes_to_tt(cur_minute, cur_tt, target_tt) -> int`（逐分钟模拟到交易 tick 恰好等于目标，返回要推进的全局 tick 数；交易分钟沿用 `is_trading_time`，即 v2 的价格 tick；在 v2 对齐不变量下也可以用 07 §1.6 的 `v2_tick_of` 闭式求差，两者必须相等，写成测试）。时间一律 epoch 毫秒整数。

### 4.3 生成流程 `generate.ensure_challenge(db, date, *, now) -> Challenge`
1. 已存在则返回。
2. `key = seed_key(settings)`；`for attempt in range(64)`：`seed = derive_seed(key, date_iso, attempt)`；`ruleset = events.ruleset(EVENT_RULESET_VERSION, clock_rules=CHALLENGE_CLOCK_RULES)`、`params = save_params(seed, ruleset)`；对 `d ∈ [0, ⌈MAX_TT/N_TPD⌉ + LOOKAHEAD_DAYS]`（v2 为 `[0, 10]`）调 `generate_day` 收集 `major`；对每个调 `build_questions`（`QuestionContext(clock_rules=2)`，structure 取 `predictions.structure_for(ruleset 版本)`，与 B 同缓存）得 `MajorRef`；`plan_rounds(..., holdable=holdable_v2)` 非 None 即接受。64 次都失败 → 建 `status='void'` 的挑战并 `logger.error`（只记日期和次数）。
3. 时段：`daily` 模式 `resume_k = date + slots[k−1]`（UTC+8 → UTC）；`compact` 模式（开发/e2e，§11）`resume_k = ceil_5s(now) + 5s + (k−1)·CHALLENGE_COMPACT_SLOT_SECONDS`。`build_timeline` 校验（daily `min_window` 30 分钟，compact 5 秒）。
4. 单事务：master Save（§6.1）+ `init_market_for_save(db, master, as_of=date)` + `challenges` 行 + N 行 `challenge_rounds` + `hooks.run_created`。`challenge_date` 唯一键冲突 → 回滚重读返回。
5. 日志只记 `challenge_date`、`seed_attempt`、`seed_commitment`。

### 7.3 推进与镜像（`sync.py`）
```python
def advance_master(db, ch, now) -> int:
    master = market_save_for(db, ch); tl = timeline_of(ch)
    target = target_tt(tl, to_ms(now)); cur = payload_meta_tt(master)
    if target <= cur: return 0
    cps = sorted({r.hold_tt for r in rounds} | {tt for r in rounds for tt in r.resolve_tts.values()} | {target})
    done = 0
    for cp in (c for c in cps if cur < c <= target):
        done += market._run_ticks(db, master, minutes_to_tt(master.clock_minute, cur, cp)); cur = cp
        for r in rounds if r.hold_tt == cp and r.opened_at is None:   rounds.materialize_round(...); hooks.run_round_open(...)
        for (r, qid) with r.resolve_tts[qid] == cp and qid not in r.outcomes: rounds.resolve_question(...); hooks.run_question_resolved(...)
    db.commit(); return done
```
- 整体包在 `market._retrying`：`StaleDataError`（另一实例已推进）/ `IntegrityError` → 回滚重读，通常发现已到目标返回 0。
- `sync_entry_save(db, save, now)`：由 `save.market_source_id` 找挑战；`maybe_run_due`（节流，失败只记日志）；`advance_master`；若 `tick/clock_minute/trading_day/paused` 与 master 不同则赋值并 commit（`_retrying`）；返回 master 本次推进数（WS `advanced` 字段）。
- 性能：非交易分钟跳过 `advance` 后，一天约 1200 个非交易分钟只是整数自增；一段快放 ≤ 726 交易 tick（v2 约 3 个交易日）。实时推进时每次请求只推 1–2 个 tick；最坏的懒推进（无 runner、整段无人访问）约为 726 × 单 tick `advance`（07 要求 p95 < 8 ms）+ 1–3 个冷缓存的 v2 日计划（01 §5.6，每个约 0.3–0.4 s），合计数秒，见 R6。
- 负载：每个 WS 玩家在快放段每 0.75 s、停顿段每 5 s 读一次 master 行，偶尔写一次镜像（几个整数），比普通存档每 tick 写整个 payload 的现状轻。

### 7.4 报名（`entries.join`）
- 条件：`status=='running'` 且 `now < entry_closes_at`，否则 `CHALLENGE_NOT_STARTED`/`CHALLENGE_ENTRY_CLOSED`。
- 单事务：建玩家 Save + SaveStats + `challenge_entries(eligible = user.created_at ≤ starts_at − CHALLENGE_MIN_ACCOUNT_AGE_HOURS, joined_tt = 当前 master tt)`；唯一键冲突 → 回滚返回已有报名（`created=False`，HTTP 200）。
- **不计入 `MAX_SAVES_PER_USER`**；每人每挑战一份。

### 7.5 回合与题目（`rounds.py`）
- `materialize_round`：`build_questions(ev, QuestionContext(seed=master.market_seed, trigger_trading_tick=hold_tt, structure=…))`，写 `round.questions = [q.to_public()…]`、`opened_at`。题目是 seed 的确定函数，重放幂等。
- `answer_round(db, ch, entry, round_index, answers_in, now)`：无报名 → `CHALLENGE_NOT_ENTERED`；回合不可见 → `CHALLENGE_ROUND_NOT_FOUND`；`now ≥ closes_at` → `CHALLENGE_ROUND_CLOSED`；`revision ≥ 20` → `CHALLENGE_ANSWER_LIMIT`；调用 B 的 `validate_answers(round.questions, answers)`（02 §1.3；每题必答、dir 5 项/rumor 2 项合计 100、rank 3 项互异且在候选内）→ 422 `VALIDATION_ERROR {field:"answers.<qid>…", reason}`；upsert `challenge_answers`（`submitted_tt` = master tt，必须等于 `hold_tt`，否则按截止处理）；首次作答 `entry.answered_rounds += 1`、`round.answer_count += 1`。时间判定用请求开始时的 `now()`。
- `resolve_question(db, ch, round, qid, master)`：按 §1.6 表算真值写 `round.outcomes[qid]`；对该回合全部答案按 §8.1 算分写 `results[qid]`，重算 `round_score`；全部 qid 齐了写 `round.resolved_at`。dir 真值为 None 时该题作废（`outcome = {"void": true}`，不计分）。

### 7.6 结算（`settle.settle_if_due`）
前置：`status=='running'`、master tt == `end_tt`、全部回合 `resolved_at` 非空、`now ≥ ends_at`。用 `tx.run_in_transaction` 包一个事务：
1. 读 `challenges` 行（version 乐观锁）；`status` 已非 running → 退出。
2. 最终价格取 master payload；每个报名 `final_equity = cash + Σ qty×price`，`return_bp = round_half_up_div((equity − initial)·10_000, initial)`，`trade_count` 为成交数。
3. §8.2 交易分；`forecast_score = Σ round_score`；`total_score = forecast + trade`。
4. 合格者竞赛排名写 `rank`，`eligible_count`。
5. §8.4 发奖：每个合格报名一次 `points.credit(db, user_id=…, delta=…, reason="challenge", ref=f"challenge:{challenge_date}", idempotency_key=f"challenge:{challenge_id}:{user_id}", meta={"rank", "total_score"})`，`points_awarded` 记金额（0 也记一条留痕）。
6. `hooks.run_settled`；`status='settled'`、`settled_at=revealed_at=now`；提交。
- 冲突整体回滚重做，账本幂等键兜底；参加人数上千时第 5 步可按 200 人一批拆事务（status 最后一批才改）。

## 8. 计分与排行

### 8.1 每题
- B 的原始分：dir/rumor `S = rps_score(probs, outcome)`、`U = uniform_rps_score(k, outcome)`；rank `S = ndcg_at_k_score(order, relevance)`、`U = expected_random_ndcg_score(8, relevance)`。
- 参考集 = 该题**合格**作答者，`n = |参考集|`。`n ≥ CHALLENGE_PEER_MIN(5)`：合格者 `peer = peer_scores([S…])[i]`（02 §5.5 分数差版本，对有序 5 档题优于对数版本），`used="peer"`；同伴分对参考集合计约为 0，多账号乱填无法抬高总和。
- `n < 5`：所有作答者用 `baseline_score(S, U)`（−100..100），`used="baseline"`。
- 不合格者：一律基线分，不进参考集、不上榜、不领奖。未作答 0 分。`S/U/baseline` 一并存，用于复盘展示。

### 8.2 交易
- 参考集 = 全部合格报名（含没交易的，收益 0）。`n ≥ 5`：`diff = return_bp − round_half_up_div(Σ − own, n − 1)`，`trade_score = clamp(round_half_up_div(diff·TRADE_POINTS_PER_100BP, 100), ±TRADE_SCORE_CAP)`；`n < 5`：用 `return_bp` 代替 `diff`。
- 初始资金、费率、交易单位统一，`return_bp` 直接可比；迟到者只是持仓时间短，不另折算。
- 封顶理由：不封顶时“全仓赌一把”会压过预测分。v2 单股日 σ ≈ 2.3%，一场挑战约 7 个交易日，全仓单股的收益离散约 ±6%，即交易分大多落在 ±60 以内，封顶只在极端时生效（v1 时单日 σ≈5%、一场跨数十个交易日，几乎必然封顶）。是否调整 `TRADE_POINTS_PER_100BP` 见 Q2。

### 8.3 排行
- **日榜** `GET /challenges/{id}/leaderboard?board=total|forecast|trade`：只在 `settled` 后可看，只含合格报名；按对应分数降序，**标准竞赛排名**（1,2,2,4）；同分显示顺序按 `username` 升序（只为分页稳定）；游标 base64url JSON `[score, username]`。
- **周榜** `GET /challenge-leaderboard?scope=week&week=YYYY-Www`：ISO 周（按 UTC+8 日期），该周已结算挑战的合格报名 `total_score` 求和，缺席计 0，附 `days_played`。
- **总榜** `scope=all`：累计求和 + `days_played`；`sort=avg` 时按平均分，只含 `days_played ≥ 5`。
- SQL `GROUP BY user_id` 聚合，名次在服务层算；`me` 返回当前用户所在行（不在页内也给）。不用 `points.totals_by_user`：它按积分流水排，与分数排行口径不同。

### 8.4 积分奖励（经 B 账本，reason=`challenge`，已在 02 `REASONS` 登记）
| 条件（仅合格，且答过至少 1 个回合或有成交） | 积分 |
| --- | --- |
| 参与 | 10 |
| 名次 ≤ ⌈eligible_count × 10%⌉（`eligible_count ≥ 10` 时） | +30 |
| 第 1 / 2 / 3 名（`eligible_count ≥ 5` 时；并列同奖） | +100 / +60 / +40 |
挑战内 B 的单题积分**不发**（`CardPolicy.points_reason=None`），不受 B 的日上限影响。数额见 Q4。

### 8.5 纯函数（`domain/challenge/scoring.py`、`ranking.py`）
`question_results(S_list, U_list, eligible, *, peer_min) -> list[QuestionResult]`、`trade_scores(returns_bp, eligible, *, peer_min) -> list[int]`、`competition_ranks(scores) -> list[int]`、`reward_points(rank, eligible_count) -> int`、`iso_week_key(date) -> str`。内部调用 `domain.scoring`（B）。

## 9. 防作弊

| 攻击 | 防护 |
| --- | --- |
| 多账号先探路再作答/下注 | 时间模型杜绝：所有账号看到的“现在”相同（§3.1） |
| 多账号对冲（各押一边赌一个进前列） | 账号年龄门槛（创建早于开局 72 h 才合格）；不合格者不进参考集、不上榜、不领奖；奖励额度小；离线“镜像答案”检测见 Q6 |
| 多账号乱填抬高他人同伴分 | 同伴分合计为 0；不合格账号不进参考集 |
| 提交后修改 | 截止前可改（≤20 次，以最后一次为准）；截止后服务端按 `closes_at` 拒绝；判定只发生在下一段快放之后，答案已锁定 |
| 时序攻击（卡截止看下一 tick） | 截止比恢复早 5 s；下单前复核 master tick；推进目标只由服务端 `now` 决定 |
| 通过 API 读未来数据 | §5 全表；没有任何接口能把 master 推过 `tt(now)` |
| 重开刷成绩 | 每人每挑战一份报名；挑战存档不可删除、不可重置 |
| 情报卡买优势 | `CardPolicy.intel_allowed=False` |
| 破解 seed | §5 #15；HMAC 派生，破一天不影响其它天 |

### 11.2 触发：懒触发为主，runner 服务为辅
- **`runner.run_due(session_factory, now)`**，每步独立短事务、全部幂等：
  1. `ensure_challenge(今天)`（缺且未过 `entry_closes_at`）；本地时间 ≥ 12:00 时 `ensure_challenge(明天)`（提前公布承诺）。
  2. `scheduled` 且 `now ≥ starts_at` → `running`（条件更新）。
  3. 每个 `running`：`advance_master`。
  4. `closes_at ≤ now` 且 `closed_hooked_at IS NULL` 的回合：条件更新抢占后跑 `RoundClosedHook`。
  5. `settle_if_due`。
  6. 清理（§6.3）。
- **懒触发**：挑战路由与 `sync_entry_save` 调 `maybe_run_due`（进程内 `time.monotonic` 节流 10 s，失败只记日志）。推进本身不依赖节流：玩家请求总会 `advance_master` 到 `tt(now)`。
- **runner（推荐生产开启）**：命令 `stocksim-challenge`（`pyproject.toml` `[project.scripts] stocksim-challenge = "stocksim.cli_challenge:main"`），子命令 `run-due`、`loop --interval 15`、`show --date`（结算前不打印 seed）、`void --date --reason`。compose：
```yaml
  challenge-runner:
    image: stocksim-backend:local
    command: ["stocksim-challenge", "loop", "--interval", "15"]
    environment: { 与 backend 相同的 DATABASE_URL / SECRET_KEY / CHALLENGE_* }
    networks: [default, 1panel-network]
    depends_on: { migrate: { condition: service_completed_successfully } }
    restart: unless-stopped
```
  作用：无人在线时也按时结算、发奖、提前生成明天的承诺。D 的 sweeper（04 §8）在 backend 进程内运行，与 runner 互不依赖。
- **不用应用内调度器**：多 worker/多实例会各跑一份，且干扰测试。
- **多实例幂等**：生成靠 `challenge_date` 唯一键；状态迁移靠条件更新 + `challenges.version`；推进靠 master `saves.version` 与 candles/快照唯一键；回合打开靠 `opened_at IS NULL` 且在推进事务内；关闭钩子靠 `closed_hooked_at` 条件更新；发奖靠 B 账本幂等键；清理是幂等删除。

## 16. 开放问题（需用户拍板）

- **Q1（最重要）时间模型**：采用“回合制全服时间线”（停顿期全服一起暂停，不能各自暂停/跳过），是否接受？默认 4 回合，时段 07:00 / 12:00 / 17:00 / 20:30 / 23:00（北京时间），v2 下约 23:10 前结算。它同时回答了 04 Q1（选“直播”）。
- **Q2 交易计分**：交易收益按同伴差折算计入综合分（100bp = 10 分，封顶 ±100），另有独立预测榜和交易榜。还是综合分只算预测、交易只做独立榜？
- **Q3 防小号门槛**：账号创建满 72 小时才进排行、同伴分参考集和奖励（04 原默认 24 小时，一致性核对后 04 改为读同一配置 `CHALLENGE_MIN_ACCOUNT_AGE_HOURS`，数值待定）。是否还要求“至少有过 1 个普通存档”？
- **Q4 奖励数额**：参与 10、前 10% +30、前三 +100/+60/+40，与 B 的积分经济（预测卡日上限 2000、情报卡 80–200）是否匹配？
- **Q5 排行展示**：直接显示用户名，还是允许匿名/昵称？
- **Q6** 是否需要离线检测“镜像答案”的多账号对冲（只出报告，不自动处罚）？
- **Q7** 是否为挑战引入加密 RNG（如按 tick 用 keyed BLAKE2 生成随机数）作为新规则集版本？代价是挑战与普通存档引擎分叉。
- **Q8** 保留期：玩家挑战存档 14 天、master 30 天（过期后只剩成绩与 seed，K 线复盘不可用）。
- **Q9** 周榜按总和（缺席计 0，鼓励每天来）还是平均？总榜默认总和、可切平均（≥5 天）。
- **Q10** 挑战存档里是否解锁普通成就？本计划不特殊处理（会解锁，随临时存档清理）。
- **Q11（时钟 v2）快放节奏**：`CHALLENGE_TICK_MS = 750`（一个交易日约 3 分钟，单段 ≤ 9.1 分钟）。是否更快（500 ms，一天 2 分钟）以缩短等待，或更慢（826 ms 是 10 分钟上限）以便围观？`MAX_BURST_TT` 取 `3·N_TPD` 是为了放下 3 日的方向题窗口；若 02 Q5 把 v2 窗口缩到 2 日，可同步改为 `2·N_TPD` 并把 tick_ms 放慢到约 1.2 s。
- **Q12（时钟 v2）非回合重大事件**：v2 一场挑战约有 6 条不出题的重大事件，玩家可能困惑“为什么这条大新闻不停”。是否在快讯上标“本场回合 / 非回合”（回合身份在 hold 前保密，只能在到达后标）？或者把非回合重大事件在挑战中降级显示为普通快讯（`major` 字段对挑战存档改写会违反 01 §1.3 的一致性，不建议）？本计划只在回合卡上标注，不改写 `major`。
