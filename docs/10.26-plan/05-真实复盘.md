## 0. 摘要

**一句话**：玩家选一个真实历史关卡（例如“2023-08 印花税减半前一周”），在**看不到未来**的前提下逐阶段推进。玩家能看到当时真实的 A 股日 K、公告、公司动态、新闻联播政策，以及（未来关卡才有的）快讯。玩家可以用模拟资金交易（只在开盘价、收盘价两个撮合点成交），也可以回答预测题拿积分。结束后揭示真实后续走势、事件影响和得分。

**与合成引擎的关系**：不走 `domain/market_engine.py`、`services/market.py::_run_ticks`、`market_states`、`candles`。复盘存档是 `saves.mode='replay'` 的存档，报价来自**关卡包**（离线构建的真实数据），在 `services/market.py::load_market` 处分发。下单仍然只走 `trading.place_order` / `place_order_detailed`，签名不变。

**范围与里程碑**（E 可与 A 并行，只有 E4 依赖 B）：

| 里程碑 | 内容 | 依赖 |
| --- | --- | --- |
| E1 数据 | 抓取 CLI（AKShare，隔离依赖组）、原始数据落盘、关卡构建器、2–3 个精选关卡包 | 无 |
| E2 回合与交易 | 表与迁移、关卡导入、复盘存档、四阶段推进、行情分发、下单复用、资产曲线 | domain 小改（§5.4） |
| E3 快讯与揭示 | 事件流 API、揭示页、前端 web 与手机端页面 | A 的快讯形状（只影响适配层） |
| E4 预测与积分 | 预测题作答、RPS/NDCG 计分、积分入账 | **B 的 `domain/scoring` 与积分账本** |
| E5 定时抓存（可与 E1 同时上线） | `replay-collector` compose 服务，从现在起抓存快讯与个股新闻 | 无 |
| E6 可选 | finbert 情绪标注、自定义关卡（玩家自选日期/个股） | E1–E3 |

**MVP 的边界**：只做精选关卡，由作者写规格，离线构建后随代码入库。暂不做玩家自选日期或个股（放在 E6）。只用日 K，不做分时。不支持自动交易和调试接口。

## 1. 玩家体验

### 1.1 入口与选关

- **入口**：网页版在存档选择界面加“真实复盘”按钮；手机端在“我的”页加入口卡片，并在行情页顶栏放一个小入口。复盘不占普通存档列表（§5.1）。
- **关卡列表** `GET /replay/levels`：卡片展示标题、导语、标签（政策 / 业绩 / 停产 / 行业 / 宏观）、难度 1–3 星、交易日数、股票数，以及“我的最好成绩 / 是否已通关”。
  - 匿名关卡的标题和导语用 `title_masked` / `teaser_masked`，例如“某个周末突发的交易成本政策”，避免标题本身剧透。
  - 筛选参数：`tag`、`difficulty`；排序：精选在前，然后按难度。
- **关卡来源**：
  1. **经典事件（精选，MVP）**：作者写规格（§3.1）、构建、人工校对。候选示例如下，具体日期和事实由关卡作者对照公告核实后再用：
     - 2023-08-27（周日）晚，财政部、税务总局宣布证券交易印花税自 8-28 起减半 → 券商、整体市场。
     - 2024-09-24 国新办发布会公布降准降息与新货币工具，随后政治局会议 → 全市场、券商、地产。
     - 2020-02-03 春节假期延长后的首个交易日 → 医药、消费、全市场。
     - 某公司公告主要产线停产或检修（作者从 `日常经营` / `风险提示` 类公告中挑选），再用 01a 产业链草稿挑上下游同行。
  2. **按主题生成（E6）**：给出主题（概念板块或 01a 的行业链）和日期，由离线批处理生成关卡（`kind='generated'`），人工抽检后发布。
  3. **玩家自选日期/个股（E6，`kind='custom'`）**：玩家选日期和 ≤5 只股票，服务端从原始数据缓存即时构建。自选就意味着玩家知道日期，所以只能实名，不进排行（§1.7）。

### 1.2 开局

`POST /replay/sessions {level_slug, masked}` 创建复盘存档：

- 资金默认 100 万元（`initial_fund_cents=100_000_000`），交易单位 100 股，T+1，费率用默认值（不模拟历史印花税变化，见 §10）。
- **开局可见**：
  - 回看期 K 线：开局前 `lookback_days`（默认 60）个交易日，对应已有前端开局 60 根的习惯。
  - 关卡里全部股票的当前报价：处在第 0 日盘前，报价 = 前收。
  - 基准指数（如沪深 300）的回看期走势。
  - 回看期最后 10 个交易日的历史资讯，以及作者标为重要的更早事件。
  - 关卡简介和预测题预告（只给题数和时点，不给题面）。
- **时间标签**：实名模式显示真实日期；匿名模式显示 `T-60 … T-1, T+0 …`。接口里的 `date` 字段用**假日历**：从 2001-01-01（周一）起连续排工作日，不保留节假日空档，防止从日期间隔推出时间（§1.7）。

### 1.3 时间怎么推进：按日，每日四个阶段，玩家手动推进

复盘是回合制。行情只在玩家点“下一阶段”时前进，没有墙钟补帧（因此 00 的决策 #6“预测时暂停”在这里天然成立）。

| 阶段 `phase` | 存档 `clock_minute` | 报价 | 能否交易 | 新可见内容 |
| --- | --- | --- | --- | --- |
| `pre_open` 盘前 | 540（09:00） | 现价 = 前收 | 否（`MARKET_CLOSED`） | 前一晚到当日开盘前的公告、事件；本时点开放的预测题 |
| `open` 开盘 | 570（09:30） | 现价 = 当日开盘价；最高 = 最低 = 开盘；量 0 | 是，按开盘价成交 | 开盘价 |
| `close` 收盘 | 900（15:00） | 现价 = 收盘价；最高、最低、量完整 | 是，按收盘价成交 | 盘中（09:30–15:00）发布的快讯和公告 |
| `post_close` 盘后 | 960（16:00） | 同收盘 | 否 | 15:00 以后的公告、新闻联播（19:00） |

- `advance` 支持两种 `to`：`next_phase`（默认）和 `next_day`。`next_day` 一直推到下一个盘前，但遇到“有预测题开放或截止”会提前停，并在响应里给 `stopped_reason`。
- 最后一个交易日的 `post_close` 之后再推进，就进入结算（§1.6）。中途也可以 `finish` 提前结束。
- 推进请求必须带 `expected_tick`（客户端看到的 `save.tick`）。不一致时不推进，直接返回当前状态，防止双击推进两次。

### 1.4 交易规则

- 复用 `trading.place_order`。成交价就是当前阶段的现价（开盘价或收盘价），限价单规则与普通存档一致（买单限价 ≥ 市价则按市价成交，否则 `ORDER_LIMIT_NOT_REACHED`）。
- **T+1**：从 trades 的 `trading_day` 推导，`trading_day` 就是关卡的 `day_idx`。所以开盘买入的股票当天收盘也不能卖（`TRADE_T1_SELL_BLOCKED`）。
- **涨跌停幅度按真实板块**：主板 10%，创业板 2020-08-24 起 20%，科创板 20%，北交所 30%。需要 domain 小改（§5.4）。
- **封板不可成交**：如果当前阶段的价格封在涨停（开盘一字板，或收盘封板），禁止买入；封在跌停则禁止卖出。错误码 `REPLAY_LIMIT_LOCKED`。
- **停牌**：停牌日报价 = 前收，成交量 0，禁止交易，错误码 `REPLAY_STOCK_SUSPENDED`。
- 不支持自动交易、调试接口和墙钟时钟操作，统一返回 `REPLAY_UNSUPPORTED`。

### 1.5 预测题

题目来自关卡包，由作者在规格里定义，答案由构建器从真实数据计算。每关 2–5 题，计分复用 B：

| `kind` | 题面示例 | 作答 | 计分（B 的纯函数） |
| --- | --- | --- | --- |
| `direction_bucket` | “从昨收到 5 个交易日后收盘，X 的涨跌幅落在哪一档？” 5 档，边界由构建器按回看期波动率设置（§3.2） | 每档一个概率，整数百分比且合计 100（02 §1.2）；只选一档等于该档 100% | RPS → `round(100·(1−RPS))` |
| `rank` | “这 5 只股票未来 5 日涨幅前三，按顺序选” | 从候选代码里有序选 3 个 | NDCG@3 |
| `binary`（即 `direction_bucket` 的 2 档特例） | “这条公告后次日相对基准是跑赢还是跑输？” | 两档概率 | RPS（2 档时等于 Brier） |

- **时点**：每题有 `opens_at` 与 `closes_at`，都是 `{day_idx, phase}`，通常同为某日 `pre_open`；还有 `resolves_at`，即第 `opens.day + horizon − 1` 日收盘。
- 截止前可以反复提交，以最后一次为准。推进越过 `closes_at` 时如果还有未答题，返回 `REPLAY_PREDICTION_PENDING`，除非带 `skip_pending=true`（跳过记 0 分）。
- **何时计分**：推进到 `resolves_at` 之后立即计分并入账。如果结算点落在揭示期（玩家看不到的后续日子），就在结算时统一计分。
- **积分**：分数 0–100 直接作为积分入 B 的账本，匿名关卡 ×1.0，实名 ×0.5（建议值，见开放问题 Q1）。**同一用户同一关卡的同一题只入账一次**，用账本幂等键实现（§5.6），重开同一关只能练习，不能刷分。
- 交易盈亏**不发积分**（决策 #2：积分与资金独立），只在揭示页和关卡排行里显示“相对基准的超额收益”。

### 1.6 结算与复盘揭示

结算发生在最后一日盘后之后再推进，或调用 `finish` 时：

1. 持仓按最后可见价格估值，算出 `final_equity_cents`、`return_bp`、`benchmark_return_bp`（同期基准指数）和 `excess_bp`。
2. 对剩余题目计分，并入 B 的账本。
3. 把 `replay_sessions.status` 置为 `settled`；之后下单、推进、作答一律返回 `REPLAY_SESSION_SETTLED`。

揭示页 `GET /replay/sessions/{id}/reveal`（只有结算后能看）展示：

- **真身**：真实代码、名称、真实日期。
- **完整 K 线**：回看期 + 游戏期 + 揭示期（`reveal_days`，默认 10），游戏期加底色，事件标在 K 线上。
- **每条事件的影响**：`ar_1d_bp`、`ar_5d_bp`，即相对基准的超额收益，由构建器预先算好。如果做了情绪标注，再附模型情绪（§4）。
- **每道题**：我的答案、正确档位、真实涨跌幅、得分、积分。
- **交易复盘**：资产曲线（复用 `equity_snapshots`）、成交列表、对比“买入持有关卡全部股票”和“只持有基准”的结果。
- **作者讲解**：规格里的 `commentary`，纯文本。

### 1.7 防剧透

| 泄露途径 | 措施 |
| --- | --- |
| 接口直接给未来 K 线 | 所有视图都经过 domain 纯函数 `visible_bar` / `event_visible` 按 `(day_idx, phase)` 过滤。前端**永远拿不到关卡包**，关卡包只在服务端。集成测试逐阶段断言不出现未来数据（§8）。 |
| 题目答案 | `questions[*].answer` 只在服务端；接口模型 `ReplayQuestionOut` 没有答案字段，只有计分后才出现 `result`。 |
| 股票名凭记忆作答 | **建议默认匿名**：别名如“券商A”，代码用 `990001` 起的别名段；公告标题由构建器做脱敏替换；价格按每只股票固定系数缩放，让第 0 日前收落在 10–50 元；量按反比缩放，成交额不展示；链接置空（巨潮链接含真实代码）；日期改用假日历。实名模式可以切换，但积分减半且不进排行（Q1）。 |
| 新闻联播或政策原文暴露日期 | 匿名模式只保留规格里 `cctv.keywords` 命中的条目，构建器把年份、具体日期替换为“近日”，并在 `redaction_report` 里列出残留数字年份供作者人工确认；作者可以把单条事件标成 `hide_in_masked`。 |
| 重开关卡刷分 | 积分按 `(user, level, question)` 幂等，只算第一次；排行只取每人每关的首个已结算会话。 |
| 导出存档 | `GET /saves/{id}/export` 只含成交与持仓（别名代码），不含关卡包。复盘存档的 `market_seed=0`，没有需要保密的东西。 |

### 2.2 代码放哪、依赖怎么隔离

- **不放 `scripts/`**：`scripts/CLAUDE.md` 要求只用标准库、不含业务逻辑。
- **放在 backend 包内、但运行时不导入**：
  - `backend/src/stocksim/replay_ingest/`：抓取、抓存、原始数据存储、构建器和 CLI。
  - 规则：**只有 `client.py` 在 `AkshareClient.__init__` 里延迟 `import akshare`，只有 `sentiment.py` 延迟 `import transformers`**，其余模块只用标准库。这样即使没装 akshare，`uv run pytest` 也能导入并测试构建器。
- **依赖组**（`backend/pyproject.toml`，用 `uv add --group ingest akshare` 生成）：

  ```toml
  [dependency-groups]
  dev = [...]                         # 不变
  ingest = ["akshare>=1.19,<2"]       # pandas/requests/bs4/lxml/curl_cffi 由其传递
  sentiment = ["transformers>=4.40", "torch>=2.3"]   # E6，可选
  ```

  `uv export --frozen --no-dev` 不包含非默认组，现有 `backend/Dockerfile` 的 runtime 镜像不会带上 akshare。验收命令：`cd backend && uv export --frozen --no-dev --no-emit-project | grep -ci akshare` 输出 0。
- **运行方式**：`cd backend && uv run --group ingest python -m stocksim.replay_ingest <子命令>`。
- **子命令**（`replay_ingest/__main__.py`，用 argparse）：

  | 子命令 | 作用 |
  | --- | --- |
  | `calendar` | 抓交易日历 |
  | `fetch --spec replay/specs/<slug>.json` | 按关卡规格补齐所需的全部原始数据（K 线、指数、公告、公司动态、新闻联播），增量 |
  | `fetch-kline --codes 600030,000776 --start 20230501 --end 20231020` | 单独抓 K 线 |
  | `collect --loop [--interval 120]` / `collect --once` | 定时抓存快讯和个股新闻（§2.5） |
  | `daily` | 每日盘后补抓当天的公司动态、新闻联播和关注池公告 |
  | `build --spec … --out replay/packs/<slug>/v<N>.json` | 构建关卡包，**只用标准库，不联网** |
  | `annotate-sentiment --pack …` | E6，需要 `--group sentiment` |
  | `verify --pack …` | 校验与脱敏报告 |

### 2.3 原始数据落盘（落文件，不落库）

原始数据量大、可以重抓、只给离线构建用，所以落文件，不进业务库。根目录取环境变量 `REPLAY_DATA_DIR`，默认 `backend/.replay-data/`，**加进 `.gitignore` 和 `backend/.dockerignore`**；容器内是卷 `replay-data:/replay`。

```
$REPLAY_DATA_DIR/
  calendar/trade_dates.json               # {"fetched_at","akshare_version","rows":["2023-08-25",...]}
  kline/none/<code>.jsonl                 # 每行 {"d":"2023-08-25","o":..,"h":..,"l":..,"c":..,"v_lot":..,"amt":..}（原值，元为 float 字符串）
  kline/hfq/<code>.jsonl
  index/<symbol>.jsonl
  cninfo/<code>/<yyyy>Q<q>.json           # 整段覆盖写（一次调用一个文件），含请求参数
  gsrl/<yyyy>/<yyyy-mm-dd>.json
  cctv/<yyyy>/<yyyy-mm-dd>.json
  cls/<yyyy-mm>/<yyyy-mm-dd>.jsonl        # 追加写；去重键见 §2.5
  em_news/<code>/<yyyy-mm>.jsonl          # 追加写
  board/<concept|industry>/<snapshot_date>/<name>.json
  _state/fetch_log.jsonl                  # 每次请求：ts_utc, fn, args, ok, rows, ms, error
  _state/collect_cursor.json              # 抓存进度：em_news 轮转位置、cls 最近去重键
```

- 整段文件的格式统一为 `{"fn","args","fetched_at"(UTC ISO),"akshare_version","rows":[...]}`；行用 `df.to_dict("records")`，日期和时间一律转成字符串。
- 写入是原子的：先写 `*.tmp` 再 `os.replace`。JSONL 追加写，每行以 `\n` 结尾，读时跳过坏行。
- 全部时间保留**源时区原文**（上海时间），另加 `ts_utc` 字段。00 要求“时间 UTC”指的是落库和 API，原文保留是为了便于核对。

### 2.4 增量、重试、限速

- **增量**：
  - K 线：读 jsonl 最后一行的日期，从下一天抓到 `end`。后复权历史值不变，所以可以安全追加。
  - 公告：按季度分片，文件存在且季度已结束就跳过；当前季度每次重抓并覆盖。
  - 公司动态和新闻联播：按日，文件存在就跳过，`--force` 强制重抓。
- **限速**（`client.RateLimiter`，令牌桶，按主机分别计）：

  | 主机 | 默认间隔 | 说明 |
  | --- | --- | --- |
  | eastmoney | 1.5s | 日 K、公司动态、个股新闻、板块 |
  | cninfo | 3s/次调用 | 函数内部还会翻页 |
  | cctv | 30s/日期 | 函数内部约 20 次请求 |
  | cls | 抓存间隔本身已足够慢 | |

  全部可用环境变量覆盖：`REPLAY_RATE_<HOST>_MS`。
- **重试**：每次调用最多 3 次，退避 2s/4s/8s 加 0–1s 抖动。可重试的异常包括 `requests` 与 `curl_cffi` 的网络异常、`JSONDecodeError`、`KeyError("result")`。连续 10 次失败就熔断，退出码为 2，并写 `fetch_log`。
- **代理**：`requests` 自动读取 `HTTP(S)_PROXY`；`curl_cffi` 需要显式传 `proxies`（`client.py` 里统一读取环境变量）。
- **可测性**：`client.py` 定义协议 `AkClient`，每个用到的函数对应一个方法，**都返回 `list[dict]`**（在 `AkshareClient` 里立即做 `df.to_dict("records")`）。测试注入 `FakeClient`，从夹具 JSON 读数据（§8），`RateLimiter` 和重试的时钟、`sleep` 也可以注入。

### 2.5 从现在起定时抓存（快讯与个股新闻）

只有最近数据的接口包括 `stock_info_global_cls`（20 条）和 `stock_news_em`（10 条/股），要从今天起持续抓存，供未来的关卡使用：

- **compose 服务**（`docker-compose.yml`，`profiles: ["collector"]`，默认不启动）：

  ```yaml
  replay-collector:
    profiles: ["collector"]
    build:
      context: ./backend
      target: ingest                 # Dockerfile 新增 stage：在 builder 基础上额外 `uv export --group ingest`
      args: { PIP_INDEX_URL: ${PIP_INDEX_URL:-https://pypi.tuna.tsinghua.edu.cn/simple} }
    image: stocksim-ingest:local
    command: ["python", "-m", "stocksim.replay_ingest", "collect", "--loop", "--interval", "120"]
    environment:
      REPLAY_DATA_DIR: /replay
      REPLAY_COLLECT_UNIVERSE: ${REPLAY_COLLECT_UNIVERSE:-pool}   # pool=股票池中的真实 A 股代码
      HTTP_PROXY: ${HTTP_PROXY:-}
      HTTPS_PROXY: ${HTTPS_PROXY:-}
    volumes: [ "replay-data:/replay" ]
    restart: unless-stopped
  # volumes: 增加 replay-data
  ```

  启动：`docker compose --profile collector up -d replay-collector`。不想常驻容器时，也可以在宿主机 crontab 里跑 `docker compose run --rm replay-collector python -m stocksim.replay_ingest collect --once`（每 2 分钟一次）和 `... daily`（每天 20:30）。
- **`collect --loop` 的调度**（单进程，不需要 cron 守护进程）：
  - 每 120s 抓一次 cls：`全部` 和 `重点` 各一次。高峰期 20 条大约覆盖 10–20 分钟，120s 有余量；要是相邻两次没有重叠（新抓的 20 条去重后全是新的），就写 `gap_suspected` 日志。
  - 每 10s 轮转一只股票抓个股新闻，股票池约 384 只真实代码（`999999` 是彩蛋，排除），一轮约 64 分钟。
  - 每天 20:30（上海时间）触发一次 `daily`。
- **去重键**：
  - cls：`sha1(发布日期 + 发布时间 + 标题 + 内容前 50 字)`。
  - em_news：`sha1(新闻链接)`。
  - 进程内保留最近 2000 个键，启动时从当月文件回填。
- **体积估算**：cls 约 1500 条/天 × ~0.5KB ≈ 0.75MB/天；个股新闻约 2MB/天；合计每年不到 1GB，按月 gzip 后约 200MB。`content` 截到 500 字。

### 2.6 历史关卡没有快讯时用什么补，以及事件的时间归属

**来源优先级**（构建器合并后按重要度截断，每日最多显示 8 条）：

1. **作者手写事件** `manual_events`：经典关卡的核心，例如政策原文的标题和时间，由作者根据公开报道写成，`importance=3`。
2. **巨潮公告**（关卡股票，回看期最后 10 日到揭示期末）。先过滤再归类：
   - 丢弃：标题匹配 `法律意见书|独立董事|核查意见|保荐|监事会决议|董事会决议公告$|章程|制度|提示性公告$` 这类例行公告（规则写在 `replay_ingest/rules.py`，可在规格里覆盖）。
   - 按标题正则归类：`业绩预告|业绩快报|年度报告|半年度报告|季度报告` → `earnings`；`停产|减产|事故|检修|火灾` → `operation`；`中标|签订|合同` → `contract`；`增持|减持|回购|质押` → `holding`；`风险提示|异常波动|退市|立案|处罚|问询` → `risk`；其余 → `other`，`importance=1`，默认不展示，只在揭示期使用。
3. **东财公司动态** `stock_gsrl_gsdt_em`：按关卡日期逐日抓，过滤关卡股票；`事件类型` 原样放进 `category`。
4. **新闻联播** `news_cctv`：只保留标题或正文命中 `sources.cctv.keywords` 的条目，默认关键词为 `国务院|常务会议|中国人民银行|央行|降准|降息|证监会|金融监管|财政部|印花税|发改委|工信部|稳增长|房地产` 加上关卡行业词。正文截到 300 字。
5. **cls 快讯与个股新闻**：只有抓存开始以后的关卡才有（2026-10-26 起）。

**时间归属规则**（构建器 `assign_slot`，按上海本地时间判断，然后换算到关卡的 `(day_idx, slot)`）：

| 情况 | 归属 |
| --- | --- |
| 发布日不是交易日 | 下一交易日的 `pre_open` |
| 时刻未知（巨潮 `00:00:00`、东财只有日期、公司动态） | 当日 `pre_open` |
| `< 09:30` | 当日 `pre_open` |
| `09:30 ≤ t < 15:00` | 当日 `intraday`（到 `close` 阶段才可见） |
| `≥ 15:00` | 当日 `post_close` |
| 新闻联播（某日） | 当日 `post_close`；如果当天不是交易日，则下一交易日 `pre_open` |

可见性（domain 函数 `event_visible`）：`intraday` 的事件到 `close` 阶段才可见，玩家此时只能按收盘价成交，收盘价已经包含了反应，所以不会因此占便宜。**“巨潮 `00:00` 等于盘前”这条假设还需核实**（盘后发布的公告通常标注为下一交易日的日期）：`verify` 子命令会统计“归到 `pre_open` 的重要公告当日的开盘跳空”与“前一日盘中的异动”，人工抽查 20 条。见 Q10。

### 2.7 复权口径：以第 0 日为锚的复权价

- 对每只股票每一天 t：`f(t) = hfq_close(t) / raw_close(t)`；调整价 `adj_x(t) = raw_x(t) · f(t) / f(T0)`，x 取 o/h/l/c，`T0` 是游戏第 0 日的**前一交易日**（也就是第 0 日盘前报价那一天）。按四舍五入取整到分（`round_half_up`，与 `domain/money.py` 同口径，构建器自己实现一份标准库版本）。
- **效果**：
  - 开局时的价格等于真实价，和新闻里提到的价格对得上。
  - 回看期价格按前复权方式缩放，K 线连续。
  - 游戏期遇到除权时，价格按后复权方式连续，相当于红股和红利再投资，持仓不用处理送转。
- 成交量不复权（股数，等于手 × 100）。
- 后复权价只有两位小数，`f(t)` 会有约 1e-4 的误差；构建器统一用 `Fraction` 计算，只在最后取整。

### 2.8 涨跌停与停牌标注（构建器计算，运行时只读）

- **每日涨跌幅 `lim_bp`**（`replay_ingest/limits.py::limit_pct_bp(code, date, is_st)`）：
  - `688/689` → 2000。
  - `300/301` → 2020-08-24 起 2000，之前 1000。
  - 北交所 `4/8/920` 开头 → 3000（只支持 2021-11-15 以后）。
  - 主板 → 1000；ST → 500（ST 由规格的 `is_st` 显式声明。**MVP 不收 ST 股**，并核对最新的主板风险警示股规则，见 Q8）。
  - 上市前 5 个交易日不设涨跌幅：**游戏期内的这类股票直接拒收**（构建报错）。
- **标志位 `flags`**（位掩码，用原始价判定，容差 ±1 分）：
  - 涨停价 = `round_half_up(ref_prev · (10000 + lim)/10000)`，`ref_prev` = 原始前收 × `f(t−1)/f(t)`（除权参考价）。
  - 位定义：
    - `1` 停牌（当日无行，构建器补齐，o=h=l=c=前收，量 0）
    - `2` 开盘封涨停（开 = 涨停）
    - `4` 开盘封跌停
    - `8` 收盘封涨停
    - `16` 收盘封跌停
    - `32` 除权除息日
- **校验**：每天 `|c/prev − 1| ≤ lim + 10bp`，否则构建失败（这样能发现 ST 漏标或板块规则错误）。

### 3.3 存储、版本化、导入

- **关卡包进 git**：放在 `backend/replay/packs/`。包小、需要 review diff，也会随镜像带上（`backend/.dockerignore` 没有排除 `replay/`，实施时要确认）。**原始数据不进 git**。
- **导入数据库**：关卡包导入 `replay_level_versions.pack`（JSON 列），会话固定引用版本 ID。
  - 导入时用 pydantic 模型 `ReplayPack`（`extra="forbid"`）严格校验，计算 `sha256(规范化 JSON)`。
  - `(slug, version)` 已存在：sha 相同就跳过（幂等）；sha 不同就报错拒绝（同一版本不可变）。
- **导入时机**：
  1. 启动时由 `main.py` 的 lifespan 在 `seed_on_startup` 之后调用 `replay_levels.import_bundled_packs(session_factory)`，扫描 `Settings.REPLAY_PACKS_DIR`（默认指向包内的 `replay/packs`）。失败只记日志，与 `seed_on_startup` 相同。
  2. 手动：`uv run python -m stocksim.services.replay.cli import <path>`。
- **退役**：`replay_levels.status='retired'` 后不能新开该关卡，已有会话不受影响。旧版本永远保留，不删除被会话引用的版本，外键用 `RESTRICT`。
- **运行时缓存**：`levels.get_pack(version_id)` 返回解析后的 `ReplayPack`，用 `functools.lru_cache(maxsize=32)` 缓存（版本不可变，单 worker 安全）。

## 5. 后端

### 5.1 存档类型，以及与 A 的事件模式开关如何共存

- **存档类型**：复盘存档是 `saves.mode='replay'`。`saves.mode` 列（`String(16)`，默认 `normal`）已经存在，目前只会写 `normal`（`services/saves.py`、`legacy_import.py`）。**本模式不改 `saves` 表结构**。
- **与 A、C 的共存（已按 01 §1.1、03 §1.5 核对）**：
  1. A 的事件模式开关是**独立列** `saves.events_enabled`（bool）+ `saves.events_ruleset`（int），不占用 `mode`。复盘存档创建时显式写 `events_enabled=False, events_ruleset=0`；A 的发布钩子只在 `_run_ticks` 里调用，复盘存档不经过那里；A 的 events 类接口对复盘存档返回 409 `EVENTS_DISABLED`，`/supply-chain` 照常返回静态结构。已按决策 16 改为不提供。
  2. C 占用 `mode='challenge'` 与 `mode='challenge_market'`，并在 `models/save.py` 定义 `SAVE_MODE_*` 常量与 `LISTED_MODES = {"normal"}`。E 复用该处的 `SAVE_MODE_REPLAY`（谁先合入谁建常量），**不给 `mode` 加 CHECK 约束**；取值全集与各 mode 的行为矩阵见 06 §3。
- **存档列表**：`GET /saves` 默认**排除** `mode='replay'`，这样现有网页版和手机端的存档列表不变。复盘会话从 `GET /replay/sessions` 列出。
- **数量上限**：
  - `create_save` 的计数改为只数 `mode in LISTED_MODES`（= `{"normal"}`）的存档，与 03 §1.5 同一规则（挑战存档同样不计入）。
  - 复盘会话单独限制 `MAX_REPLAY_SESSIONS_PER_USER = 10`（已结算的也算），超出时返回 `SAVE_LIMIT_REACHED {limit:10, mode:"replay"}`，复用现有错误码。
- **创建时 `Save` 字段取值**：`mode='replay'`、`events_enabled=False`、`events_ruleset=0`、**`clock_rules=1`（显式传入）**、`market_seed=0`、`tick=0`、`trading_day=0`、`clock_minute=540`、`paused=True`、`last_tick_at=None`、`t0_mode=False`、`trade_unit=100`、默认费率、`auto_enabled=False`。同时创建 `SaveStats`。**不调用** `init_market_for_save`，也就没有 `market_states` 和 `candles` 行。
- **为什么是 `clock_rules=1`**：07 给 `saves.clock_rules` 的 ORM 默认值是 2（新存档默认 v2），而 v2 的撮合窗是 `[9:30,11:30) ∪ [13:00,15:00)`，**不含 900**（07 §4.2）。复盘的收盘阶段在 900 按收盘价成交（§1.3、§5.4 第 2 点），只有 v1 的 `is_order_time(m, 1) == is_trading_time(m)`（两端闭区间）满足。复盘不经过 07 的调度器、引擎和换日逻辑，`clock_rules` 只影响撮合窗与成就时段窗口，所以写 1 没有副作用。若将来想让复盘也用 v2，就要把收盘阶段的 `clock_minute` 改为 899（并核对成就时段），不建议。
- **阶段与时钟的对应**：`phase` 从 `save.clock_minute` 推导（540/570/900/960，四个值）。`save.trading_day = day_idx`，`save.tick = day_idx·4 + phase_idx`，单调递增，成交行会记录这个值。结算后 `tick = play_days·4`，`clock_minute=960`，`trading_day = play_days − 1`。

### 5.4 下单复用 `trading.place_order` 需要满足什么

`place_order(db, save, user_id, *, code, side, quantity, price_type, …) -> Trade` **签名不变**。复盘要满足的条件和对应改动：

1. **报价**：`_place_once` 调 `load_market` 拿到复盘状态（§5.3），`to_quote(state, code)` 得到 `Quote`，价格是当前阶段的开盘价或收盘价。
2. **交易时段**：时钟 v2 合入后 `execute_order` 改用 `is_order_time(minute, settings.clock_rules)`（07 §4.2，`TradeSettings.clock_rules = save.clock_rules`）。复盘存档 `clock_rules = 1`，所以仍等于 `is_trading_time(save.clock_minute)`：570 和 900 都在交易时段内（两端闭区间），540 和 960 不在，**盘前和盘后会自然得到 `MARKET_CLOSED`**，不用新增代码。若误写成 v2，900 会被拒，§8.2 的测试要覆盖“收盘阶段能成交”。
3. **T+1**：`today_trade_refs(db, save, trading_day)` 用 `state["trading_day"] = day_idx`，天然成立。
4. **真实涨跌幅（domain 小改，归 domain agent，向后兼容）**：
   - `domain/rules.py`：`limit_up_cents(prev, pct_bp=LIMIT_PCT_BP)`、`limit_down_cents(prev, pct_bp=LIMIT_PCT_BP)`、`clamp_to_limits(price, prev, pct_bp=LIMIT_PCT_BP)`，默认值保持 10%。
   - `domain/types.py::Quote` 增加 `limit_pct_bp: int = 1000`。
   - `domain/market_engine.py::to_quote` 读取 `stock.get("limit_pct_bp", LIMIT_PCT_BP)`。
   - `domain/matching.py::_check_limit_price` 改用 `quote.limit_pct_bp`。
   - 现有单元测试全部保持通过，另加 20% 的用例。
5. **封板和停牌（服务层钩子，不改 domain）**：在 `trading._place_once` 里 `quote` 之后、`execute_order` 之前插入：

   ```python
   guard = market_service.trade_guard(state, code, side)   # 普通存档恒为 None
   if guard is not None:
       raise AppError(*guard)
   ```

   `trade_guard` 的判定：
   - 有 `suspended` → `(REPLAY_STOCK_SUSPENDED, {"code":code})`。
   - 买入且 `locked_up` → `(REPLAY_LIMIT_LOCKED, {"code":code,"side":"buy"})`。
   - 卖出且 `locked_down` → 同上，`side` 为 `"sell"`。
   - 会话已结算 → `REPLAY_SESSION_SETTLED`。为此复盘状态里带 `_settled=True`，由 `trade_guard` 读取。

   阶段与标志位：`open` 阶段用 flags 位 2/4，`close` 阶段用位 8/16，停牌是位 1。
6. **乐观锁**：推进和下单都会改 `saves` 行（`trade_seq`、`cash`、`tick`），沿用 `saves.version`。推进服务按 `_retrying` 模式写，遇到 `StaleDataError` 就回滚、刷新后重算。
7. **成交快照**：`trades.prev_close_cents` = 显示前收，`tick` = 阶段 tick，`clock_minute` = 570/900，都由现有代码按 `save` 字段写入。

### 5.5 推进、结束、结算服务（`services/replay/sessions.py`）

- `create_session(db, user, *, level_slug, masked, name="") -> Save`：
  - 校验关卡已发布；`masked=False` 时不受限，`masked=True` 时要求 `masked_allowed`。
  - 检查上限，取 `current_version_id`。
  - 计算 `is_first_attempt`：该用户此前有没有该 `level_id` 下任何版本的会话。
  - 建 `Save`、`SaveStats`、`ReplaySession`，在同一事务里提交。
- `advance(db, save, *, to, expected_tick, skip_pending) -> AdvanceResult`：
  1. 会话已结算 → `REPLAY_SESSION_SETTLED`。`expected_tick != save.tick` → 不推进，直接返回当前视图，并带 `stale=true`。
  2. 本位置是某题 `closes`、且该题未答 → 有 `skip_pending` 时写 `skipped=true`、分数 0，否则抛 `REPLAY_PREDICTION_PENDING {"question_ids":[...]}`。
  3. `next_position`：
     - 返回 `None` → 调 `settle`。
     - 离开 `close` 阶段（进入 `post_close`）时 → `equity.upsert_snapshot(db, save, day_idx, cash, mv_at_close, tick)`。
  4. 更新 `save.trading_day/clock_minute/tick`。
  5. 对 `resolves ≤ 新位置` 的题计分（§5.6）。
  6. 收集新可见事件（相对旧位置新增的部分），一并返回。
  7. 遇到 `StaleDataError` / `IntegrityError` 时回滚、重读后重算，最多 3 次。
  8. `to="next_day"` 就循环第 2–5 步，直到下一个 `pre_open`；遇到题目开放或截止就提前停，`stopped_reason ∈ {"question_open","question_due","settled"}`。
- `finish(db, save)`：直接 `settle`，持仓按当前可见价估值，未答题记 0 分。
- `settle(db, save)`：
  - 写最后一日的权益快照（如果还没写）。
  - 计算 `final_equity_cents` / `return_bp`（相对 `initial_fund_cents`）/ `benchmark_return_bp`（基准从第 0 日前收到最后可见收盘）/ `excess_bp`。
  - 对剩余题计分入账；累加 `points_total`；`status='settled'`，`settled_at=now`；`clock_minute=960`。
  - 和上面的步骤在**同一事务**里提交（B 的入账函数不自己提交，见附录 A）。

### 5.6 预测与积分：复用 B（E4）

E 不自己实现计分公式，也不自己建积分表。`services/replay/predictions.py`：

- `list_questions(db, save)`：只返回已开放（`opens ≤ 当前位置`）的题，状态取 `open|answered|closed|scored|skipped`；计分后带 `result`（正确档位、真实涨跌幅、得分、积分）。
- `answer(db, save, question_id, payload)`：
  - 题目不存在 → `VALIDATION_ERROR {"field":"question_id"}`。
  - 未开放或已截止 → `REPLAY_QUESTION_CLOSED {"question_id", "state":"not_open"|"closed"}`。
  - 校验 payload：
    - `direction_bucket`：长度等于档数、每项是整数且 ≥0、合计 100。
    - `rank`：长度 = `top_k`，元素来自候选，且不重复。
  - upsert 到 `replay_predictions`。
- `score_due(db, save, session, upto_position)`：
  - 对 `resolves ≤ upto` 且未计分的题调用 B：
    - `direction_bucket` → `scoring.rps_score(probs, outcome_idx)`。
    - `rank` → `scoring.ndcg_at_k_score(order, relevance, k=3)`。
  - 积分 = `round_half_up(score × 系数)`，系数为匿名 100/100、实名 50/100（Q1）。
  - 只有 `session.is_first_attempt` 才入账：调用 `points.credit(db, user_id=…, save_id=…, delta=points, reason="replay_prediction", ref=f"replay:{save_id.hex}:{qid}", idempotency_key=f"replay:{user_id.hex}:{level_id.hex}:{qid}")`（02 §1.1：uuid 用 32 位 hex，键 ≤96 字符）。`credit` 只 flush 不 commit，冲突时抛 `StaleDataError`/`IntegrityError`，由 §5.5 第 7 步的整体重试处理（重试时幂等键命中已提交流水）。非首次只记录 `score`，`points=0`。
  - 这里用 `level_id` 而不是 `version_id` 做幂等键，所以关卡升级版本后也不能重复刷分。
- 答案里的代码是本会话可见的代码（匿名时是别名），计分前按包内 `stock_key` 映射。

如果 B 还没合入：E4 之前的里程碑不受影响。E4 可以先只写 `score`、`points=NULL`，等 B 合入后用一次性回填命令 `cli backfill-points` 补记。

### 5.7 快讯对象：复用 A 的形状

复盘事件流接口返回 `ReplayFeedItemOut`，**字段与 A 的 `NewsOut`（01 §1.4）同名**，以便前端复用 A 的快讯组件（网页 `features/news/view.js`、手机 `js/pages/news.js` 的条目渲染）。映射写在唯一的适配点 `services/replay/feed.py::to_feed_item(ev, session) -> dict`：

| A `NewsOut` 字段 | 复盘取值 |
| --- | --- |
| `news_id` / `event_id` | 都取 `"replay:" + ev.id`（复盘事件由关卡包确定，不是 A 的 `e{day}-{slot}`，加前缀避免混淆） |
| `stage` | 恒为 `"publish"`（复盘没有铺垫/证实/辟谣） |
| `kind` | `policy` → `policy`；`announcement` / `company_event` → `announcement`；`news` / `flash` → `news`。不产生 `sudden` / `rumor` |
| `subtype` | null |
| `scope` | `ev.scope` |
| `major` | `importance == 3` |
| `sentiment` | null（A 中为 `1\|-1`；复用组件需容忍 null。E6 的模型情绪只在揭示页给） |
| `title` | 匿名模式取 `title_masked`，实名取原文；`hide_in_masked=true` 的事件在匿名模式下不出现 |
| `industry` / `code` / `stock_name` | 第一个关联行业 / 第一个关联股票的本会话可见代码与名称（匿名时为别名） |
| `trading_day` | `ev.day_idx` |

## 10. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| AKShare 接口变动或数据源改版（东财参数、巨潮接口、央视页面结构） | 抓取失败 | 依赖组版本锁定在 `<2`；原始数据落盘以后，构建不再依赖网络；`fetch_log` 监控失败率；升级 akshare 时先用 `FakeClient` 夹具回归，再实测一次。 |
| 限速或封 IP（东财、巨潮对海外和高频请求敏感） | 抓不到 | 令牌桶 + 退避 + 熔断；支持代理环境变量；抓存服务部署在国内服务器（Q7）；历史数据一次性抓完后只做增量。 |
| 函数内部不限速（巨潮翻页、新闻联播约 20 次请求） | 触发反爬 | 缩小单次调用范围（每股每季度、每日一次）；调用之间的间隔放大。 |
| 复权误差（hfq 只有两位小数） | 价格差 1 分 | `Fraction` 计算 + `clamp_to_limits`；flags 用原始价判定。 |
| 巨潮 `00:00` 时间归属不准 | 盘后公告提前或推后一个阶段，形成剧透 | §2.6 的核实统计 + 人工抽查；有疑问时归到更晚的阶段（宁可晚看）。 |
| 停牌、长期停牌、退市股 | 关卡期间停牌 | 停牌标志与禁止交易；游戏期停牌超过一半的股票构建时告警；退市股巨潮函数会 `KeyError`，MVP 不收（E6 再评估东财数据）。 |
| 板块成分只有当前（幸存者偏差） | 主题关卡选股失真 | 只当提示，作者人工确认；精选关卡的股票由作者指定。 |
| ST 与涨跌幅规则变化 | `lim_bp` 错误 | MVP 不收 ST；越限校验让构建失败；规则集中写在 `limits.py`，带日期分段。 |
| 历史印花税和费率变化 | 交易成本与当年不同 | 用存档默认费率，揭示页注明“费率按本游戏设置”。如果要还原，可在包里放 `fees_hint` 供 `create_session` 使用（不做为 MVP）。 |
| 版权（cls、东财新闻、新闻联播全文） | 仓库公开或分发有风险 | 关卡包里只存标题和 ≤300 字摘要加来源链接；原始数据不进 git；手写事件由作者用自己的话写（Q3）。 |
