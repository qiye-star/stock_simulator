## 0. 摘要

- **只在每日挑战上开市**：全服同一 seed、同一剧本，才有共同价格。单人存档每人事件不同，**不开市**。
- **开市对象**：挑战的 **4 个回合事件**（03 §1.3、§1.7 `round_event_ids`）。每个回合事件生成 1 个**分档合约**（5 档，3 个交易日涨跌幅）；传闻类再加 1 个**真假合约**（二元），即一场 4–8 个市场（上限常量仍为 8）。v2 每个交易日都有 1–2 条重大事件，回合以外的重大事件**不开市**。
- **做市**：LMSR，`domain/prediction_market/lmsr.py` 纯函数。份额为整数，每份兑付 100 积分；买入向上取整、卖出向下取整。为保证跨平台逐位可复现，用 `decimal`（libmpdec 的 `exp/ln` 是正确舍入的）计算，**不用 `math` 浮点**。
- **`b` 由补贴上限反推**：`b = S / (100·ln(1/p_min))`。S 按挑战预期参与人数分 3 档：1000、2000、4000 积分。做市商最大亏损（即补贴）≤ S，由“资金池永不为负”这一不变量来验证。
- **用户积分全走 B 的账本，补贴记在市场行**：买入、卖出、兑付、退款是用户与资金池之间的往来，经 B 的 `debit/credit` 记账（reason `market_*`）；B 没有系统账户，开市时补贴 S 记为本市场的发行量 `subsidy_points`，结算后池余额记为 `subsidy_returned_points`。全局守恒：账本 `market_*` 流水合计 + 各池余额 = Σ发行 − Σ退回（§5.6）。
- **时间线**：市场按 C 定义的**回合制全服公共时间线**（03 §1.2，真实时间 → 挑战 trading tick）开市、休市、结算。没有人能领先公共时间线，“先玩后押”由时间模型根治；`PM_LOCKED_AHEAD` 只保留为防御性检查。
- **并发**：市场行 `SELECT … FOR UPDATE`（PostgreSQL/MySQL），再加 `version` 乐观锁兜底（SQLite 不支持 FOR UPDATE，靠它）。另有 Idempotency-Key 幂等、`max_cost_points`/`min_proceeds_points` 滑点保护，以及单市场净投入、单挑战买入额度、频率三道限额。
- **推送**：新增全服通道 `WS /api/v1/ws/prediction-markets`。每个进程一个 Hub，每秒轮询数据库差量后扇出；多实例无需消息总线。断线时客户端退回 REST 轮询。
- **AI**：首期不做 AI 交易员。开盘先验用离线仿真得到的“公开基率”。单人模式的 AI 群体概率**不值得做**，理由见 §7。

## 1. 对外契约

### 1.1 D 依赖 B（02）的积分账本：按 02 §1.1 定稿
放在 `backend/src/stocksim/services/points.py`（02 §1.1）。D 只用以下函数，**全部 keyword-only、只 flush 不 commit**，冲突时原样抛 `StaleDataError`/`IntegrityError`，由 D 的重试循环整体回滚重做：

```python
points.debit(db, *, user_id, amount, reason, ref, idempotency_key, save_id=None, meta=None) -> LedgerEntry
    # 买入扣款；余额不足抛 AppError(POINTS_INSUFFICIENT, {"required", "balance"})（422，02 §1.4）
points.credit(db, *, user_id, delta, reason, ref, idempotency_key, save_id=None, meta=None) -> LedgerEntry
    # 卖出回款、兑付、退款；delta ≥ 0
points.balance(db, *, user_id) -> int
points.find_entry(db, *, user_id, idempotency_key) -> LedgerEntry | None
```
- **reason**（已在 02 `REASONS` 登记，D 不另起）：`market_buy`（debit）、`market_sell`、`market_payout`、`market_refund`（credit）。
- **幂等键与 ref**（02 §1.1 表）：`market_buy:{trade.hex}`、`market_sell:{trade.hex}`、`market_payout:{market.hex}:{user.hex}`、`market_refund:{market.hex}:{user.hex}`，最长 80 字符（≤96）；`ref = f"market:{market.hex}"`（39 字符，≤64）。兑付与退款的键由 (市场, 用户) 决定，不依赖重试中会重新生成的结算行 id。
- **没有系统账户**（02 §1.1 定稿）：做市补贴不进用户账本。开市时把 S 记在本市场行 `subsidy_points`（“发行”），资金池 `pool_points = S`；结算或作废后池余额“退回”记在 `subsidy_returned_points`（作废时可为负，表示系统多发），然后 `pool_points = 0`。全局守恒改用含发行量的形式（§5.6）。
- **没有 `lock_account`**：每次 `credit/debit` 都会改 `point_accounts` 行（`version` 乐观锁），同一用户跨市场并发下单会在 flush/提交时冲突并重试，重试时重新查询额度，所以“额度检查不被并发绕过”仍成立（§5.5）。
- **锁顺序**：先 `SELECT … FOR UPDATE` 本市场行，再调 `credit/debit`；同一事务给多个用户记账（结算、作废）时按 `user_id` 升序调用。B 自己的流程只改账户行，不会反向等待市场行。

## 2. 现状要点（已读代码核对）

- `services/trading.py`：下单幂等用 `trades.idempotency_key`（存档内唯一）。命中就回放；并发同键时撞 `IntegrityError`，回滚后查出已有记录回放（`replayed=True`，HTTP 200）。乐观锁用 `saves.version`（`__mapper_args__={"version_id_col": version}`），冲突抛 `StaleDataError`，回滚后 `db.refresh(save)` 重试，`MAX_ATTEMPTS=3`。服务函数**自己 commit**。D 沿用这套写法，但锁的是市场行而不是存档行。
- `services/market.py::_retrying` 把 `StaleDataError` 与 `IntegrityError` 都当作“别人已改”处理，整体回滚重算，**不做 insert-or-ignore**。D 的结算与状态迁移照此处理。
- `db/types.py`：`Money` 拒绝 float，底层 BigInteger，**仅用于分**。积分不是钱，用 `BigInteger` 加 `_points` 后缀（以 02 的命名为准），不复用 `Money`。JSON 列用 `json_column_type()`。
- `db/session.py`：SQLite 开 WAL、`busy_timeout=5000`。SQLite 单写者：并发事务在首次写时串行化，后来者 UPDATE 版本不匹配，抛 `StaleDataError`。
- `api/ws.py`：每个连接每 `refresh_rate_ms` 在线程池里新建 Session 跑一轮 `tick_once`，与上一轮快照做差。消息格式是 `{"t": ...}`。鉴权失败时先 accept，再发 error，然后以 4401/4404 关闭。路由由 `api/routers/__init__.py` 自动发现（模块暴露 `router` 即可）。
- 部署：`backend/Dockerfile` 目前 `--workers 1`。nginx（`deploy/host-nginx.example.conf`、`mobile-prototype/deploy/nginx.conf.template`）和 vite 都按前缀 `/api/v1/ws/` 做升级转发，新的 WS 路径放在这个前缀下，不用改代理。
- `tests/unit/domain/test_purity.py`：禁止 import `random/time/json/uuid/os/...`，禁止访问 `.now/.time/.random` 属性。`math`、`decimal`、`hashlib` 不在禁止名单，但 D 的 domain 只用 `decimal`。
- 前端：`frontend/src/features/*/index.js` 自动登记；`state/session.js::TABS` 是导航页名单。手机端 `store.real.js` 已经给下单带 `Idempotency-Key: uuid()`。
- 颜色约束：手机端 `--up/--down`（网页端 `--up-color/--down-color`）**只用于行情数据**（价格、涨跌幅、K 线、盈亏）。

## 3. 合约设计

### 3.1 哪些事件开市
- 只在挑战上开市，且事件是**回合事件**（`event_id ∈ round_event_ids(ch)`，必然 `major=true`）。v2 下 03 不再保证 `[1, end_tt]` 内只有回合事件（03 §4.2 已改为贪心挑回合），所以“对全部 major 开市”与“对回合事件开市”不再等价，必须按回合过滤。一场挑战有 4 个分档合约和 0–4 个传闻合约。
- 非回合的重大事件不开市：它们没有停顿窗口，交易只能在快放中进行，价格来不及形成；也不出题，与 C 的回合题一一对应。
- 小快讯不开市：数量多、信噪比低（01 §5.1 中小快讯单股方向一致率约 62%），开了会分散流动性。
- 单人存档、普通事件存档都不开市。

### 3.2 合约生成规则（纯函数 `domain/prediction_market/contracts.py::contracts_for_event`）
输入是 A 的 `GameEvent`（服务端完整形态）、挑战边界 `(first_tt, last_tt)` 和 B 的公开结构 `Structure`（只取 `stock_count` 定 n）。输出 `tuple[ContractSpec, ...]`。**合约文本只用 01 §1.8 允许公开的字段**：kind、scope、源行业/源股票、sentiment、首次出现时点。不得用 `magnitude_ppm`、`expectation`、`knots`、`impacts`、`rumor.truth`、`publish_trading_tick`（priced_in 事件在正式发布前这个时点是隐藏的）。

记 `f = first_seen_trading_tick`（该事件所有 news 的最小 tick），`d0 = tb.day_of(f)`（v2 即 `f // 242`）。

| 合约 `kind` | 生成条件 | 选项（idx 顺序固定） | 问题（前端按 i18n 渲染） |
| --- | --- | --- | --- |
| `bucket` | 每条重大事件 | 5 档：`b0` < e0 ≤ `b1` < e1 ≤ `b2` < e2 ≤ `b3` < e3 ≤ `b4` | “{主体} 在 D{d0}–D{d0+2} 的累计涨跌幅（相对 D{d0-1} 收盘）落在哪一档？” |
| `rumor` | `kind=="rumor"` 的重大事件 | `deny`、`confirm`（与 02 传闻题 `probs=[p_辟谣, p_证实]` 同序） | “这条传闻最终会被证实还是辟谣？” |

- **主体**：scope=industry 时是源行业等权；stock 是源股票本身；market 是全部 385 只等权。
- **档位边界与窗口直接用 02 的公开函数**（02 §1.3）：`edges_bp = bucket_edges_bp(scope, n, DIRECTION_WINDOW_DAYS, clock_rules=ch.clock_rules)`，n 取 B 的 `structure_for(ruleset).stock_count[源行业]`（industry）、1（stock）、385（market）；窗口 `DIRECTION_WINDOW_DAYS = 3`。这样同一事件的挑战回合题（C 复用 B 的出题）和市场合约档位、窗口逐一相同。例（v2，02 §4.1 的 v2 表）：n=5 的行业为 `(-320, -110, 110, 320)`，单股 `(-600, -200, 200, 600)`，全市场 `(-200, -70, 70, 200)`；v1 对照为 `(-600,-200,200,600)` / `(-1340,-450,450,1340)` / `(-250,-100,100,250)`。
- 用户举的“有色板块 3 个交易日涨超 5%”对应 industry 分档的最高档 `b4`（具体边界随行业股票数 n 与时钟版本变化，n=5 时 v2 为“≥3.2%”、v1 为“≥6%”）。前端在列表卡片上把概率最高的档写成一句话（如“涨超 5%：38%”）。
- **窗口锚定在首次出现日 d0，而不是正式发布日**：priced_in 事件的发布时点在发布前是隐藏的，锚定发布日会泄露它。
- **过滤**（任一不满足就不生成该合约）：
  - `f ≥ first_tt`；
  - bucket：`resolve_tt ≤ last_tt`（窗口必须完整落在挑战内，且窗口本身由公开的 f 推出，过滤不会泄密）；
  - `close_tt - open_tt ≥ MIN_OPEN_TICKS[clock_rules]`：v1 10，v2 `N/8 ≈ 30`（10 个 v2 tick 只有 10 个游戏分钟、快放时约 7.5 秒）。v2 的回合事件里 bucket 合约 `close − open ≥ 2·242 − 241 = 243`、传闻合约 `≥ 242 − 12`，这条过滤实际不会触发，只作防御；
  - 每场挑战按 `(f, event_id, kind)` 升序截断到 `MAX_MARKETS_PER_CHALLENGE = 8`。
- **rumor 合约总是生成**。若揭晓 tick 超出挑战，在 `last_tt` 结算（§3.3）。不能用“这条传闻有没有市场”泄露揭晓时点。

```python
@dataclass(frozen=True)
class ContractSpec:
    kind: Literal["bucket", "rumor"]
    event_id: str
    scope: Literal["industry", "stock", "market"] | None   # rumor 合约也带上，用于展示
    industry: str | None
    code: str | None
    from_day: int | None; to_day: int | None               # 仅 bucket
    edges_bp: tuple[int, ...]                              # rumor 为 ()
    n_outcomes: int                                        # 5 或 2
    prior_ppm: tuple[int, ...]                             # 见 §4.5，和为 1_000_000
    open_tt: int; close_tt: int; resolve_tt: int
    close_public: bool                                     # rumor 为 False
```

例（v2）：回合事件 `e3-0`（industry，有色，sentiment=+1，发布偏移 47 即 10:17，f = 242·3+47 = 773）→ bucket 合约：`from_day=3, to_day=5`，`open_tt=773`，`close_tt=242·5=1210`（第 5 日 9:30），`resolve_tt=242·6=1452`（第 6 日 9:30，第 5 日收盘已写入），`edges_bp=(-320,-110,110,320)`（有色 n=5，02 §4.1 的 v2 表）。
（v1 对照：`e37-0`，f = 20·37+5 = 745 → `from_day=37, to_day=39`，`open_tt=745`，`close_tt=780`，`resolve_tt=800`，`edges_bp=(-600,-200,200,600)`。）

### 3.3 时点（全部是挑战公共时间线上的 trading tick）

| 合约 | open_tt | close_tt（≥ 时停止交易） | resolve_tt（≥ 时结算） |
| --- | --- | --- | --- |
| bucket | `f` | `tb.first_tt(to_day)`，即最后一个交易日开盘（v2 为第 to_day 日 9:30）：最后一天“盲盘”，避免临近收盘抢跑 | `tb.first_tt(to_day+1)`，即 to_day 收盘数据可得（v2 为次日 9:30 换日 tick） |
| rumor | `f` | `min(r, last_tt+1) - RUMOR_CLOSE_LEAD_TICKS[clock_rules]`（v1 1，v2 `scale(1) = 12`，约 12 个游戏分钟、快放时 9 秒），r = `rumor.resolve_trading_tick` | `min(r, last_tt+1)` |

- 状态以 `public_trading_tick(ch, now)` 为准，每次交易实时计算，不信任库里存的 status（§5.1）。`opens_at/closes_at/resolves_at` 由 `real_time_of` 换算，只用于展示和排程。
- **rumor 的 close/resolve 时点保密**（会泄露揭晓延迟）：API 在 `status=open` 时 `close_tt/closes_at/resolve_tt/resolves_at` 输出 null。
- **超前锁定**：`knowledge_trading_tick(user) > public_tt` 的用户，对该挑战的所有市场**既不能买也不能卖**（`PM_LOCKED_AHEAD`）。已有持仓照常结算。按 03 的时间模型，`knowledge_trading_tick` 恒等于当前公共 tt（或 None），本检查恒不触发，只作防御（若用户否决 03 Q1 的时间模型，它重新变成主要防线且挡不住小号）。

### 3.4 结算口径
- **bucket**：`v = reference_change_bp(ch, scope, subject, from_day, upto_tt=resolve_tt)`。获胜档 `w = scoring.bucket_of(v, edges)`（02 §1.2，左闭右开 = `#{e ∈ edges : v ≥ e}`，等于边界值时进上一档，与 `bisect_right` 一致）。v 写入 `resolution_value_bp`。**舍入与等权口径以 A 的 `industry_change_bp` 为唯一实现**：D 不自己写涨跌幅公式，由 C 的 `reference_change_bp` 经 B 的 `change_bp_for` 复用 A 的实现。
- **rumor**：`w = 1 if rumor.truth else 0`（选项序 deny、confirm）。按 03，回合事件的传闻揭晓 tick 计入 `end_tt`，所以 `r ≤ last_tt` 恒成立，结算时真值已由 `confirm/deny` 快讯公开；`min(r, last_tt+1)` 只作防御。
- 兑付：每持有 1 份获胜选项得 `SHARE_PAYOUT_POINTS = 100` 积分，其余选项得 0。

### 3.5 作废与退款
| 触发 | 判定 | `void_reason` |
| --- | --- | --- |
| 挑战被撤销（seed 泄露、数据事故，由 C 的 `on_revoked` 触发） | 钩子 | `challenge_revoked` |
| 事件重算不一致 | 开市和结算前用 C 的 `challenge_events` 重算 spec + 真值，对比 `event_fingerprint` | `event_mismatch` |
| 结算数据缺失 | `reference_change_bp` 返回 None（确定性，重试无意义，立即作废） | `data_unavailable` |
| 规则集不一致 | `market.events_ruleset != ch.events_ruleset` | `ruleset_changed` |
| 人工 | `POST /debug/prediction-markets/{id}/void`（仅 `ENABLE_DEBUG_API`） | `manual` |

- **退款口径**（沿用 forecast-arena `settlement_service._refund_market`）：每个用户退 `max(0, Σbought_points − Σsold_points)`。也就是“作废后每人最多回到不亏”，已经卖出获利的人保留利润。
- 退款从资金池出。资金池不足时差额视为额外发行：`subsidy_returned_points = pool − Σ退款`（可为负），然后池清零，池本身永不为负。作废是唯一可能让系统多付的路径，正常结算不会（§4.4）。
- 作废后每个有持仓的用户写一行 `prediction_settlements(kind="voided")`，并推送 `pm_resolved`。

### 3.6 状态机（`prediction_markets.status`）
```
scheduled ──(public_tt ≥ open_tt：记补贴发行 S、定 b 与 q0)──▶ open ──(≥ close_tt)──▶ closed ──(≥ resolve_tt：兑付)──▶ resolved
    └───────────────────────────── 任意非终态 ──(作废条件)──▶ voided
```
- `scheduled` 在挑战创建时由 `materialize` 预生成（含未来事件的问题），**API 永不返回**。
- 迁移由 `pm_lifecycle.sync_market(db, market_id, now)` 完成：锁行、按 public_tt 连跳到应达状态，幂等。调用方有三处：后台 sweeper、交易前、详情读取前。

## 4. LMSR 实现（`backend/src/stocksim/domain/prediction_market/`）

### 4.1 模块与签名
新目录（带 `CLAUDE.md`、`README.md`）：
- `constants.py`：§4–§5 的全部常量。
- `types.py`：`ContractSpec`、`Quote`、`LimitState`。
- `lmsr.py`：
```python
def cost_points(q: Sequence[int], b_milli: int) -> Decimal            # 100·C(q)，未取整
def prices_ppm(q: Sequence[int], b_milli: int) -> tuple[int, ...]     # 和恰为 1_000_000（最大余数法，平分时取小 idx）

def sell_proceeds(q, b_milli, i: int, shares: int) -> int             # 向下取整，可为 0（服务层拒绝 0）

def max_loss_points(b_milli: int, q0: Sequence[int]) -> Decimal      # 100·C(q0) − 100·min(q0)
```
- `contracts.py`：`contracts_for_event`、`resolve_rumor`（档位判定直接用 `domain.scoring.bucket_of`，边界用 `domain.predictions.bucket_edges_bp`）。
- `limits.py`：`check_trade(...) -> str | None`（返回错误码，见 §5.5）。
- `Quote = (side, outcome, shares, points, avg_price_ppm, price_before_ppm, prices_after_ppm)`，字段借自 marketsim `amm.py` 的 `Quote`。

### 4.2 公式（logsumexp）
`q_i` 是选项 i 的未平仓份额（含虚拟先验 `q0_i`，整数），`b = b_milli/1000`（份额单位）：
```
m      = max_i q_i
C(q)   = 100 · ( m + b · ln Σ_i exp((q_i − m)/b) )        # 单位：积分；减 m 保证指数 ≤ 0，不溢出
p_i    = exp((q_i − m)/b) / Σ_j exp((q_j − m)/b)
买 Δ 份 i：x = C(q + Δe_i) − C(q)
卖 Δ 份 i：y = C(q) − C(q − Δe_i)
按花费反求（forecast-arena `_shares_for_cost` 闭式）：Δ* = b · ln( (exp(B/(100b)) − (1−p_i)) / p_i )
```
- `max_shares_for_budget`：先用闭式算 `n = floor(Δ*)`，再用整数校正：当 `n>0` 且 `buy_cost(n) > B` 时 `n -= 1`，当 `buy_cost(n+1) ≤ B` 时 `n += 1`，各最多 3 次，最后夹到 `[0, cap]`。闭式只给初值，结果由 `buy_cost` 判定，因此精确。
- **数值环境**：模块级 `LMSR_CTX = Context(prec=50, rounding=ROUND_HALF_EVEN, Emax=999_999, Emin=-999_999)`，每个函数体都在 `with localcontext(LMSR_CTX):` 内运行。所有运算（含 `+ - * /`）受同一上下文控制，不依赖线程默认上下文。`Decimal.exp()` 与 `Decimal.ln()` 在 libmpdec 中**正确舍入**（Python 文档写明），结果与平台、CPU、libm 无关。
- **一个都不用 float**：输入是 `int` 的 q、b_milli，输出是 `int` 积分和 ppm。

### 4.3 整数规则
| 量 | 规则 |
| --- | --- |
| 份额 | 整数 ≥1；单笔 ≤ `MAX_SHARES_PER_TRADE = 200` |
| 买入花费 | `ceil(quantize(x, 1e-12))`。先量化到 1e-12 消除 prec=50 的尾差（例如买全套时 x 理论上是整数），再向上取整；最少 1 积分 |
| 卖出回款 | `floor(quantize(y, 1e-12))`。为 0 时拒绝（`PM_TRADE_TOO_SMALL`），避免“卖 1 份白丢” |
| 兑付 | `100 × 获胜份额` |
| 价格展示 | `prices_ppm`；均价 `avg_price_ppm = round_half_up_div(points·10_000, shares)`（100 积分 = 1e6 ppm） |

**防刷的数学保证**（写成性质测试，§11）：
- 往返：`sell(Δ)` 紧跟 `buy(Δ)` 时，`ceil(x) ≥ x = y ≥ floor(y)`，回款 ≤ 花费。
- 拆单：Σceil(x_k) ≥ Σx_k = x，拆买不会更便宜；Σfloor(y_k) ≤ y，拆卖不会多拿。
- 任意闭环（同一批账户的成交序列让 q 回到起点）：LMSR 路径无关，合计净收益 ≤ 0。所以**对倒在 LMSR 下无法从做市商或彼此身上套利**，多账号只能绕开单人限额去多吃补贴（§5.5）。
- 顺序买全套（每个选项各 1 份）花费 ∈ [100, 100+n]。实测 5 档、b=6.213 时为 102。不提供“全套赎回”，所以不存在全套套利。

### 4.4 `b` 的选取
- **补贴上限反推**：开市时取 `S = SUBSIDY_TIERS[expected_participants]`，`SUBSIDY_TIERS = ((0, 1_000), (30, 2_000), (150, 4_000))`，即 N<30、30≤N<150、N≥150 三档。
- `b_for_subsidy`：`b_milli = floor(S·1000 / (100·ln(1e6/p_min_ppm)))`；`q0_i = round_half_even(b·ln(p_i/p_min))`（整数，min=0）。之后校验 `max_loss_points(b_milli, q0) ≤ S`；不满足就 `b_milli -= max(1, b_milli//200)` 再算，最多 20 次。b 与 q0 在开市时写库，**之后不再改变**。不在交易中按人数动态调 b：动态 b 会破坏路径无关性和亏损上界。
- **最大亏损证明**：资金池 `P = S + C(q_T) − C(q0) − 100·(q_T,w − q0_w)`。由 `C(q) ≥ 100·max_i q_i ≥ 100·q_w` 得 `P ≥ S − (C(q0) − 100·q0_w) ≥ S − max_loss ≥ 0`。取整只会让 P 更大。所以**正常结算时资金池永不为负**，作为运行时断言和性质测试。
- 数值（用 §4.2 的 Decimal 实现实算，脚本见 §12 步骤 1 的金值）：

| S | 分档（n=5，均匀先验） `b_milli` | 买 1 / 5 / 10 份某档的花费（价格 0.2 → ） | 传闻（先验 辟谣 0.3 / 证实 0.7，选项序 deny、confirm） `b_milli`、q0 | 买“辟谣” 5 / 10 / 20 份（0.30 →） |
| --- | --- | --- | --- | --- |
| 1000 | 6213 | 22 / 138 / 366（→0.227 / 0.359 / 0.556） | 8305，`[0,7]` | 185 / 442 / 1161（→0.44 / 0.589 / 0.827） |
| 2000 | 12426 | 21 / 118 / 275（→0.213 / 0.272 / 0.359） | 16611，`[0,14]` | 167 / 369 / 884（→0.368 / 0.44 / 0.589） |
| 4000 | 24853 | 21 / 109 / 235（→0.207 / 0.234 / 0.272） | 33223，`[0,28]` | 159 / 334 / 738（→0.334 / 0.368 / 0.44） |

往返示例：S=1000 分档，买第 2 档 7 份花 217，立即卖回得 216。
- 含义：在 1000 档，一个人花 ~140 积分能把某档从 20% 推到 36%；在 4000 档要花 ~240 积分才推到 27%。人越多 b 越大、越难推动、补贴越多。**这些数值要与 02 的积分发放量对齐**（Q2，汇总见 06 §4）：按 02，每题 0–100 积分、一张卡 1–3 题，单市场净投入上限 `max(200, S//4)`（250–1000）约等于 1–4 张满分卡。

### 4.5 开盘先验
- rumor：`RUMOR_PRIOR_PPM = (300_000, 700_000)`（deny、confirm）。与时钟版本无关。00 决策 5 写明约三成传闻被辟谣，这是公开规则。
- bucket：`BUCKET_PRIOR_PPM[(scope, sentiment)]`，由离线脚本 `scripts/pm_prior_report.py` 统计得到：纯标准库，只 import `stocksim.domain`，用 01 §11 步骤 12 的仿真器，**按 v2 时间基**（`--clock-rules 2`：07 的 v2 噪声、01 的 v2 事件常量、02 的 v2 档位）对 20 个 seed × 120 交易日统计每个 `(scope, sentiment)` 的分档频率。D 只在挑战（v2）上开市，所以只需 v2 先验；若将来出现 v1 挑战，再加 `clock_rules` 维度。必须在 07 的 C4 与 01 的 v2 仿真定稿之后跑。统计结果夹到 `PRIOR_FLOOR_PPM = 100_000` 后再归一。这只是**公开基率**（只按公开字段分组），不含单个事件的隐藏信息。脚本未跑出结果前，用均匀先验 `(200_000,)*5`。
- 代价：p_min 从 0.2 降到 0.1 时 ln(1/p_min) 从 1.61 变成 2.30，同样 S 下 b 约减 30%。换来的是“第一个进场的人白捡补贴”的情况大幅减少。

### 4.6 `math` 浮点可以接受吗：结论
- **账本相关（花费、回款、份额反求、b、q0）一律用 Decimal**。原因：`math.exp/log` 依赖平台 libm，glibc、musl、macOS 在最后一位上可能不同，ceil/floor 恰在整数边界时会翻转 1 积分。Python 升级也可能改变结果。这样“同样的成交序列得到同样的结果”就无法跨部署保证，金值测试也会在不同 CI 镜像上随机失败。
- **展示和前端预估可以用浮点**：`frontend` 的 `model.js::lmsrPreview` 用 JS `Math.exp`，只用于滑块即时反馈。权威数字永远来自服务端 `quote`/`trade`，容差由 `max_cost_points` 吸收。
- **跨数据库一致**：库里只存整数（q、b_milli、积分、ppm）和 JSON 整数数组，不在 SQL 中做任何数学运算，所以 SQLite、PostgreSQL、MySQL 读回的值完全相同。可复现性由 `domain` 的纯函数和金值测试保证（§11.1）。
- 性能：prec=50 时一次 `exp` 约数十微秒；一次买入约 2×(n+1) 次超越函数运算，再加反求校正，单笔 < 5 ms。

## 5. 并发与一致性

### 5.1 交易事务（`services/prediction_markets.py::trade`）
```
for attempt in range(PM_MAX_ATTEMPTS = 5):
  try:
    1. 幂等：用 (user_id, Idempotency-Key) 查 prediction_trades → 命中且 market_id 相同则回放（replayed=True）；market_id 不同 → 422 VALIDATION_ERROR {field:"Idempotency-Key"}
    2. m = SELECT prediction_markets WHERE id=? FOR UPDATE（.execution_options(populate_existing=True)）
    3. ch = challenges.get_challenge；ptt = public_trading_tick(ch, now)；lifecycle._advance_locked(m, ptt)（只改内存状态，随本事务提交）
       非 open → PM_NOT_OPEN（先 commit 状态迁移再抛错）
    4. kt = knowledge_trading_tick(user)；kt is not None and kt > ptt → PM_LOCKED_AHEAD
    5. 频率：近 60 s 该用户 prediction_trades 条数 ≥ RATE_LIMIT_TRADES → PM_RATE_LIMITED
    6. q = 选项行（按 idx）；pos = 该用户在本市场的持仓行
    7. （无单独加锁步骤：账户行在第 9 步 debit/credit 时随乐观锁更新；锁顺序 市场 → 账户，见 §1.1）
    8. domain：shares（或由 budget 反求）、cost/proceeds、限额检查（§5.5）、滑点检查（§5.4）
    9. 买：points.debit(amount=cost, reason="market_buy", …)；卖：points.credit(delta=proceeds, reason="market_sell", …)；更新选项 q、m.pool_points、m.trade_seq+=1、m.prices_ppm、m.volume_shares、持仓；插入 prediction_trades（seq=m.trade_seq）
   10. db.commit()；返回
  except IntegrityError:  rollback；按幂等键查到就回放，否则 raise
  except StaleDataError:  rollback；continue
raise AppError(PM_BUSY)
```
- 市场行**每笔都会改**（`trade_seq`、`pool_points`），所以 `version` 必然递增，乐观锁一定生效。
- 第 3 步的状态迁移随交易一起提交。抛 `PM_NOT_OPEN` 前单独 commit 迁移（此时还没写任何交易数据），sweeper 之后再做是幂等的。

### 5.2 锁：三种数据库都能跑
| 库 | 市场行 | 冲突表现 | 处理 |
| --- | --- | --- | --- |
| PostgreSQL | `FOR UPDATE` 行锁，同一市场的交易排队 | 基本不重试 | — |
| MySQL InnoDB | `FOR UPDATE`（锁定读，读到最新已提交版本） | 同上；死锁时抛 `OperationalError 1213` | 把 1213 也归入重试（`_is_retryable(exc)`），并按固定锁顺序避免死锁 |
| SQLite | `with_for_update()` 被忽略；WAL 下写者在首次写时串行化，`busy_timeout=5000` 等锁 | 后到者 UPDATE 版本不匹配，抛 `StaleDataError` | 重试，最多 5 次 |

- 模型同时开 `version_id_col`，无论哪种库都兜底。
- 结算与作废：锁市场行，然后按 `user_id` 升序逐个 `points.credit`（`market_payout` / `market_refund`），在**单个事务**里完成全部兑付，最后写 `subsidy_returned_points` 并把池清零。一个市场的持仓在百人量级，单事务足够；千人以上的分批方案见风险 4。

### 5.3 幂等
- HTTP：`POST /prediction-markets/{id}/trades` **必须**带 `Idempotency-Key`（≤64），缺失返回 422。表上 UQ `(user_id, idempotency_key)`。重复请求返回 200 和原结果（`replayed=true`），首次是 201。
- 账本：每笔流水的幂等键见 §1.1；事务重试时整体回滚，不会重复记账。
- 生命周期：`materialize` 靠 UQ `(challenge_id, event_id, kind)`；开市记发行靠 scheduled→open 的条件迁移（`subsidy_points` 只在这一步写一次）；结算靠 status 终态 + UQ `prediction_settlements(market_id, user_id)`。多实例 sweeper 并发执行也安全。

### 5.4 滑点保护
- 买：必须给 `max_cost_points`，实际花费 > 它时返回 409 `PM_SLIPPAGE_EXCEEDED {quoted_points, limit_points}`。按预算买时，`budget_points` 本身就是上限，`max_cost_points` 可省略（默认等于 budget）。
- 卖：必须给 `min_proceeds_points`，实际回款 < 它时同样报错。
- 客户端流程：先 `GET …/quote`，再按用户设置的容差（默认 2%）计算 `max_cost = ceil(quote·1.02)` 或 `min_proceeds = floor(quote·0.98)` 提交。没采用 forecast-arena 的 `expected_market_state_version` 硬校验：热门市场里它会让几乎所有单子失败。

### 5.5 限额与防刷（`domain/prediction_market/limits.py`，纯函数，参数由服务层查好传入）
| 规则 | 常量 | 错误 |
| --- | --- | --- |
| 单市场净投入（Σ买 − Σ卖，各选项合计）≤ `max(MARKET_NET_COST_CAP_MIN=200, S // 4)` | 只检查买入 | 409 `PM_POSITION_LIMIT {limit_points, used_points}` |
| 单场挑战累计买入 ≤ `CHALLENGE_BUY_CAP_POINTS = 3_000`（“每日额度”，因为每日一场挑战） | 只检查买入 | 409 `PM_DAILY_LIMIT {limit_points, used_points}` |
| 单笔份额 1..`MAX_SHARES_PER_TRADE=200`；卖出 ≤ 持有份额 | | 422 `PM_INSUFFICIENT_SHARES {held, requested}` / `VALIDATION_ERROR` |
| 频率：每用户每 60 s ≤ `RATE_LIMIT_TRADES = 12` 笔（跨市场，按 `prediction_trades.created_at` 计，多实例共享） | | 429 `PM_RATE_LIMITED {retry_after_s}` |
| 回款为 0 | | 422 `PM_TRADE_TOO_SMALL` |
| 账号注册 ≥ `CHALLENGE_MIN_ACCOUNT_AGE_HOURS` 小时（读 03 §11.1 的同一配置，默认 72，Q3） | | 403 `PM_NOT_ELIGIBLE {reason:"account_age"}` |
| 挑战进度超前（§3.3） | | 403 `PM_LOCKED_AHEAD` |

- **限额检查与扣款在同一事务**（§5.1 第 8–9 步）。同一用户在两个市场并发下单时，两笔都会改 `point_accounts` 行，后提交者乐观锁冲突、重试时重读额度，额度不会被并发绕过。
- **来回买卖套取整误差**：§4.3 已证明不可行。频率限制再挡掉刷单造成的写压力。
- **多账号对倒**：LMSR 没有对手盘撮合，对倒无法转移价值（§4.3）。“小号先玩挑战拿到未来行情、大号下注”在 03 的全服时间线下不存在；剩余风险是多账号绕开单人限额多吃补贴。缓解办法：
  1. 每个市场的总损失 ≤ S，是有界的积分增发；
  2. 单人上限 S/4，单场 3000；
  3. 账号年龄门槛；
  4. 风控报表 `scripts/pm_abuse_report.py`：找出“成交后 N tick 内价格同向且最终获胜比例”异常高的账户，人工处理；
  5. 时间模型（03 §3.1）保证没有人比全服更早看到未来。

### 5.6 守恒与不变量（测试与运行时断言）
- `Σ 账本中 reason ∈ {market_buy, market_sell, market_payout, market_refund} 的 delta + Σ prediction_markets.pool_points = Σ subsidy_points − Σ subsidy_returned_points`，任何时刻成立（无用户删除时；删除用户会级联删除其流水）。
- 对每个选项：`q_i − q0_i ≥ Σ 持仓 shares_i`（无用户删除时取等号，见 §6）。
- 正常结算前对每个选项：`pool − 100·(q_w − q0_w) ≥ 0`。违反就记 `logger.error`，差额按作废同样的方式计入 `subsidy_returned_points`（为负），因为这说明有 bug。
- `trade_seq` 在市场内连续，等于成交行数。

## 7. AI 参与者：是否首期做

### 7.1 多人市场里的 AI 做市参与者：**首期不做**
- forecast-arena 的做法（`population_service.py`）是：原型参数加 `_rng(seed,"archetype",i)` 扰动，由大量 AI 账户真实下单。放到我们这里有三个问题：
  1. AI 的信念要么来自隐藏真值（泄露答案，还削弱 B 的情报卡），要么只来自公开信息（与先验等价，什么也没增加）；
  2. AI 账户的持仓要兑付，相当于额外增发积分，还会把亏损上界从 S 变成 S + AI 亏损；
  3. AI 的随机流若由挑战 seed 派生，公开成交会泄露 seed 的比特。splitmix64 不是密码学 RNG，见风险 6。
- 首期用 **§4.5 的公开基率先验**，等价于“AI 群体的开盘一致意见”，但不需要账户、不需要兑付，也没有泄密面。
- 二期可选：**原型混合先验**。在 domain 里定义 4–6 个原型（顺势：相信 sentiment；逆向：相信 priced_in；基率派；噪声派），每个原型给出一组档位分布，用 `rand_below(pub_salt, …)` 扰动权重后混合，作为 q0。`pub_salt = int(sha256(challenge_id‖event_id)[:16], 16)`，**不得用挑战 seed**。这样仍然只用到公开信息，只是让开盘价因事件而异、更像“群体”。

### 7.2 单人模式的“AI 群体概率”参考：**不值得做**
- 单人存档的事件每人不同，没有真实群体。模拟群体只有两种信息源：用了隐藏真值，就等于免费情报卡，破坏 B 的积分经济和计分；只用公开信息，就只是一个基率数字，体验上与 B 已有的提示等价。
- 成本不低：需要按存档跑仿真、做 UI、做缓存，还会把玩家锚定到 AI 数字上，影响 B 的校准度统计。
- 替代方案（不在 D 范围内，供 02 参考）：把“多人市场的历史校准度”（同类合约开盘 1 小时的市场概率 vs 实际命中率）作为单人模式的参考卡；或者在 B 中加一种“研究员观点”情报卡，准确率公开（如 70%）、按积分售卖。

## 8. 实时推送

### 8.1 方案：全服 WS 通道 + 进程内 Hub 轮询数据库
- 路由 `api/routers/pm_ws.py`：`@router.websocket("/ws/prediction-markets")`，由自动发现注册。循环实现放在 `api/pm_ws.py`。
- **`PmHub`**（每个进程一个，挂在 `app.state.pm_hub`，在 `main.create_app` 的 lifespan 中启动和停止，开关是 `Settings.PM_BACKGROUND_ENABLED: bool = True`）：
  - 每 `PM_POLL_MS = 1000` ms，在线程池里执行 `svc.poll_markets(session_factory, challenge_ids)`：`SELECT id, status, trade_seq, prices_ppm FROM prediction_markets WHERE challenge_id IN (...) AND status <> 'scheduled'`，只查有订阅的挑战。与上一轮 `(status, trade_seq)` 比较，把变化扇出给本进程订阅者。
  - 每 `PM_SWEEP_MS = 10000` ms，在线程池里执行 `pm_lifecycle.sync_due(session_factory, now)`：对 `live_challenges` 做 `materialize`（幂等），对 `status IN (scheduled, open, closed)` 且已到点的市场逐个 `sync_market`（各自一个事务）。**sweeper 与有没有 WS 连接无关**，这样无人访问时也能按时结算。
- 连接协议：

| 方向 | 消息 |
| --- | --- |
| 客户端 → | `{"t":"watch","challenge_id"}`（订阅列表变化）· `{"t":"subscribe","market_id"}` / `{"t":"unsubscribe","market_id"}`（每连接最多 20 个）· `{"t":"ping"}` |
| 服务端 → | `{"t":"pm_tick","id","seq","status","prices_ppm":[...],"volume_shares","public_tt"}`：已订阅市场有成交或状态变化 |
| | `{"t":"pm_list","challenge_id","rev"}`：该挑战的市场集合或状态变化（开市、休市、结算），客户端重拉列表 |
| | `{"t":"pm_resolved","id","status":"resolved"\|"voided","winning_outcome"}`：客户端重拉 `/me/prediction-settlements` 和余额 |
| | `{"t":"subscribed"\|"unsubscribed","market_id"}` · `{"t":"pong"}` · `{"t":"error","code"}` |

- 鉴权与现有 WS 一致：读 Cookie `session`。未登录时先 accept，再发 `{"t":"error","code":"AUTH_REQUIRED"}`，然后以 4401 关闭。未知 `market_id` 返回 `VALIDATION_ERROR`。
- 推送内容全部是公开数据（价格、份额、状态），不含任何人的持仓。自己的成交结果在 REST 响应里同步返回。

### 8.2 为什么不复用 `/ws/saves/{id}`
现有通道按存档鉴权，按用户刷新率推进行情。预测市场是全服共享的，观看者不一定打开了存档，刷新节奏也应该与个人刷新率无关。塞进去会让每个存档连接都查一次市场表，而且关掉存档页就收不到市场推送。

### 8.3 多实例影响
- 状态全部在数据库，每个实例的 Hub 各自轮询。**不需要粘性会话，也不需要 Redis**。代价是 `实例数 × 有订阅的挑战数` 次/秒的小查询，配合 IX `(challenge_id, status)` 可以忽略。
- sweeper 在每个实例上都跑，靠行锁、版本号和幂等键保证只生效一次（§5.3）。
- 当前 `--workers 1` 时只有一个 Hub。扩到多 worker 或多实例时**推荐 PostgreSQL**（SQLite 多进程写入会频繁 busy）。规模更大时，可在成交提交后 `NOTIFY pm_changed`，Hub 改为 `LISTEN`，那是后续优化。
- 推送延迟上限约 `PM_POLL_MS` 加网络时延，“实时”体感足够。
- 降级：WS 断开时客户端每 3 s 轮询 `GET /prediction-markets/{id}`（详情页）或 `GET /prediction-markets?challenge_id=`（列表页），用 `trade_seq` 判断有无变化。

## 10. 前端

### 10.1 颜色判断：概率涨跌**不算**行情数据
- 概率不是证券价格。多选合约里各档概率此消彼长，零和。“辟谣”概率上升也不代表利好或利空，用红绿只会误导。因此**概率数值、概率变动、价格曲线一律用中性色**：`--text-*`，选中选项用 `--accent`，其他选项用中性灰阶分类色（以明度区分，加图例）；涨跌箭头 ▲▼ 用文字色。
- **持仓的积分盈亏**（`pnl_points`、结算盈亏）属于“盈亏”，可以用 `--up/--down`（网页端是 `--up-color/--down-color`），与持仓页一致。
- 买/卖按钮不用红绿（手机端既有约束，网页端同样遵守）。

### 10.2 网页版 `frontend/`

## 13. 风险

1. **异步挑战与共享市场的根本冲突**：已由 03 的回合制全服时间线根治（没人能先看到未来）。若用户在 03 Q1 否决该时间模型，本风险恢复：超前锁定只能管住本人，管不住小号。
2. **积分通胀**：每场最多 8 个市场 × S。在 4000 档且全被吃满时，一场约 3.2 万积分。实际只有信息优势者能吃到补贴，通常远低于上限。要与 02 的积分产出、消耗一起核算（Q2）。
3. **公共行情可见性**：市场的意义在于“看着行情交易”。如果 C 不提供公共时间线上的行情和快讯视图（§1.2 第 4 条），交易者等于盲猜，价格也就不是“全服认为的概率”。
4. **结算事务规模**：单市场持仓用户上千时，单事务锁住大量账户行，可能拖慢其他人的积分操作。届时改为按 200 用户一批、每批一个事务，靠 `prediction_settlements` UQ 实现断点续跑；市场先进入 `settling` 子状态（需要迁移加枚举值）。
5. **SQLite 写竞争**：热门市场在 SQLite 下只能靠乐观重试，`PM_BUSY` 概率随并发上升。线上多人场景应使用 PostgreSQL，写进 deployment.md。
6. **seed 可被逆推**：splitmix64 不是密码学 RNG，公开行情本身就带有大量 seed 输出，这个风险归 03。D 只保证**不新增**由挑战 seed 派生的公开量（AI 先验用 `pub_salt`）。
7. **A 的规则集版本变化**：如果 A 发布 v2 规则集而挑战仍在进行，重算的事件可能变化。`event_fingerprint` 与 `ruleset_changed` 作废兜底，但玩家体验差。要求 C 在挑战创建时冻结 `events_ruleset`。
8. **Decimal 性能**：`max_shares_for_budget` 的校正循环在极端 q 下可能多算几次，但每次 < 1 ms，可接受。前端预估使用浮点，可能与服务端差 1 积分，由滑点容差吸收。
