# ADR 0003：行情引擎采用确定性计数器 RNG 与补帧

- 状态：已采纳
- 日期：2026-10

## 背景

原版行情使用 `Math.random()`，且行情推进依赖页面是否打开。这带来三个问题：

1. 同一存档无法复现，无法对拍，测试只能断言区间；
2. 关闭页面期间的行情要么丢失，要么只能一次性"跳"到当前时刻，结果依赖观察时机；
3. 服务端化之后，多个连接或多次请求可能各自推进行情，造成不一致。

## 决策

- 随机数由 `rand01(seed, tick, stock_idx, k)` 给出，它是 splitmix64 的计数器式变体，实现在 `backend/src/stocksim/domain/rng.py`。公式与常量以 [CONTRACT.md](../CONTRACT.md) 为准。
- 行情状态只由存档的种子与 tick 推导。服务端按需补算缺失的 tick（catch-up），补算是纯函数调用。
- 领域代码（`domain/`）不得调用 `datetime.now()` 或全局随机数；时间与 tick 由调用方注入。
- 每个交易日 `TICKS_PER_TRADING_DAY` 个 tick，默认 20。

## 理由

- 计数器式 RNG 无状态：任意 `(tick, stock_idx, k)` 可以独立计算，不需要顺序消耗随机数。这使得"跳到第 N 个 tick"是 O(1)，补帧也不需要保存中间状态。
- 同一种子在任何语言、任何机器上结果一致（只依赖整数运算与 mod 2^64），便于与 `legacy/` 对拍。
- 测试可以固定种子做快照断言，不需要 mock 随机数。
- 补帧的结果与观察时机无关，用户离线期间触发的自动交易规则也可以复现。

## 后果

- 正面：可测试、可复现、可对拍，服务端状态简单（只需存种子与 tick）。
- 负面：行情是"可预测"的。对于娱乐性模拟器，这是可接受的；但必须在 UI 与文档中避免暗示行情来自真实市场。
- 负面：一旦修改 RNG 公式或常量，历史存档的行情会改变。因此该公式视为契约，修改需要新 ADR 并考虑存档版本号。
- 负面：补帧的最大回放量受时间跨度限制，需要在服务端设置上限，防止长时间离线后一次性计算过多 tick。
